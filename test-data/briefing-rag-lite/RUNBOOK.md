# 0단계. 준비

## 0-1. 터미널 3개

```sh
# 1번
bash scripts/backend.sh                                    # http://localhost:8000
# 2번
bash scripts/frontend.sh                                   # http://localhost:5173
# 3번
cd backend && uv run python -m app.services.agent_worker
```

3번(워커)의 역할을 알아야 헷갈리지 않는다.

| 무엇 | 누가 실행하나 |
| --- | --- |
| 일정을 **처음 등록**할 때 만들어지는 첫 브리핑 | 백엔드 API가 직접 실행 (워커 없어도 됨) |
| 자료가 추가·변경돼서 **다시 만드는** 브리핑 | **워커만 처리** (워커 없으면 영원히 안 바뀜) |
| 일정을 수정해서 다시 만드는 브리핑 | **워커만 처리** |

이 테스트는 7단계와 9단계에서 재생성을 쓰므로 워커가 반드시 떠 있어야 한다.

## 0-2. `backend/.env` 확인

| 키 | 안 되어 있으면 |
| --- | --- |
| `DATABASE_URL` | 전부 안 됨. http://localhost:8000/api/health/db 로 확인 |
| LLM 키 | 자료 처리가 `failed` → **그 문서는 검색에서 통째로 빠진다.** 브리핑 생성도 실패 |
| `EMBEDDING_PROVIDER` | `none` 이면 키워드 검색만. 테스트는 되고, 화면에 "키워드로 관련 자료를 검색했습니다" 가 붙는다 |
| `EMBEDDING_DIMENSIONS` | 로컬 MiniLM=384, external text-embedding-3-small=1536. 안 맞으면 검색이 안 걸린다 |

의미 검색까지 보려면 `EMBEDDING_PROVIDER=local` + `cd backend && uv sync --extra local`.

## 0-3. DB

- `backend/sql/20260912_0031_document_vectors.sql` 적용 (pgvector 필요). 절차는 `backend/sql/document_vectors.md`.
- **SQL을 직접 실행할 수단을 하나 열어 둔다** (Supabase SQL Editor 또는 psql). 7단계에서 한 줄 필요하다.

## 0-4. 계정

- **팀장(매니저) 계정**으로 로그인한다. `상품관리` 메뉴가 팀장에게만 보인다.
- 10단계까지 하려면 같은 팀 **일반 담당자 계정 2개**를 `관리 > 팀 관리` 에서 미리 초대해 둔다.

# 6단계. 처리 완료 확인

업로드하면 요약·색인이 자동으로 돈다(따로 누를 버튼 없음). 파일당 10~40초.

**화면으로**: 자료실 목록에서 파일 행을 클릭 → 오른쪽 드로어에 **AI 요약이 채워졌으면 완료**.

**SQL로 (빠름)**:

```sql
select file_name, processing_status, processing_error
from file
order by created_at desc
limit 10;
```

- `completed` 5개가 될 때까지 기다린다.
- `failed` 가 있으면 `processing_error` 를 보고 0-2의 LLM 키부터 확인한다.
- 색인까지 확인하려면: `select count(*) from document_chunk where embedding_vector is not null;`

# 7단계. 일정 만들고 **딜 연결하기** ← 여기가 이 테스트의 함정

## 왜 특별한가

브리핑의 📦 제품 자료는 **일정에 붙은 영업 딜**을 거쳐 제품을 찾는다
(`activity.sales_deal_id` → 딜 대표 제품 + 견적 품목).
그런데 **일정 등록 화면에는 영업 딜을 고르는 칸이 없다.** 고객사와 고객만 고른다.
그래서 일정을 만든 뒤 딜을 직접 붙여 줘야 한다. 안 붙이면 📦 제품 자료가 **항상 빈 채로** 나온다.

## 7-1. 일정 등록

**대시보드** 오늘 일정 영역의 **`일정 등록`** 버튼 (또는 `영업` > `캘린더`에서 등록).

| 칸 | 값 |
| --- | --- |
| 제목 * | `SLV-LITE-100 설치환경 및 검수조건 확인` |
| 시작 | **내일 이후** 아무 시각 (지난 일정은 브리핑을 다시 만들지 않는다) |
| 고객사 * | 코덱스 테스트병원 |
| 고객 * | 김검수 |
| 장소 | `영상의학과 2층 검사실 3` |
| 메모 | `전용 전원 220V, 출입문 폭 90cm, 검수코드 BLUE-731 확인` |

**`저장`**

> 제목·메모를 그대로 쓰는 이유: 검색어가
> `고객사명 + 일정 제목 + 딜 제목 + 일정 메모 + 제품명` 으로 조립된다.
> 메모의 `220V`, `90cm`, `BLUE-731` 이 그대로 검색어가 된다.

이 시점에 첫 브리핑이 한 번 만들어진다. 아직 딜이 없어서 📦 제품 자료는 비어 있다. 정상이다.

## 7-2. 딜 붙이기 (SQL 한 줄)

```sql
update activity
set sales_deal_id = (
  select id from sales_deal
  where title = '테스트병원 초음파 도입 딜' and deleted_at is null
)
where title = 'SLV-LITE-100 설치환경 및 검수조건 확인';
```

확인:

```sql
select a.title, d.title as deal, a.starts_at
from activity a left join sales_deal d on d.id = a.sales_deal_id
where a.title = 'SLV-LITE-100 설치환경 및 검수조건 확인';
```

## 7-3. 브리핑 다시 만들게 하기

SQL로 직접 바꾼 것은 백엔드가 모른다. 화면에서 일정을 한 번 건드려 줘야 재생성이 예약된다.

**`영업` > `캘린더`** 에서 그 일정을 **다른 날짜(역시 미래)로 끌어다 놓는다.**
날짜 이동은 시작 시각만 바꾸는 요청이라 방금 붙인 딜을 지우지 않는다.

3번 터미널(워커)에 새 실행이 잡히는 게 보이면 성공이다. 확인은:

```sql
select agent_code, status_code, error_code, created_at
from agent_run
order by created_at desc
limit 5;
```

`contract_management_briefing` 이 `completed` 가 될 때까지 기다린다(보통 10~60초).

# 8단계. 미팅 상세에서 확인

**대시보드**에서 방금 만든 일정을 **클릭** → 오른쪽 드로어가 열린다 → **AI 브리핑** 영역.

갱신이 도는 중이면 제목 옆에 **`최신 자료 반영 중`** 태그가 있다. 5초 간격으로 알아서 바뀐다.

위에서부터 이 순서로 본다.

| 볼 것 | 기대 | 체크리스트 |
| --- | --- | --- |
| **📦 제품 자료** | `01_초음파진단기_제품자료.txt`(대표 제품), `02_이동형카트_제품자료.txt`(견적 품목) 2개 | C-1, C-2 |
| **📎 관련 자료** | `03_초음파도입_납품계약서.pdf`, `04_같은고객사_설치점검.txt` | C-3, C-4 |
| 📎 제목 옆 **`RAG 검색`** 태그 | 보인다 (임베딩이 꺼져 있으면 "키워드로 관련 자료를 검색했습니다" 안내가 함께) | C-5 |
| 인용문 내용 | `BLUE-731`, `220V`, `90cm` 이 들어간 문장 | D-1~3 |
| **계약서 인용 위 페이지 표시** | **`2페이지`** | D-4 |
| 브리핑 본문 | 계약금 30% / 잔금 70% 같은 지급 조건이 반영 | D-5 |
| **`05_다른고객사_제외자료.txt`** | 📎 관련 자료·인용 **어디에도 없어야 한다** | E-1~3 |

- 계약서는 2쪽짜리이고 `BLUE-731` 과 대금 지급 조건은 **2쪽에만** 넣어 뒀다. 1페이지로 표시되면 버그다.
- `05` 에는 `BLUE-731`·`220V`·`90cm` 을 **일부러 똑같이** 넣어 뒀다. 그런데도 안 나와야 정상이다.
- 각 자료의 **`원문 보기`** 로 실제 파일을, **`자료요약 보기`** 로 저장된 요약을 열어 볼 수 있다.
- 브리핑이 인용한 자료에는 **`브리핑에 인용됨`** 표시가 붙는다.

> 📎 관련 자료는 상위 5개 청크만 고른다. `03`·`04` 중 하나가 안 보이면 먼저 6단계로 돌아가
> 그 파일이 `completed` 인지 확인한다. 처리 안 된 파일은 검색에서 통째로 빠진다.

# 9단계. 브리핑 생성 후 자료 추가 → 자동 갱신

1. 8단계 브리핑이 **다 만들어진 것을 확인한 뒤**,
   `자료실 > 영업자료` → `파일 업로드` → `06_브리핑생성후_추가자료.txt`
   → 딜 연결 / 기타 / `테스트병원 초음파 도입 딜`.
2. 6단계 방법으로 `completed` 를 확인한다.
3. 처리가 끝나면 백엔드가 이 미팅의 브리핑을 **알아서 다시 예약한다.** 워커 로그에 새 실행이 뜬다.
4. 미팅 상세를 다시 연다. `최신 자료 반영 중` 태그가 보이다가, 끝나면 `06` 이 📎 관련 자료에 들어와 있다.

> **화면에 수동 새로고침 버튼은 없다.** 자료·일정이 바뀌면 백엔드가 미래 미팅의 브리핑을 미리
> 다시 만들어 두는 방식이다(`backend/app/services/briefing_refresh.py`). 갱신 중에도 이전 브리핑이
> 그대로 보이고, 갱신이 실패하면 "최신 자료로 다시 만들지 못했습니다" 안내만 붙고 이전 것이 남는다.

# 잘 안 될 때

| 증상 | 먼저 볼 것 |
| --- | --- |
| 📦 제품 자료가 계속 비어 있다 | 7-2 SQL이 실제로 반영됐는지, 7-3 재생성을 했는지. `activity.sales_deal_id` 가 null 이면 항상 빈다 |
| 브리핑이 아예 없다 | `select agent_code, status_code, error_code from agent_run order by created_at desc limit 5;` / 워커(3번 터미널)가 떠 있는지 |
| 📎 관련 자료만 비었다 | 그 파일들의 `processing_status` 가 `completed` 인지 |
| "이전 브리핑입니다" 안내 | RAG 적용 전에 만들어진 브리핑이다. 7-3처럼 일정을 한 번 옮기면 새로 만들어진다 |
| 일정을 건드려도 아무 일이 없다 | 일정이 **과거 시각**이거나, 완료 처리됐거나, 고객 담당자가 안 붙어 있다 |
| 자료를 올려도 브리핑이 안 바뀐다 | 워커가 떠 있는지. 그리고 그 자료가 **이 딜/고객사/제품 범위**에 연결됐는지 |
| `05` 가 검색 결과에 나온다 | 고객사 범위 필터 버그 → 체크리스트 E에 기록 |
| 페이지가 1로 나온다 | PDF 청크 `page_start` 문제 → 체크리스트 D에 기록 |
