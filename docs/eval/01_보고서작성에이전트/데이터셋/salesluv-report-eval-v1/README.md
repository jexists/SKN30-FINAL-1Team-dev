# SalesLuv 보고서 평가 데이터셋 v1

9개 가상 회사·9명 가상 고객·27개 영업 건에서 이어지는 2026년 6월의 합성 업무 기록입니다. 실제 고객 자료를 포함하지 않습니다. 텍스트 원문만 사용하며 STT·OCR을 실행하지 않습니다.

| 구분 | 구성 |
|---|---|
| 미팅 | 월·수·금 하루 3건, 주 9건 × 4주 = 36건 |
| 일일 | 미팅이 있는 12일의 보고서 12건 |
| 주간 | 6/1~7, 6/8~14, 6/15~21, 6/22~28의 4건 |
| 월간 | 6/1~30의 1건. 6/29~30 활동 자료는 제공되지 않음 |
| 전체 | 서로 연결된 개발용 평가 53건. 독립적인 53개 표본이 아님 |

각 회사는 매주 한 번 등장합니다. 회사 01~03은 월요일, 04~06은 수요일, 07~09는 금요일입니다. 모든 날짜·시각은 Asia/Seoul 기준입니다. 월간 사례가 하나이므로 이 묶음만으로 월간 품질 전체를 일반화하지 않습니다. 가이드를 개선하는 개발용이며 최종 블라인드 검증용 별도 데이터셋은 아닙니다.

## 파일과 정보 경계

```text
scenarios/company01~09.json   회사별 사전 확정 사실·초기 상태·4주 흐름
generated/meeting*.json      원문 생성/사실 검사 기록·사용량·정확 인용
transcripts/meeting*.txt     최종 한국어 텍스트 원문 36건
seed.json                   계정과 독립된 회사·고객·영업 건·미팅 입력
scenario.json               미팅별 알려진 상태와 관측 사건·후속 업무
cases/<id>/input.json        실제 작성기가 읽을 수 있는 고정 입력
cases/<id>/golden.json       작성기에 전달하지 않는 평가 근거
reference_submissions.json  합성 기준 제출본; 실제 모델 A/B 출력이 아님
manifest.json              사례 종류·기간·상하위 연결·해시
sources.md                 웹 조사 근거와 사용 범위
judge.md                   독립 LLM 평가 기준
```

회사별 사건표를 먼저 작성했습니다. 모델에는 현재 미팅의 공개된 사실과 관련 제품 설명만 제공합니다. 향후 주차의 계약 결과, 골든 판정, 실제 고객 자료를 전송하지 않습니다. 공개 교육 자료의 문장을 복사하거나 번역하지 않고 업무 논점만 참고했습니다. 원천 사건표에 없는 모델의 새 금액·조건·약속은 정답으로 편입하지 않습니다.

`generated`의 사실 일치 검사는 원문 제작 단계의 보조 검사입니다. 보고서 품질 점수나 A/B Judge가 아닙니다. 모델 검사에서 통과했더라도 실제 인용·숫자·업무 말투를 검토하고, 정정 내역을 남깁니다.

## 상태 변화 규칙

`state_before`는 직전까지 관측·기록된 CRM 상태입니다. 이번 미팅에서 새로 확인한 과거 사건은 원문에 해당 실제 날짜와 함께 나타나고, 미팅이 확인된 뒤 `state_after`에 반영합니다. 예를 들어 6/16 서명은 그 이후 미팅에서만 확인됩니다. 미팅 이전 CRM에 미래 최종 결과를 넣지 않습니다.

후속 업무의 예정·진행·실제 이행을 구분합니다. 제안서 발송 약속만으로 발송 완료가 되지 않으며 수신 확인이 있는 후속 미팅에서 완료됩니다. 담당자·기한이 미정인 업무도 존재합니다. 보고서 제출은 사건을 반영할 시점을 연결할 뿐, 생성된 글이 원천의 진실을 바꾸지는 않습니다.

각 미팅의 `observed_event_ids`는 한 번만 적용합니다. 일일 보고서가 같은 미팅을 요약해도 상태를 다시 변경하거나 실적을 이중 집계하지 않습니다. 계약금액은 양사 서명이 확인된 계약의 금액이며 청구·수금·회계 매출과 다릅니다. 주간의 당기 9건과 월 누적 9/18/27/36건을 더해 90건으로 계산하면 오류입니다.

## 두 가지 실행 방식

**전체 흐름 A/B:** A에서는 실제 미팅 출력 36건을 확정해 실제 일일 12건의 입력으로 사용하고, 그 실제 일일에서 주간 4건, 그 실제 주간에서 월간 1건을 작성합니다. B도 동일 원천 사건·일정으로 별도 계정에서 같은 과정을 실행합니다. 상위 입력은 각 실행의 실제 하위 결과이므로 달라질 수 있습니다. 이는 의도한 시스템 전체 비교입니다. A 결과를 확인하고 구조 변경을 논의하기 전 B를 자동 실행하지 않습니다.

**개별 작성기 비교:** `cases/*/input.json`의 고정 입력을 A와 B에 똑같이 전달합니다. 기간 입력은 사람이 검토할 수 있는 합성 기준 제출본으로 구성했습니다. 이를 실제 A가 만든 결과라고 표시하거나 전체 흐름 시험에 끼워 넣지 않습니다. 미팅 입력은 검증된 고정 근거 장부와 해당 시점 CRM을 사용합니다.

계정에 전체 4주 데이터를 넣은 뒤 앱에서 현재 CRM을 다시 조회하면 당시 입력과 다를 수 있습니다. 개별 비교에는 반드시 고정 입력을 사용하고, 전체 흐름 실행기는 사전 사건표의 시점별 상태와 실제 이전 출력만 사용해야 합니다. 미팅분석·보고서 외 ML, 계약·일정 생성, 알림은 보고서 시험에서 별도로 격리합니다.

## 반복 가능한 계정 입력

실제 앱 계정이 필요하면 관리자에게 테스트 계정과 팀을 발급받고 초기 팀 설정을 완료합니다. 셀프 회원가입 스크립트가 아니며 외부 Auth 계정을 자동 생성하지 않습니다. 팀의 기본 공개 영업 파이프라인, `needs_validation`, `new_installation`, 활동 `visit`·`call` 코드를 사용합니다. 빠진 설정이 있으면 중단하며 기존 팀 설정을 자동 변경하지 않습니다.

저장 대상은 `CustomerCompany` 9개, `CustomerContact` 9개와 담당자 관계, `SalesDeal` 27개, `Activity` 36개입니다. 여기의 회사는 계정 소속 `Team`이 아니라 영업 대상 거래처입니다. 제품 카탈로그 생성은 포함하지 않으며 영업 건의 설명에 검토 제품 범위를 담습니다. 골든·기준 보고서·LLM 출력은 이 명령으로 DB에 넣지 않습니다.

backend에서 실행합니다. `<...>`에는 해당 테스트 대상의 UUID와 출력 위치를 지정합니다.

```sh
uv run python -m scripts.seed_report_evaluation \
  --member <기존-member-UUID> --team <기존-team-UUID> \
  --output-dir <새로운-출력폴더>
```

기본 동작은 DB에 연결하지 않는 검사·내보내기입니다. `id_map.json`과 `meeting_requests.jsonl`이 만들어지며 요청 JSON은 실제 `ReportGenerationCreate` 계약을 검사합니다. API 실행은 하지 않습니다. 앱에서 생성하는 용도의 요청에는 현재 CRM을 조회하는 미팅분석 단계가 포함되므로 개별 작성기 A/B용 고정 입력과 구분합니다.

위 명령에 `--apply`를 명시하면 설정된 비운영 DB의 활성 계정·팀 일치·역할·필수 설정을 확인한 뒤 하나의 트랜잭션으로 삽입합니다. `APP_ENV=production` 쓰기는 거부합니다. UUID는 계정 UUID와 데이터셋 논리 ID에서 결정되므로 다른 계정은 분리됩니다. 재실행 시 기존 행을 덮어쓰지 않으며 소유·회사·고객 관계 충돌이나 삭제된 행을 발견하면 중단합니다. 내보내기 파일의 존재는 DB 적용 성공을 의미하지 않습니다.

실제 테스트 대상·설정을 확인한 경우에만 `--apply`를 사용합니다. 현재 데이터셋 제작 검사는 임시 SQLite와 가상 계정으로 수행하며 외부 DB/Auth를 변경하지 않습니다. SQLite 검사는 PostgreSQL 고유 제약·RLS의 실통합 검증을 대체하지 않습니다.

## 제작 및 재검사

원천 사실을 바꾸지 않는 단순 재검사는 외부 호출 없이 수행합니다.

```sh
APP_ENV=test uv run python -m scripts.build_report_evaluation
APP_ENV=test uv run pytest -q tests/test_seed_report_evaluation.py tests/test_report_evaluation_dataset.py
```

`generate_report_evaluation_transcripts.py`는 현재 설정 모델로 **유료 외부 생성 호출**을 수행하는 제작 도구입니다. 평소 재사용 때 실행할 필요가 없습니다. 이미 완성된 원문·고정 입력을 그대로 재사용해야 입력이 같은 실험이 됩니다. 원문을 수정했다면 사실 인용·근거 구간·SHA256과 파생 입력을 모두 다시 검사하고 데이터셋 버전을 구분합니다.
