# 샘플 데이터 생성 보고서 (2026년 3분기)

## 1. 생성 목적

로그인 가능한 4개 계정이 속한 팀 `테스트1`(브레이스 / 영업1팀)에는 업무 데이터가 하나도
없어 로그인해도 모든 화면이 비어 있었다. 기존에 있던 고객사 12·딜 11·활동 17·보고서 5 건은
전부 다른 팀(`SalesLuv 데모팀`) 소유라 이 계정들에게는 보이지 않는다.

네 명이 3개월간 실제로 CRM 을 써 온 것처럼, 고객 → 딜(영업·견적·계약) → 활동 → 보고서 →
발주 → 매출이 실제 외래키로 이어지는 데이터를 넣었다.

## 2. 데이터 기준 기간

`2026-06-01` ~ `2026-08-25`. 기준일 이후 날짜로 기록된 활동·견적 발행·계약 체결은 없다.
견적 유효기간과 계약 종료일, 진행 중 발주의 입고 예정일만 미래 날짜를 가진다.

## 3. 사용한 영업사원 계정

담당자는 이메일로 조회한 실제 `member.id` 를 그대로 썼다. 새 계정은 만들지 않았다.

## 12~14. 금액

| 항목 | 금액 |
| --- | --- |
| 전체 딜 금액 | 808,010,000 |
| 확정(매출) 13건 | 323,560,000 |
| 발주 금액 9건 | 148,440,000 |

**이 프로젝트에는 매출 테이블이 없다.** 대시보드는 확정 단계(`outcome_code = 'confirmed'`)
딜의 `deal_amount` 를 `contract_signed_on` 이 속한 달로 집계한다
([`dashboard.py:270-296`](../backend/app/api/dashboard.py#L270-L296)). 이 보고서의 매출도
같은 기준이다. 견적과 계약도 별도 테이블이 아니라 `sales_deal` 의
`quote_*` / `contract_*` 컬럼이다.

따라서 **분할 매출은 스키마상 표현할 수 없다.** 대신 한 계약을 두 번에 나눠 발주하는
분할 발주로 그 상황을 만들었다(아래 거래 #1, #2).

## 17. 데이터 연결 구조

```text
customer_company ──┬── customer_contact ── customer_contact_assignee ── member
                   │
                   └── sales_deal ──┬── (견적: quote_no / quote_issued_on / quote_valid_until)
                    │  sales_pipeline_stage
                    │               ├── (계약: contract_no / contract_signed_on / contract_ends_on)
                    │               │        └── 확정 딜의 deal_amount = 그 달의 매출
                    │               ├── purchase_order ── purchase_order_item ── product
                    │               ├── support_request ── support_response
                    │               └── activity ──┬── report (미팅보고서, source_activity_id)
                    │                              └── report_activity ── report (일일·주간·월간)
                    └── sales_target (담당자 x 고객사 x 월)
```

데이터 근거는 `data/sample/Sales_DB.xlsx` 다. 품목리스트 시트의 제품군·모델명·판매단가를
`product` 로, 영업현황 시트의 병원명·지역·부서·연락처·유입경로를 고객사와 담당자로 옮겼다.
공급사 이름은 `3개회사_매출데이터_2022-2024_샘플완료.xlsx` 의 회사명을 썼다.
기존 `data/sample/` 파일은 읽기만 했고 그대로 있다.

## 18. 데이터 검증 결과

`uv run python -m scripts.verify_sample_bracelet` 의 15개 검사가 모두 통과했다.

- 관계: 팀 밖 고객사·담당자·딜을 참조하는 행 0건, 활동이 다른 고객사의 딜에 붙은 경우 0건,
  고객불만의 고객사와 딜의 고객사 불일치 0건, 미팅보고서에 근거 일정이 없는 경우 0건
- 날짜: `개설 ≤ 견적 ≤ 계약` 을 어긴 딜 0건, 계약일보다 앞선 발주 0건,
  기준일(2026-08-25) 이후로 기록된 활동·견적·계약 0건
- 금액: 발주 합계가 계약 금액을 넘는 딜 0건, 확정 단계인데 계약일이 없는 딜 0건
- 번호: 견적번호 중복 0건

또 로그인 없이 라우터 함수를 직접 호출해 네 계정 모두 대시보드(오늘 일정·팔로업·C/S·
월 목표·공지·갱신 대상·주간 밴드)와 영업현황·고객·활동·보고서·발주·고객불만 목록이
실제로 채워지는 것을 확인했다.

## 21. 재실행

모든 신규 행의 id 는 `uuid5(팀 id, "sample2026q3:<종류>:<자연키>")` 라 스크립트를 다시
실행해도 같은 행을 갱신할 뿐 늘어나지 않는다. 이 규칙으로 이번 샘플분만 골라낼 수도 있다.
기존 4개 계정·팀·다른 팀의 데이터는 읽기만 하고 고치지 않았다.

```bash
cd backend
uv run python -m scripts.seed_sample_bracelet --dry-run   # 저장하지 않고 결과만
uv run python -m scripts.seed_sample_bracelet
uv run python -m scripts.verify_sample_bracelet
```
