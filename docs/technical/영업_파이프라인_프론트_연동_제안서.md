# 영업 파이프라인 프론트 기능 제안서

> 이 문서는 필요한 기능과 업무 규칙, 현재 백엔드 계약만 정의한다. 화면 위치, 컴포넌트 구성, 디자인과 상태 관리 방식은 프론트엔드에서 결정한다. 상세 타입 제한은 실행 중인 FastAPI의 `/openapi.json`을 최종 기준으로 한다.

## 1. 목적

한 영업 딜이 영업 시작부터 견적, 계약, 발주까지 이동하는 현재 단계를 모든 화면에서 같은 데이터로 보여준다. 팀마다 여러 영업 파이프라인을 저장해 사용할 수 있고, 이미 생성된 딜의 단계 정의는 이후 설정 변경으로 바뀌지 않아야 한다.

## 2. 필요한 기능

| 기능 | 역할 | 필요한 동작 |
|---|---|---|
| 파이프라인 선택 | 어떤 영업 절차의 딜을 볼지 정한다. | 사용 가능한 파이프라인을 조회하고 하나를 선택해 그 파이프라인의 단계와 딜을 보여준다. |
| 영업현황 | 현재 팀의 딜 전체를 관리한다. | 단계의 업무 구분과 관계없이 접근 가능한 모든 딜을 조회한다. 보드에서는 선택한 파이프라인의 단계 순서로 보여준다. |
| 견적현황 | 현재 견적 업무 중인 딜만 보여준다. | 현재 단계의 `phase_code=quote`인 딜만 조회하고 견적 번호·발행일·유효기한을 보여준다. |
| 계약현황 | 현재 계약 업무 중인 딜만 보여준다. | 현재 단계의 `phase_code=contract`인 딜만 조회하고 계약 번호·체결일·종료일을 보여준다. |
| 발주현황 | 현재 발주 업무 중인 딜과 실제 발주 정보를 보여준다. | 현재 단계의 `phase_code=order`인 딜을 기준으로 연결된 발주와 품목을 조회한다. 고객사와 담당자는 연결된 딜 정보를 사용한다. |
| 딜 생성 | 사용할 영업 절차와 시작 단계를 정한다. | published 파이프라인과 그 안의 단계를 선택해 딜을 생성한다. 다른 파이프라인 소속 단계는 선택할 수 없다. |
| 단계 이동 | 딜의 현재 업무 위치를 바꾼다. | 같은 파이프라인 안의 단계로만 이동한다. 이동 뒤 화면별 phase 조건에 따라 기존 화면에서 빠지고 새 화면에 나타난다. |
| 파이프라인 관리 | 팀장이 새 영업 절차를 준비하고 배포한다. | draft를 만들고 단계를 추가·수정·삭제한 뒤 publish한다. published 파이프라인은 수정하지 않고, 변경이 필요하면 복사한 새 draft를 사용한다. |
| 표시값 관리 | 팀 업무 용어를 설정한다. | 고객 담당자 상태, 일정 분류, 일정 태그, 딜 유형, 발주 상태의 이름·순서를 추가·수정·삭제하고, 색상을 사용하는 항목은 색상도 관리한다. |
| 과거 데이터 표시 | 설정 변경 후에도 기존 기록을 이해할 수 있게 한다. | archived 파이프라인은 저장된 단계 정의를, 삭제된 표시값은 마지막 저장 이름을 기존 데이터에서 계속 보여준다. 새 입력 선택지에서는 제외한다. |

## 3. 화면별 포함 규칙

| 화면 | 포함되는 딜 |
|---|---|
| 영업현황 | 전체 phase |
| 견적현황 | 현재 `quote` phase |
| 계약현황 | 현재 `contract` phase |
| 발주현황 | 현재 `order` phase |

화면 이름, 단계 표시 이름, 단계 순번으로 포함 여부를 판단하지 않는다. 서버가 반환하는 현재 단계의 `phase_code`를 사용한다.

예를 들어 계약현황에 있던 딜이 발주 단계로 이동하면 계약현황에서는 빠지고 발주현황에 나타나야 한다. 영업현황에는 이동 전후 모두 나타난다.

## 4. 고정되는 업무 의미

아래 값은 서버의 필터와 업무 규칙에 사용하므로 팀장이 변경하거나 자유 입력할 수 없다.

- 영업 phase: `sales | quote | contract | order | closed`
- 영업 결과: `in_progress | confirmed | cancelled`
- 일정 성격: `meeting | task`
- 발주 결과: `in_progress | completed | cancelled`
- 파이프라인 상태: `draft | published | archived`

팀장이 설정하는 단계와 표시값은 위 고정 의미 중 하나를 선택해 사용한다. 한국어 이름, 색상과 표시 순서는 업무 편의를 위한 값이며 시스템 의미를 대신하지 않는다.

## 5. 파이프라인 변경 규칙

- 한 팀은 여러 파이프라인을 동시에 사용할 수 있다.
- 새 팀에는 기본 published 파이프라인 하나와 기본 단계가 제공된다.
- 한 팀의 기본 published 파이프라인은 하나다.
- draft에서만 단계 구조와 표시값을 수정한다.
- published 파이프라인과 단계는 이름·색상·순서를 포함해 수정하지 않는다.
- 변경이 필요하면 기존 파이프라인을 새 draft로 복사한 뒤 수정하고 publish한다.
- 기존 딜은 기존 파이프라인과 단계를 계속 사용한다.
- 새 딜부터 새로 published한 파이프라인을 선택할 수 있다.
- archived 파이프라인은 신규 딜과 단계 이동 선택지에서 제외하지만 기존 딜 조회에는 남긴다.

## 6. 프론트에서 필요한 데이터

### 파이프라인

- 파이프라인 UUID, 이름, 설명, 상태, 기본 여부
- 파이프라인에 속한 단계 UUID와 정렬 순서
- 단계 코드, 표시 이름, 색상, phase, 영업 결과

### 영업 딜

- 딜 UUID와 표시용 딜 번호
- 현재 파이프라인 UUID와 현재 단계 UUID
- 현재 단계의 이름, 색상, phase, 영업 결과
- 고객사, 고객 담당자, 담당 팀원, 상품
- 딜 유형, 금액, 딜 시작일과 종료일
- 견적 번호·발행일·유효기한
- 계약 번호·체결일·종료일

### 발주

- 발주 UUID와 표시용 발주 번호
- 필수 영업 딜 UUID
- 발주 상태와 고정 발주 결과
- 공급사, 발주일, 납기일, 입고 예정일, 품목
- 표시용 고객사와 담당자는 연결된 딜에서 파생한 값

### 팀별 표시값

- UUID, 안정적인 코드, 표시 이름, 색상, 순서
- 일정 분류·태그의 고정 일정 성격
- 발주 상태의 고정 발주 결과
- 삭제 여부는 신규 선택 가능 여부를 판단할 수 있어야 한다.

## 7. 공통 동작 요구사항

- 조회·상세·수정·이동·삭제의 식별자는 UUID를 사용한다.
- 딜 번호, 견적 번호, 계약 번호, 발주 번호와 설정 코드는 표시·검색값으로만 사용한다.
- 팀원은 본인 담당 범위, 팀장은 같은 팀의 허용 범위만 볼 수 있다.
- 다른 팀 데이터는 존재 여부도 노출하지 않는다.
- loading, 조회 실패, 정상적인 빈 결과를 구분한다.
- 변경 요청 중 중복 제출과 중복 이동을 막는다.
- `409` 동시 변경 충돌이 발생하면 최신 단계와 딜을 다시 조회하고 사용자에게 변경 충돌을 알린다.
- archived 또는 삭제된 설정값은 기존 데이터에서 표시하되 신규 선택지에는 넣지 않는다.
- filled 팀과 empty 팀의 데이터가 섞이지 않아야 한다.
- 새로고침 뒤에도 서버에 저장된 파이프라인 선택, 현재 단계와 업무 데이터가 다시 보여야 한다.

## 8. 목업 교체 원칙

- 한 화면을 API 데이터로 전환하면 같은 목록에 목업과 API 데이터를 섞지 않는다.
- 목업을 다른 화면이 아직 사용하면 파일은 유지한다.
- 모든 소비 화면이 전환된 뒤에만 해당 목업을 제거한다.
- 표시 이름으로 기존 목업과 API 레코드를 연결하지 않고 서버 UUID를 사용한다.

## 9. 현재 사용할 API

### 조회 선택지

| 역할 | 메서드와 경로 | 응답 핵심값 |
|---|---|---|
| 파이프라인 목록 | `GET /api/sales-pipelines` | `id,name,description,status_code,is_default,published_at?,archived_at?,created_at,updated_at` |
| 파이프라인 단계 | `GET /api/sales-pipelines/{sales_pipeline_id}/stages` | `id,sales_pipeline_id,stage_code,name,tone,phase_code,outcome_code,position` |
| 딜 유형 | `GET /api/sales-deal-types` | `id,code,name,position` |
| 상품 | `GET /api/products?q=&skip=&limit=` | active 상품 페이지 `id,name,active` |
| 발주 상태 | `GET /api/purchase-order-statuses` | `id,code,name,tone,outcome_code,position` |
| 고객 상태 | `GET /api/customer-contact-statuses` | `id,code,name,tone,position` |
| 일정 분류 | `GET /api/activity-categories?activity_type=meeting|task` | `id,code,name,tone,position,activity_type` |
| 일정 태그 | `GET /api/activity-action-tags?activity_type=meeting|task` | `id,code,name,tone,position,activity_type` |

파이프라인 목록에는 기존 딜 표시를 위해 published와 archived가 함께 온다. 신규 딜과 이동 선택지는 `status_code=published`만 사용하고 archived는 과거 딜 표시용으로만 사용한다. archived 단계로 생성·이동을 요청하면 `404 sales_pipeline_stage_not_found`다. lookup 목록은 soft delete되지 않은 현재 선택지만 반환한다.

### 영업 딜

| 기능 | 메서드와 경로 | 요청·필터 |
|---|---|---|
| 목록 | `GET /api/sales-deals` | `q?,start_date?,end_date?,owner_member_id*?,sales_pipeline_id?,sales_pipeline_stage_id*?,phase_code*?,skip=0,limit=30` |
| 상세 | `GET /api/sales-deals/{sales_deal_id}` | UUID |
| 생성 | `POST /api/sales-deals` | 아래 `SalesDealCreate` |
| 수정 | `PATCH /api/sales-deals/{sales_deal_id}` | 아래 수정 가능 필드 중 보낸 값만 변경 |
| 단계 이동 | `POST /api/sales-deals/{sales_deal_id}/move` | `expected_sales_pipeline_stage_id,sales_pipeline_stage_id,stage_position` |
| 삭제 | `DELETE /api/sales-deals/{sales_deal_id}` | 성공 `204`; soft delete |

`SalesDealCreate`의 필수값은 `customer_company_id`, `product_id`, `sales_pipeline_id`, `sales_pipeline_stage_id`, `deal_type_code`, `deal_amount`, `opened_on`이다. `customer_contact_id`, `title`, `description`, `quote_no`, `quote_issued_on`, `quote_valid_until`, `contract_no`, `contract_signed_on`, `contract_ends_on`, `warranty_terms`, `expected_delivery_at`, `memo`는 nullable이다. 제목을 생략하면 서버가 고객사명과 상품명으로 만든다. 서버는 `deal_no`를 `SL-DL-YYYY-####` 형식으로 발급하고 생성 성공 시 `201`과 `Location`을 반환한다.

`PATCH`는 고객사, 고객 담당자, 상품, 제목, 설명, 딜 유형 코드, 금액, 시작일, 견적·계약 필드, 보증 조건, 납품 예정 시각, 메모를 수정한다. pipeline과 stage는 `PATCH`가 아니라 단계 이동 API로만 바꾼다.

`SalesDealRead`는 위 업무 필드와 함께 다음 표시값을 반환한다.

- 고객사: `customer_company_id`, `customer_company_name`, `customer_company_region_code?`
- 고객 담당자: `customer_contact_id?`, `customer_contact_name?`
- 담당자·상품: `owner_member_id`, `owner_display_name`, `product_id?`, `product_name?`
- 파이프라인: `sales_pipeline_id`, `sales_pipeline_name`, `sales_pipeline_status_code`, `sales_pipeline_is_default`
- 단계: `sales_pipeline_stage_id`, `sales_pipeline_stage_code`, `sales_pipeline_stage_name`, `sales_pipeline_stage_tone`, `sales_pipeline_stage_phase_code`, `sales_pipeline_stage_outcome_code`, `sales_pipeline_stage_position`
- 딜 유형: `sales_deal_type_id`, `deal_type_code`, `deal_type_name`
- 날짜: `opened_on`, `closed_on?`, 견적·계약 날짜와 `created_at`, `updated_at`

목록은 `opened_on DESC, id` 순이다. 같은 Query key를 반복해 여러 `owner_member_id`, `sales_pipeline_stage_id`, `phase_code`를 보낸다. 페이지 응답은 `items,skip,limit,total,has_more,next_skip`이다.

### 발주

| 기능 | 메서드와 경로 | 요청·필터 |
|---|---|---|
| 목록 | `GET /api/orders` | `q?,supplier_name?,stage_code*?,start_date?,end_date?,owner_member_id*?,skip=0,limit=30` |
| 상세 | `GET /api/orders/{purchase_order_id}` | UUID |
| 생성 | `POST /api/orders` | 아래 `OrderCreate` |
| 수정 | `PATCH /api/orders/{purchase_order_id}` | 보낸 값만 변경 |
| 상태 이동 | `POST /api/orders/{purchase_order_id}/move` | `expected_stage_code,stage_code` |
| 삭제 | `DELETE /api/orders/{purchase_order_id}` | 성공 `204`; soft delete |

`OrderCreate`의 필수값은 `sales_deal_id`, `supplier_name`, `stage_code`, `ordered_on`, `due_on`, `expected_receipt_on`, `items`이며 `memo`만 nullable이다. `items`는 1~100개이고 각 항목은 `product_id`, 1 이상의 `quantity`, 0 이상의 `unit_price`를 가진다. 서버가 `order_no`를 생성하고, 고객사와 담당자는 연결 딜에서 파생한다. 발주 생성 트랜잭션에서 딜은 같은 파이프라인의 첫 `order` phase 단계로 이동한다. 신규 발주와 발주의 딜 변경은 published 파이프라인 딜만 허용하며 archived 딜은 `404 deal_not_found`다. 생성 성공은 `201`과 `Location`이다.

`OrderRead`는 `id,order_no,sales_deal_id,deal_no`, 파생한 고객사·담당자 UUID/이름, 공급사, 발주 상태 UUID/code/name/tone/outcome/position, 세 날짜, `memo?`, 상품명이 포함된 `items`, `created_at`, `updated_at`을 반환한다.

### 성공·오류 처리

- 조회·수정·이동 `200`, 생성 `201`, 삭제 `204`다. 빈 목록은 `200`과 빈 `items`다.
- 인증 없음·만료는 `401`; 본인 담당 범위를 넘는 필터는 `403 scope_not_allowed`다.
- 다른 팀이거나 보이지 않는 리소스는 존재 여부를 숨기고 `404`를 반환한다.
- 단계/상태가 다른 요청과 먼저 바뀌었으면 `409 invalid_state_transition`이다. 최신 상세를 다시 조회한 뒤 사용자가 다시 시도할 수 있게 한다.
- 유일값·동시 저장 충돌은 `409 sales_deal_conflict|order_conflict`다.
- 다른 pipeline의 stage, 잘못된 날짜·순서·설정 코드는 `422`와 안정적인 `detail` 코드를 반환한다.
- 딜 관련 주요 코드는 `sales_pipeline_not_found`, `sales_pipeline_stage_not_found`, `sales_deal_type_code_not_found`, `sales_pipeline_stage_pipeline_mismatch`, `invalid_sales_deal_dates`, `invalid_sales_deal_position`이다.
- 발주 관련 주요 코드는 `purchase_order_status_code_not_found`, `invalid_order_dates`, `sales_pipeline_order_stage_not_found`이다.

## 10. 후속 관리 기능

파이프라인 draft 생성·복사·단계 편집·publish·archive와 다섯 lookup의 추가·수정·삭제 API는 이번 연결 범위에는 아직 없다. 프론트가 팀장 관리 기능을 실제 동작으로 제공하려면 해당 백엔드 API가 먼저 필요하다. 지금은 조회 API가 반환하는 기본값을 사용하고, 없는 mutation을 가정해 저장 UI를 연결하지 않는다.

필요한 후속 기능의 역할은 다음과 같다.

- 기존 published 정의를 새 draft로 복사한다.
- draft의 단계 이름·색상·phase·outcome·순서를 검증하고 편집한다.
- draft를 publish한 뒤 해당 버전을 불변으로 만든다.
- published를 archive하되 기존 딜 조회와 단계 표시를 유지한다.
- 고객 상태, 일정 분류·태그, 딜 유형, 발주 상태를 팀 범위에서 추가·수정·soft delete한다.

프론트의 폴더, 파일, 컴포넌트, 화면 배치와 디자인은 이 문서의 범위가 아니다.

## 11. 새로 준비된 백엔드와 남은 프론트 연결

이 문서를 쓴 뒤 백엔드에 아래 API가 추가되었다. 모두 `develop`에서 동작하며 프론트 연결만 남았다.
프론트의 폴더·컴포넌트·디자인은 이 문서의 범위가 아니고, 어떤 데이터를 어디서 받는지만 정한다.

| 기능 | 메서드와 경로 | 프론트 현재 상태 |
|---|---|---|
| 일정 완료 | `POST /api/activities/{activity_id}/complete` | 미연결. 캘린더는 `completed_at`을 읽어 표시만 하고 바꾸지 못한다. |
| 보고서 | `GET/POST /api/reports`, `GET/PATCH/DELETE /api/reports/{report_id}` | 미연결. 업무보고 화면이 API를 호출하지 않는다. |
| 보고서 제출 | `POST /api/reports/{report_id}/submit` | 미연결. |
| 공지·개인 지시 | `GET /api/notices`, `GET /api/notices/{notice_id}` | 미연결. 대시보드가 `/api/auth/me` 외에는 호출하지 않는다. |
| 자료실 문서 | `GET/POST /api/documents`, `GET/PATCH /api/documents/{document_id}` | 미연결. 자료실 화면이 API를 호출하지 않는다. |
| 자료 파일 | `POST /api/documents/{document_id}/files`, `GET .../files/{file_id}/download` | 미연결. |
| 보고서 AI 초안 | `POST /api/agent-runs`, `GET /api/agent-runs/{agent_run_id}` | 미연결. |
| 대시보드 집계 | `GET /api/dashboard` | 미연결. 카드·주간 밴드가 모두 목업이다. |

### 화면별 남은 작업

| 화면 | 지금 상태 | 해야 할 일 |
|---|---|---|
| 영업·견적·계약·발주현황 | 조회 연결 완료 | 견적·계약 **작성·수정 폼**을 `PATCH /api/sales-deals/{id}`에 연결한다. 현재 폼은 고객사·상품·금액·유형·시작일·메모 여섯 값만 보내고 `quote_no`, `quote_issued_on`, `quote_valid_until`, `contract_no`, `contract_signed_on`, `contract_ends_on`을 보내지 않는다. |
| 캘린더 | 일정 조회·등록·수정·삭제 연결 완료 | 완료 처리를 `complete`에 연결한다. 완료 시각은 서버가 정하므로 값을 보내지 않는다. 유스케이스에 완료 취소가 없어 토글이 아니라 단방향이다. |
| 대시보드 | `/api/auth/me`만 호출 | `GET /api/dashboard`로 카드 5개와 주간 밴드를 받고, 공지·개인 지시는 같은 응답의 `notices`·`directives`를 쓴다. 오늘 일정 목록은 `GET /api/activities`다. |
| 업무보고 | 목업 | 미팅·일자별·주간 보고서를 `reports` API로 바꾸고 제출은 `submit`을 쓴다. 유스케이스에 월간 보고서가 없어 종류는 세 가지다. |
| 자료실 | 목업 | 목록·등록·수정을 `documents` API로, 업로드와 다운로드를 파일 API로 바꾼다. |

### 대시보드 응답 구조

`GET /api/dashboard?date=&owner_member_id=&notice_limit=3&renewal_within_days=` 하나로 아래를 받는다.
`date`를 생략하면 `Asia/Seoul` 오늘이고, 모든 집계는 응답의 `as_of` 한 시각을 기준으로 한다.

| key | 화면 자리 | 내용 |
|---|---|---|
| `notices` | 공지 | `total`과 최근 `items` |
| `directives` | 팀장 지시사항 | `total`과 최근 `items`. 로그인한 사람이 받은 지시만 |
| `visited_companies` | 오늘 방문 회사 | `count`. 같은 회사를 여러 번 방문해도 1로 센다 |
| `activities` | 오늘 일정 | `count`. 미팅과 업무를 모두 포함 |
| `follow_ups` | 미완료 후속업무 | `total`, `overdue`, `due_within_7_days` |
| `support_requests` | C/S 대응요청 | `total`, `in_progress`, `urgent` |
| `contract_renewals` | 계약갱신 예정 | `count`와 `items`. 각 항목에 `deal_no`, `title`, `customer_company_name`, `contract_no`, `contract_ends_on` |
| `sales_target` | 매출 목표 | `target_month`, `target_amount`, `confirmed_amount`, `in_progress_amount`, `achievement_rate` |
| `weekly` | weekly plan | `start_date`, `end_date`, `days[7]`. 각 날짜에 `meeting_count`, `task_count`, `due_count` |

- 주간 밴드는 기준일이 속한 주의 **일요일부터 7일**이다. 전 주·다음 주는 `date`를 옮겨 다시 부른다.
- 계약갱신 기준 일수는 서버가 정하지 않는다. `renewal_within_days`를 주면 그 창으로 거르고, 생략하면 기준일 이후 만료 예정 전체를 센다.
- 매출 목표가 없으면 `achievement_rate`는 `0`이 아니라 `null`이다. 미설정과 미달성을 구분한다.
- `새봄정형외과 외 1곳`, `D-4` 같은 표시 문자열은 서버가 만들지 않는다. `items`와 날짜로 프론트가 조합한다.
- 오늘 일정 **목록**은 이 응답에 없다. `GET /api/activities`를 따로 부른다.

### 개발 DB 현재 데이터

연결한 화면이 비어 보이면 버그가 아니라 seed가 없는 것이다. 2026-08-18 기준 filled 데모팀 현황이다.

| 테이블 | 건수 | 연결 시 화면 |
|---|---|---|
| `customer_company` / `customer_contact` | 6 / 32 | 고객현황 정상 |
| `activity` | 12 | 캘린더 정상 |
| `sales_deal` | 61 | 영업·계약현황 정상 |
| `purchase_order` | 2 | 발주현황 정상 |
| `support_request` | 3 | 고객불만 정상 |
| `notice` | 7 (팀 공지 5, 개인 지시 2) | 대시보드 공지 정상 |
| `report` | **0** | 업무보고 빈 목록 |
| `document` / `file` | **0** | 자료실 빈 목록 |
| `sales_target` | **0** | 매출 목표 `achievement_rate=null` |
| `agent_run` | **0** | 실행 이력 없음 |

- 대시보드 계약갱신도 0으로 나온다. `confirmed` 딜 47건이 모두 `contract_ends_on`이 비어 있어서다.
- `report`, `document`는 화면에서 직접 만들어 보는 편이 seed 보다 확인 가치가 크다. 필요하면 seed 를 따로 만든다.
- empty 데모팀은 모든 업무 데이터가 0이다. 빈 화면 처리를 확인할 때 쓴다.

### 연결할 때 지킬 것

- 대시보드는 아직 `shared/agenda`의 목업 ID를 쓴다. 실제 API에 `a1` 같은 목업 ID를 보내지 않도록 ID 출처를 먼저 UUID로 바꾼다.
- 보고서는 `draft`에서만 수정·삭제할 수 있다. 제출한 뒤에는 `409 report_not_editable`이다.
- 보고서 제출은 `expected_status_code`를 함께 보내 중복 제출을 막는다.
- 공지는 `scope=team|personal`로 나눠 조회한다. 응답의 `scope`가 팀 공지와 개인 지시를 구분해 주므로 `recipient_member_id`로 다시 판정하지 않는다.
- 파일 업로드는 `multipart/form-data`만 쓴다. 허용 형식은 `.pdf`, `.docx`, `.pptx`이고 형식 위반은 `415`, 크기 초과는 `413`이다.
- 다운로드는 짧게 사는 서명 URL을 받아 쓴다. 서버는 저장소 경로를 응답하지 않으므로 파일 주소를 따로 만들지 않는다.
- AI 초안은 `202`와 `Location`을 받고 `GET /api/agent-runs/{agent_run_id}`로 polling한다. 같은 작업을 다시 보낼 때는 같은 `idempotency_key`를 쓴다.
- AI 초안 결과는 제안이다. 사용자가 확인해 `PATCH /api/reports/{report_id}`로 반영하기 전까지 보고서 내용을 바꾸지 않는다.
- 8절의 목업 교체 원칙을 그대로 적용한다. 한 화면을 전환하면 그 화면에서 목업과 API 데이터를 섞지 않는다.

### 아직 백엔드가 없는 것

- 매출 목표 등록·수정 API (`sales_target`은 조회만 하고 현재 0건이라 달성률이 `null`이다)
- 팀 명부 조회 API와 담당자 전환
- 파이프라인 draft·publish·archive와 표시값 관리 (10절)

## 12. 완료 확인

- [ ] 영업현황은 모든 phase의 딜을 보여준다.
- [ ] 견적·계약·발주는 현재 phase에 맞는 딜만 보여준다.
- [ ] 딜이 phase를 이동하면 화면 포함 관계가 즉시 바뀐다.
- [ ] 여러 published·archived 파이프라인의 기존 딜을 올바르게 조회한다.
- [ ] 새 딜은 선택한 pipeline과 그 소속 stage로 생성된다.
- [ ] 현재 범위에서는 published pipeline과 설정값을 조회만 한다.
- [ ] 후속 관리 API가 생기면 published 변경 대신 새 draft 복사 흐름을 사용한다.
- [ ] 후속 설정 수정·삭제가 기존 기록을 깨뜨리지 않는다.
- [ ] 모든 mutation identity가 UUID다.
- [ ] filled/empty 팀 데이터가 섞이지 않는다.
- [ ] loading/error/empty와 권한·동시 변경 오류를 구분한다.
- [ ] 견적·계약 화면에서 견적 번호·발행일·유효기한과 계약 번호·체결일·종료일을 저장한다.
- [ ] 캘린더에서 일정을 완료·재개하고 새로고침 뒤에도 유지된다.
- [ ] 대시보드 공지와 개인 지시가 실제 API 데이터다.
- [ ] 업무보고를 작성·수정·제출하고 제출한 보고서는 수정되지 않는다.
- [ ] 자료실에서 허용 형식만 업로드되고 다운로드가 서명 URL로 동작한다.
- [ ] AI 초안이 사용자 확인 전에는 보고서를 바꾸지 않는다.
- [ ] 대시보드 카드 숫자와 그 카드를 눌러 여는 목록의 전체 수가 같다.
- [ ] 주간 밴드의 전 주·다음 주 이동이 달력 주 단위로 움직인다.
- [ ] 데이터가 없는 화면이 오류가 아니라 빈 상태로 보인다.
- [ ] empty 데모팀으로 로그인했을 때 모든 화면이 빈 상태로 정상 동작한다.
