# SalesLuv 목표 ERD v2

> 상태: 설계 진행 중 — 확정된 요구사항만 누적 기록한다.<br>
> 마지막 갱신: 2026-08-23<br>
> 기존 물리 스키마 문서: [SalesLuv ERD](SalesLuv_ERD.md)

## 1. 문서 운영 원칙

- 이 문서는 향후 구현할 목표 데이터 모델을 정의한다.
- 기존 `SalesLuv_ERD.md`는 현재 물리 스키마의 기준 문서로 유지한다.
- 논의 중인 내용은 확정 요구사항과 분리하여 `미결정 사항`에 기록한다.
- 확정된 설계는 다음 논의를 시작하기 전에 이 문서에 바로 반영한다.
- 현재 단계에서는 도메인별 구체적인 컬럼을 정의하지 않고 테이블, 관계, 책임과 권한 경계만 정의한다. 단, 전 테이블에 공통으로 적용하기로 확정한 감사 및 소프트 삭제 컬럼은 전역 규칙으로 기록한다.
- 전체 도메인의 테이블과 핵심 관계를 먼저 확정한다. 조회·수정·삭제 같은 세부 권한, 이력, 컬럼과 제약조건은 큰 구조가 완성된 뒤 결정한다.

## 2. 설계 및 전환 방식

목표 ERD v2를 먼저 설계한 뒤 기존 ERD와 매핑하여 단계적으로 전환한다.

1. 현재 구현에 얽매이지 않고 목표 ERD v2를 확정한다.
2. 기존 테이블을 유지, 분리, 이름 변경, 신규 추가, 폐기 대상으로 분류한다.
3. 데이터 이관과 애플리케이션 변경을 단계적으로 진행한다.

## 3. 전역 감사 및 소프트 삭제 규칙

목표 ERD v2의 모든 테이블에 다음 공통 컬럼을 둔다.

| 컬럼 | 목적 |
|---|---|
| `created_at` | 생성 일시 |
| `created_ip` | 생성 요청 IP |
| `updated_at` | 마지막 수정 일시 |
| `updated_ip` | 마지막 수정 요청 IP |
| `deleted_at` | 소프트 삭제 일시 |
| `deleted_ip` | 소프트 삭제 요청 IP |

다음 처리 원칙을 적용한다.

- 레코드 생성 시 생성 일시와 생성 IP를 기록한다.
- 레코드 수정 시 수정 일시와 수정 IP를 갱신한다.
- 일반적인 삭제는 물리 삭제하지 않고 삭제 일시와 삭제 IP를 기록하는 소프트 삭제로 처리한다.
- 일반 조회는 `deleted_at IS NULL`인 레코드만 반환한다.
- 삭제된 레코드는 복구, 감사 또는 별도로 허용된 관리 기능에서만 명시적으로 조회한다.
- IP 주소의 판별 방식, 삭제 복구, 연쇄 삭제 및 보존기간 만료 후 물리 삭제 정책은 상세 설계 단계에서 결정한다.

## 4. 용어

| 용어 | 의미 |
|---|---|
| `organization` | CRM을 사용하는 내부 회사 |
| `team` | 내부 회사에 소속된 팀 |
| `member` | CRM을 사용하는 사내 사용자 또는 영업사원 |
| `customer_company` | 영업 대상인 외부 고객사 |
| `customer_contact` | 외부 고객사에 소속된 담당자 또는 직원 |
| `customer_contact_assignment` | 사내 `member`와 외부 `customer_contact` 사이의 담당 관계 |

내부 회사와 외부 고객사를 모두 `company`라고 부르지 않는다. 내부 회사는 `organization`, 외부 고객사는 `customer_company`로 구분한다.

## 5. 확정 테이블

조직 및 외부 고객 영역에는 다음 테이블이 필요하다.

1. `organization`
2. `team`
3. `member`
4. `customer_company`
5. `customer_contact`
6. `customer_contact_assignment`

현재는 다음 테이블을 만들지 않는다.

- `customer_company_rel`
- `customer_contact_rel`
- `customer_company_assignment`

단순한 1:N 관계에는 중간 관계 테이블을 추가하지 않는다. 관계 테이블이 필요한 경우에는 `rel` 대신 업무 목적이 드러나는 이름을 사용한다.

## 6. 확정 관계와 카디널리티

| 관계 | 카디널리티 | 의미 |
|---|---:|---|
| `organization` → `team` | 1:N | 하나의 내부 회사에 여러 팀이 소속된다. |
| `team` → `member` | 1:N | 하나의 팀에 여러 사내 사용자가 소속된다. |
| `organization` → `customer_company` | 1:N | 하나의 내부 회사가 여러 외부 고객사를 관리한다. |
| `customer_company` → `customer_contact` | 1:N | 하나의 외부 고객사에 여러 외부 담당자가 소속된다. |
| `member` → `customer_contact_assignment` | 1:N | 한 사내 사용자가 여러 담당 관계를 가질 수 있다. |
| `customer_contact` → `customer_contact_assignment` | 1:N | 한 외부 담당자를 여러 사내 사용자가 공동 담당할 수 있다. |
| `member` ↔ `customer_contact` | N:M | `customer_contact_assignment`를 통해 성립하는 담당 관계다. |

추가 관계 규칙은 다음과 같다.

- 시스템에는 여러 `organization`이 존재할 수 있다.
- `member` 한 명은 하나의 `organization`과 하나의 `team`에만 소속된다.
- `member`의 `organization` 소속은 `team`을 통해 결정한다. 개념 모델에 중복된 직접 관계를 추가하지 않는다.
- `customer_company` 하나는 하나의 `organization`에 속한다.
- `customer_contact` 한 명은 현재 기준으로 하나의 `customer_company`에만 소속된다.
- `customer_contact`의 `organization`은 소속 `customer_company`를 통해 결정한다.
- `customer_contact_assignment`는 반드시 동일한 `organization`에 속한 `member`와 `customer_contact`만 연결한다.

## 7. 관계의 목적

### 7.1 외부 고객사 소속 관계

`customer_company`와 `customer_contact`의 1:N 관계는 외부 담당자가 어느 외부 고객사에 소속되어 있는지를 표현한다.

이 관계에는 별도의 중간 테이블을 두지 않는다.

### 7.2 사내 담당 관계

`member`와 `customer_contact`의 N:M 관계는 어떤 사내 사용자가 해당 외부 담당자를 담당하는지를 표현한다.

이 관계는 `customer_contact_assignment`로 연결한다. 외부 고객사 소속 관계와 사내 담당 관계는 목적이 다르므로 동시에 존재해야 한다.

## 8. `customer_contact_assignment`의 역할

`customer_contact_assignment`는 다음 역할을 가진다.

- `member`와 `customer_contact`의 N:M 관계를 해소한다.
- 실제 영업 담당 또는 공동 담당 관계를 표현한다.
- 일반 `member`가 조회할 수 있는 외부 담당자의 기본 데이터 범위를 결정한다.
- 향후 주 담당자·공동 담당자 구분이나 담당 이력이 필요해질 경우 그 업무 의미를 확장할 수 있는 독립 엔티티다.

다음 역할은 담당하지 않는다.

- 외부 담당자의 고객사 소속 관계
- 고객사 전체에 대한 담당 관계
- 같은 고객사에 속한 모든 외부 담당자의 자동 조회 권한
- 수정, 삭제, 내보내기 등 모든 행위 권한의 자동 부여

따라서 권한은 다음 두 축으로 구분한다.

- 데이터 범위: `customer_contact_assignment`
- 허용 행위: 별도의 역할 및 권한 정책

## 9. 담당 범위와 조회 권한 경계

기본 조회 정책은 다음과 같다.

1. `organization`이 최상위 데이터 격리 경계다.
2. 서로 다른 `organization` 사이에는 담당 관계를 만들 수 없다.
3. 일반 `member`는 자신에게 배정된 `customer_contact`를 조회할 수 있다.
4. 일반 `member`는 배정된 `customer_contact`가 속한 `customer_company`의 기본 정보를 조회할 수 있다.
5. 같은 `customer_company`에 속해 있더라도 자신에게 배정되지 않은 다른 `customer_contact`는 자동으로 조회할 수 없다.
6. 같은 `team` 소속이라는 사실만으로 다른 팀원의 담당 고객이 자동 공유되지는 않는다.
7. 고객사 기본 정보 조회 권한은 딜, 견적, 계약, 발주, 고객불만, 매출 등 고객사 관련 전체 데이터의 조회 권한을 자동으로 의미하지 않는다.
8. 담당 관계가 부여하는 범위는 우선 기본 조회 범위다. 수정, 삭제, 내보내기 권한은 별도로 결정한다.

## 10. `customer_company_assignment` 추가 조건

현재는 고객사 단위 담당 테이블을 만들지 않는다. 다음 요구사항 중 하나 이상이 실제로 필요해지면 `customer_company_assignment`를 독립 테이블로 추가한다.

- 고객사 전체를 담당하는 계정 담당자가 필요하다.
- 고객사의 현재 및 향후 모든 외부 담당자를 자동으로 조회해야 한다.
- 외부 담당자가 아직 등록되지 않은 고객사를 먼저 사내 사용자에게 배정해야 한다.
- 딜, 계약, 고객불만 등 고객사 단위 업무 전체에 담당 권한을 상속해야 한다.
- 고객사 단위 주 담당자, 공동 담당자 또는 담당 팀을 관리해야 한다.
- 고객사 전체를 다른 담당자나 팀으로 일괄 이관해야 한다.

추가하는 경우 `customer_contact_assignment`를 재사용하거나 의미를 넓히지 않고 별도 관계로 유지한다. 두 담당 관계가 동시에 존재할 때 권한을 합산할지, 우선순위를 둘지는 도입 시점에 결정한다.

## 11. 영업 파이프라인

### 11.1 딜과 견적서 관계

다음 관계를 확정한다.

```text
deal 1:N quote
```

- 하나의 `deal`에는 여러 `quote`가 존재할 수 있다.
- 견적을 수정하거나 재발행할 때 기존 `quote`를 덮어쓰지 않고 새로운 `quote`를 생성한다.
- 이전 `quote`는 견적 변경 및 협상 이력으로 그대로 보존한다.
- 별도의 견적 백업 테이블을 만들지 않는다.
- 현재 단계에서는 `quote`와 `quote_version`을 분리하지 않는다. 각각의 `quote`가 발행 시점의 견적 내용을 나타낸다.
- DB 장애 복구를 위한 시스템 백업은 이 업무 이력과 별개의 운영 정책으로 다룬다.

### 11.2 계약과 견적서 관계

계약 생성에 견적서를 필수로 요구하지 않는다.

- `contract`는 연결된 `quote` 없이 독립적으로 생성할 수 있다.
- 견적을 기반으로 계약한 경우에는 해당 `quote`를 선택적으로 참조할 수 있다.
- 견적이 없는 계약을 위해 빈 견적이나 임시 견적을 생성하지 않는다.
- `contract` 하나가 참조하는 원본 `quote`는 없거나 하나다.

### 11.3 딜과 계약 관계 및 파이프라인 상태

다음 관계를 확정한다.

```text
deal 1:N contract
```

- 모든 `contract`는 반드시 하나의 `deal`에 속한다.
- 하나의 `deal`에는 여러 `contract`가 존재할 수 있다.
- `contract`가 `quote`를 참조하는 경우 해당 `quote`는 같은 `deal`에 속해야 한다.
- `deal`은 견적, 계약 등 전체 영업 진행 상황을 대표하는 파이프라인의 중심 엔티티다.
- `deal`의 상태값은 현재 영업 진행 단계를 요약하며 딜 목록과 파이프라인 화면에서 사용한다.
- 견적과 계약의 상세 데이터 및 이력은 각각의 테이블에 보존하고, `deal` 상태값만으로 대체하지 않는다.
- 구체적인 딜 상태 종류와 상태 전환 규칙은 상세 설계 단계에서 결정한다.

하나의 `quote`에서 여러 `contract`가 만들어질 수 있는지와 딜·발주의 관계는 아직 확정하지 않았다.

## 12. 기존 ERD와의 주요 차이

- 기존 ERD의 최상위 데이터 경계는 `team`이지만 목표 v2에서는 `organization`이 최상위 경계다.
- 기존에는 외부 담당자와 사내 담당자의 관계가 단일 담당자 형태지만 목표 v2에서는 `customer_contact_assignment`를 통한 N:M 관계다.
- 외부 고객사는 특정 팀이 아니라 `organization`이 관리하는 대상으로 모델링한다.

구체적인 기존 테이블 매핑과 마이그레이션 순서는 목표 ERD v2 전체 구조가 확정된 후 작성한다.

## 13. 설계 진행 순서

현재는 전체 ERD의 큰 틀을 먼저 설계한다.

1. 각 도메인에 필요한 핵심 테이블을 정한다.
2. 테이블 사이의 1:1, 1:N, N:M 관계를 정한다.
3. 전체 도메인이 연결된 뒤 권한, 이력, 상태, 컬럼과 제약조건을 상세 설계한다.

조직·외부 고객 영역의 큰 구조는 확정됐다. 다음으로 영업 파이프라인, 고객불만, 매출·정산, AI 에이전트 대화 로그 등 다른 도메인의 핵심 테이블과 관계를 결정한다.

## 14. 미결정 사항

### 14.1 큰 구조 단계에서 결정할 사항

1. 하나의 견적에서 여러 계약이 만들어질 수 있는지와 딜·발주를 어떻게 연결할 것인가?
2. 고객불만을 고객사, 외부 담당자, 계약과 각각 어떻게 연결할 것인가?
3. 매출을 계약에서 계산만 할지 독립된 매출·정산 엔티티로 관리할 것인가?
4. 일정과 보고서가 고객, 딜, 계약 등 여러 업무 대상을 어떻게 참조할 것인가?
5. AI 에이전트의 대화, 실행, 모델 호출 및 원본 로그를 어떤 계층으로 분리할 것인가?

### 14.2 큰 구조 확정 후 결정할 상세 사항

1. `customer_contact_assignment`가 조회 외에 수정, 삭제, 내보내기 중 어떤 행위까지 허용하는가?
2. 조직 관리자와 팀장은 담당 배정 없이 어느 범위까지 조회할 수 있는가?
3. 팀장이 팀원들의 담당 고객을 자동으로 조회할 수 있는가?
4. 주 담당자와 공동 담당자를 구분해야 하는가?
5. 담당자 변경 및 이관 이력을 보존해야 하는가?
6. 배정되지 않은 `customer_contact`를 누가 조회하고 배정할 수 있는가?
