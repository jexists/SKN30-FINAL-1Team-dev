나머지는 함수와 서비스로.

SalesLuv는 서로 다른 책임과 판단 범위를 가진 Assistant Agent, Deal Agent, Portfolio Agent가 협업하는 멀티에이전트 CRM이다. Deal Agent는 딜별 독립 인스턴스로 실행되며, Portfolio Agent와 제약 및 판단 결과를 주고받아 전체 영업 우선순위와 일정을 완성한다.

01

왜 멀티에이전트이고, 왜 LLM인가

멀티에이전트가 성립하는 상황은 하나다 — 한 영업사원이 서로 다른 상태의 여러 딜을 동시에 관리하며, 한정된 시간을 그 사이에 배분해야 한다. 활성 딜이 1~2개면 단일 에이전트가 낫다. 이 구조는 딜이 늘어나 하나의 문맥에 다 넣을 수 없을 때 성립한다.

1-1 · 왜 멀티에이전트인가 — 결정적 이유는 하나다

목적 함수의 분리, 그리고 그 사이의 협상

개별 딜의 최선("이번 주 미팅을 잡아야 한다")과 전체 시간 배분("모든 딜이 그렇게 말한다")은 서로 충돌하는 다른 목적 함수다. 한 판단 주체에 두 목표를 함께 주면 대변인과 심판을 한 사람이 맡는 꼴이 되어 판단이 서로를 오염시키고, 충돌이 생겼을 때 제약을 주고받으며 재판단할 상대가 없다.

그래서 목적별로 판단 주체를 분리한다 — Deal은 딜 내부의 최선만(국소), Portfolio는 전체 배분만(전역). 충돌하면 Portfolio가 제약을 되돌려 보내고, 해당 딜이 자기 문맥에서 다시 판단한다(양방향 재판단). 이 분리와 협상이 멀티에이전트의 유일한 결정적 근거다.

따라오는 운영상 이점 — 멀티의 증명은 아니다. 문맥 격리(딜 간 정보 간섭 없음) · 부분 재실행(바뀐 딜만 재계산) · 실패 격리(재시도 단위 축소)는 단일 에이전트 + 세션 구조로도 얻을 수 있다. 이 구조를 택하면 기본으로 따라온다.

1-2 · 왜 룰 기반이 아니라 LLM인가

LLM이 필요한 지점은 둘이다. ① 비정형 데이터 해석 — 딜 입력의 원천부터가 STT 전사·OCR·사용자 자유 입력이다. 룰이 돌아갈 구조화 필드(단계·위험·약속)는 LLM이 그 원문에서 추출해 만든 2차 산물이라, LLM 없이는 요약·정리·판단의 대상 자체가 만들어지지 않는다. "예산은 확보됐지만 결재권자가 바뀌었다"에서 위험을 뽑는 룰은 만들 수 없다. ② 에이전트 간 소통과 우선순위 판단 — 에이전트끼리 주고받는 Deal State의 위험·근거·제약은 숫자가 아니라 의미다. 정성 신호(관계 위험 · 이의 · 경쟁 맥락)를 비교해 트레이드오프를 정하고, 재분석 요청의 제약을 해석하고, 그 이유를 승인 화면에 문장으로 설명하는 일은 가중치 공식으로 되지 않는다. 결정적 조건(기한 D-day · 미접촉 · 정체 감지)은 여전히 룰이 하고, Deal Agent를 깨우는 것도 룰이다 — 룰은 트리거와 계산, LLM은 해석과 판단.
02

멀티에이전트 구조도 — 한 사이클

Deal Agent 역할을 딜 수만큼 독립 인스턴스로 병렬 실행하고(map), 구조화된 Deal State만 위로 올린다. Portfolio Agent가 우선순위를 판별하고, 충돌한 딜에는 제약을 붙여 재분석을 요청하며(양방향), 팀장 단위는 Team Reduce 1회 호출로 종합한다. 승인된 변경은 CRM에 반영되어 다음 사이클의 입력이 된다. 파란 대형 노드가 에이전트다 — 나머지는 에이전트에게 데이터를 나르고, 결과를 받아 적는 조연이다.

03

각 구성요소 설명

역할 경계의 한 줄 규칙 — Deal은 딜 내부(무엇·왜), Portfolio는 딜 사이(언제·순서), 팀 층위는 팀장 승인을 거친 보조 경로. 이 경계는 프롬프트 규율이 아니라 스키마 계약(위로는 Deal State만, 아래로는 ReanalysisRequest만)으로 강제된다.

구성요소유형하는 일
Assistant Agent에이전트 ⟳챗봇 진입점. 질문 범위를 해석하고 권한 안에서 조회하며, 판단이 필요하면 세션을 실행해 근거와 함께 답한다
Deal Agent ×N에이전트 ⟳딜 하나의 위험·가치·다음 행동을 판단하고, 확정된 미팅에는 목표·질문·위험·준비물로 구성된 브리핑을 생성. 딜 내부만 본다 — 다른 딜의 존재를 모름
Portfolio Agent에이전트 ⟳전체 딜을 비교해 우선순위 판별, 캘린더를 조회하며 일정 배치(언제·순서). 딜 사이만 본다 — 원문 기록엔 접근 없음, 충돌 딜에는 재분석 요청
Team Reduce판단 호출 ×1팀원별 결과·보고서·매출 집계를 한 번에 종합해 팀 리스크·코칭 포인트 제안. 팀장 승인 → 팀 목표 변경 이벤트 → Portfolio 재계획의 보조 피드백 경로
미팅 보고서 작성 함수LLM 함수미팅 후 STT·OCR·직접 입력을 해석해 같은 카드 안에 보고서 초안과 고객·딜 변경안을 생성
Orchestrator일반 서비스이벤트에 맞는 Agent·함수를 호출하고 데이터를 전달하며, 승인 후 저장·미팅 완료·재분석 요청을 처리. 콘텐츠를 직접 판단하거나 작성하지 않음
04

사용 시나리오 — 팀원과 팀장

두 화면의 원칙은 같다 — LLM은 분석·준비·초안·제안까지, 확정은 사람의 선택과 결재로. 팀원은 에이전트를 직접 부르지 않는다. 추천을 받고, 선택하고, 승인하는 것이 사용자의 일이다.

팀원(영업사원)의 하루

1
하루 시작 — 오늘의 우선순위 확인전체 딜 비교 결과와 추천 일정을 보고, 선택한 항목만 캘린더에 등록
Portfolio Agent
2
미팅 전 — 카드에서 브리핑 확인오늘의 미팅 카드를 열어 고객 히스토리, 딜 상태, 확인할 질문과 준비물을 확인
Deal Agent
3
미팅 후 — 같은 카드에서 보고서 작성STT·OCR·직접 입력 → LLM이 미팅 보고서와 고객·딜 변경안 초안 생성
미팅 보고서 작성 함수
4
보고서 확정 — 미팅 완료사용자가 초안을 수정·확정하면 보고서가 제출되고 해당 일정이 완료 상태로 전환
사용자 확정
5
정보 반영 — 다음 판단 시작승인된 변경만 CRM에 반영되고, 해당 Deal과 전체 Portfolio가 새로운 정보로 재계산
Deal → Portfolio
6
수시 — 챗봇 질문"이번 달 성사 가능성 높은 딜은?" — 권한 범위에서 근거와 함께 답변
Assistant Agent

팀장의 하루 — 숫자(매출 집계·달성률)는 LLM이 아니라 서비스가 계산한다

1
아침 — 팀 브리핑팀원별 파이프라인 요약, 관계·지연 리스크, 코칭 포인트, 목표 갭 해석 확인
Team Reduce
2
보고 현황 확인완료된 미팅별 보고서와 아직 보고서가 확정되지 않은 일정을 한 화면에서 확인
일반 서비스
3
보고서 검토팀원이 미팅 카드에서 확정한 보고서와 주요 이슈를 확인
조회
4
매출 관리매출 자료(xlsx) 업로드 → 추출 초안 확인·확정 → 목표 달성률 자동 집계
서비스 계산 → 확정
5
팀 목표 조정집중 상품·기간 목표 변경을 결재하면, 팀원 전원의 우선순위가 자동 재계산
이벤트 → Portfolio
6
수시 — 팀 범위 질문"이번 분기 리스크 큰 고객사는?" — 팀 권한 범위에서 조회·답변
Assistant Agent
Key Sentence

SalesLuv는 서로 다른 목표와 판단 범위를 가진 Assistant·Deal·Portfolio Agent가 협업하고, 딜별 Deal Agent와 Portfolio Agent가 제약과 판단 결과를 주고받는 양방향 재판단으로 전체 우선순위와 일정을 완성하는 멀티에이전트 CRM이다. 팀장 단위는 Team Reduce 1회 호출로 종합한다(reduce). 에이전트는 판단 루프가 필요한 곳에만 둔다.
