# SalesLuv API 최소 공통 규약

부트캠프 프로젝트에서 프론트엔드 화면과 ERD가 확정되기 전에도 공통으로 적용할 최소 규칙만 정의한다. HTTP의 일반적인 사용법은 반복해서 규정하지 않으며, 상세 엔드포인트와 필드는 기능이 확정될 때 정한다. 제품·Agent 동작 경계는 [SalesLuv 멀티에이전트 운영 플로우](../SalesLuv_멀티에이전트_운영_플로우.html)를 따른다.

## 1. 경로와 이름

- 기본 경로는 `/api`이며 현재는 버전을 붙이지 않는다.
- 업무 리소스 URL은 영문 소문자, 복수 명사, `kebab-case`를 사용한다.
- Query와 JSON 필드명은 `snake_case`를 사용한다.

표기 예시이며 실제 리소스는 기능 확정 후 정한다.

```http
GET /api/purchase-orders
GET /api/activities?start_date=2026-08-12
```

## 2. 요청 검증

- 요청은 Pydantic 모델로 검증한다.
- 요청 모델에 `ConfigDict(extra="forbid")`를 적용하고, 정의되지 않은 JSON 필드는 `422 Unprocessable Entity`로 거절한다.
- 잘못된 값을 서버가 추측해서 자동 보정하지 않는다.

## 3. 응답과 에러

- 성공 응답은 실제 객체나 배열을 그대로 반환한다.
- `success`, `data`, `message` 공통 포장은 사용하지 않는다.
- 에러는 적절한 HTTP 상태 코드와 FastAPI 기본 `detail` 형식을 사용한다.

```json
{
  "detail": "activity not found"
}
```

## 4. 날짜와 금액

- 업무 기준 시간대는 `Asia/Seoul`이다.
- 날짜는 `YYYY-MM-DD` 형식을 사용한다.
- 일시는 `+09:00`을 포함한 ISO 8601 형식을 사용한다.
- 금액은 KRW 원 단위 정수로 전달하고 쉼표나 통화 기호를 포함하지 않는다.

형식 예시이며 필드 계약이 아니다.

```json
{
  "expected_close_date": "2026-08-31",
  "starts_at": "2026-08-12T14:30:00+09:00",
  "contract_value": 1200000
}
```

## 5. 인증과 데이터 범위

- 사용자·조직·팀 범위는 검증된 인증 정보로 서버가 결정한다.
- 요청에 포함된 `user_id`, `organization_id`, `team_id`를 소유권이나 권한의 근거로 신뢰하지 않는다.

## 6. LLM과 Agent

- LLM·Agent가 만드는 요청에도 프론트엔드 요청과 동일한 검증과 권한 검사를 적용한다.
- LLM·Agent가 제안한 실제 데이터 변경은 사용자 확인 후 반영한다.
- 검증 실패, 사용자 거절 또는 Agent 실패 시 미확정 결과를 저장하지 않고 기존 확정 데이터를 유지한다.

## 7. 최소 보안

- CORS는 환경별로 허용한 프론트엔드 주소만 등록한다.
- 토큰, 비밀번호, API 키, 고객 데이터는 로그에 남기지 않는다.
- 실제 고객 데이터를 사용할 때는 SQL 쿼리 파라미터가 출력되지 않도록 SQL echo를 끈다.

## 8. API 계약과 문서

- 기능 API의 요청·응답 계약은 Pydantic 모델과 FastAPI의 명시적 타입 선언으로 정의한다.
- `/docs`와 `/openapi.json`은 FastAPI가 자동 생성한 결과를 사용한다.
- 같은 내용을 수동 OpenAPI YAML로 중복 관리하지 않는다.

## 기능 확정 후 결정할 항목

- 실제 엔드포인트와 요청·응답 필드
- 인증·세션 방식
- ID 형식
- 목록 포장, 검색, 정렬, 페이지네이션
- `PATCH`의 필드별 `null` 의미
- 리소스별 삭제·취소·보관 및 승인·확정 흐름
- 중복 요청 방지와 커스텀 에러 코드
- 계층 구조, 트랜잭션 구현, 테스트 범위 등 기능별 구현 세부사항
