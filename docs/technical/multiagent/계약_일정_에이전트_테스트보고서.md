## 1. 테스트 범위와 대상

### 1.1 범위

SalesLuv 멀티 에이전트 **다섯 개**(`docs/project-overview.md` 7.1) 중
**영업·계약관리·일정관리 두 에이전트**를 대상으로 한다. 나머지 셋은 경계면만 확인하고
내부 동작은 검증 대상에서 제외한다.

| 에이전트 | 구현 상태 | 이 보고서에서 |
|---|---|---|
| 미팅 분석 `meeting_analysis` | 구현됨 | 제외 |
| 보고서 작성 `report_writing` | 구현됨 | 경계면만 (트리거로 들어오는 상태 변화) |
| **영업·계약관리 `contract_management`** | 구현됨 | **검증 대상** |
| **일정관리 `schedule_management`** | 구현됨 | **검증 대상** |
| 자료요약 `document_summary` | **개발 중** (이슈 #80) | 경계면만 (8절 한계 참고) |

검증 대상 두 에이전트의 실행 단위는 넷이다.

| 검증 대상 | `agent_code` |
|---|---|
| 계약관리 — 제안 대상 선별 | `contract_management_select_candidates` |
| 계약관리 — 다음 미팅 제안 | `contract_management_next_meeting` |
| 계약관리 — 미팅 브리핑 | `contract_management_briefing` |
| 일정관리 — 시간 후보 추천 | `schedule_management` |

### 1.2 LLM 시스템 특유의 검증 난점

일반 소프트웨어 테스트와 다른 점이 둘 있다.

**① 출력이 실행마다 다르다.** 같은 입력에 같은 문장이 나오지 않는다. 따라서
"기대 문자열과 일치하는가"로 검증할 수 없다.

**② 외부 호출에 비용과 시간이 든다.** 모든 테스트를 실제 LLM으로 돌릴 수 없다.

이 두 가지 때문에 테스트를 **네 계층으로 나눴다.**

## 2. 테스트 전략

```
계층 1  단위 테스트        LLM 없이, 결정적 로직만        빠름 · 무료 · 매 커밋
계층 2  실제 LLM 개별      각 에이전트 1회씩              느림 · 유료 · 수동
계층 3  실제 LLM 반복      같은 입력 20회                 안정성 확인
계층 4  실 데이터 전수     운영 데이터 81딜               최종 확인
```

### 2.1 계층 1 — 단위 테스트 (LLM 없음)

LLM 호출을 대역(fake)으로 대체하고 **결정적으로 확인 가능한 것만** 검증한다.

| 검증 항목 | 왜 여기서 |
|---|---|
| 위험 신호 판정 규칙 | 날짜 계산이라 LLM과 무관 |
| 입력 스냅샷 조립 범위 | 어떤 딜이 들어가는지는 규칙 |
| 서버 재검증 로직 | 업무시간·충돌 판정은 규칙 |
| 개인정보 필터링 | 허용 목록 검사 |
| 동시성 방어 | 쿼리 순서와 잠금 |
| 상태 전이 | pending → accepted |

### 2.2 계층 2 — 실제 LLM 개별 실행

각 에이전트를 실제 LLM으로 한 번씩 돌려 **출력 형식과 내용 규칙**을 확인한다.

### 2.3 계층 3 — 실제 LLM 반복 실행

같은 입력으로 전체 흐름을 20회 돌려 **안정성**을 본다. 1회 성공은 우연일 수 있다.

### 2.4 계층 4 — 실 데이터 전수 실행

개발 DB의 실제 딜 전체에 파이프라인을 돌리고, 나온 결과를 **전수 검사**한다.
합성 입력으로는 드러나지 않는 문제를 찾기 위한 계층이다.

## 3. 테스트 계획

### 3.1 검증 기준

문장 일치는 검사하지 않는다. 대신 아래를 본다.

| # | 기준 | 확인 방법 |
|---|---|---|
| 1 | 출력 형식이 스키마에 맞는가 | 구조화 출력 파싱 |
| 2 | 필수 값이 비어 있지 않은가 | 단위 테스트 |
| 3 | **입력에 없는 사실을 만들지 않았는가** | 날짜·ID 대조 |
| 4 | **개인정보가 LLM에 전달되지 않았는가** | 입력 스냅샷 검사 |
| 5 | 일정이 요청 기간·업무시간 안인가 | 서버 재검증 |
| 6 | 기존 일정과 겹치지 않는가 | 서버 재계산 |
| 7 | 확인 불가 정보가 `missing_information`에 있는가 | 출력 검사 |
| 8 | 승인한 후보가 브리핑에 연결되는가 | 통합 테스트 |
| 9 | **트리거 딜과 응답 딜이 일치하는가** | 딜 ID 대조 |
| 10 | **과거·주말 날짜가 없는가** | 실 데이터 전수 검사 |

3·4·9·10이 LLM 시스템에 특유한 항목이다.

### 4.2 계층 2 — 실제 LLM 개별 실행

실행일 2026-08-25. `5 passed in 40.64s`, 실제 DB 쓰기 없음.

| 테스트 | 결과 | 확인 내용 |
|---|---:|---|
| 제안 대상 선별 | 통과 | 신호가 겹치거나 심각도 높은 딜 선별, 약한 신호 제외 |
| 다음 미팅 제안 | 통과 | 위험, 부족한 정보, 미팅 제안 |
| 시간 후보 추천 | 통과 | 기간, 업무시간, 소요 시간, 충돌 |
| 미팅 브리핑 | 통과 | 승인 미팅, 계약 요약, 근거와 부족한 정보 |
| 전체 흐름 | 통과 | 후보 승인과 `activity_id` 전달 |

**출력 내용 관찰**

*제안 대상 선별* — 위험 신호가 겹치는 딜(계약 만료 + 미해결 C/S)과 심각도가 높은 딜(견적
만료 임박)을 선별했다. 신호가 약한 딜은 후보에서 뺐다. **입력에 없는 딜 ID를 만들지
않았다.** 선택 이유가 근거 신호를 정확히 인용했다.

*다음 미팅 제안* — 견적 만료 임박을 높은 위험으로 판단했다. **입력에 없는 미팅 날짜는
만들지 않고 `null`로 반환했다.** 참석자와 미팅 일시를 부족한 정보로 표시했다. 내부
이메일은 LLM 입력에서 빠졌다.

*시간 후보 추천* — 개별 60분 후보 5개, 통합 30분 후보 4개를 만들었다. 기존 일정
`09:00~10:00`과 겹치지 않게 첫 후보를 `10:00`에 배치했다. 모든 후보가 요청 기간과
`09:00~18:00` 안에 있었다. 내부 담당자 ID는 LLM 입력에서 빠졌다.
후보는 최대 10개이며 **항상 10개를 만들지는 않는다** — 유효한 후보가 적으면 그보다 적게
반환한다. 개수가 아니라 유효성이 기준이다.

*미팅 브리핑* — 계약 단계·금액·견적 만료일과 승인 미팅을 요약했다. 입력에 없는 계약
기간, 결제 조건, 납품 조건은 부족한 정보로 표시했다. 통합 테스트에서는 영업 건·일정·문서
ID가 근거에 포함됐으나, **개별 테스트에서는 문서 ID만 근거로 나온 실행이 있었다.**
브리핑 문장 자체는 입력에 근거했지만 근거 ID 구성이 실행마다 흔들릴 수 있다는 뜻이라,
8절에 후속 과제로 남긴다.

## 5. 발견한 결함과 조치

테스트와 코드 리뷰에서 찾은 결함이다. **모두 조치 완료했고 회귀 테스트로 고정했다.**

### 5.1 LLM 출력 품질

| # | 결함 | 조치 |
|---|---|---|
| 1 | 과거·주말 날짜를 제안 | 프롬프트에 `current_date` 전달 + 서버 재검증 |
| 2 | 이미 미팅이 잡힌 딜을 다시 후보로 올림 | 선별 단계에서 예정 활동 있는 딜 제외 |
| 3 | **같은 고객사의 다른 딜 내용이 섞임** | 입력을 트리거 딜로 한정 + 응답 딜 ID 대조 |
| 4 | 시작이 끝보다 늦은 구간을 그대로 통과 | 역전 검사 후 기본 범위로 폴백 |

**3번이 가장 위험했다.** 회사 단위로 입력을 만들면서 응답의 `sales_deal_id`를 확인하지
않아, 한 고객사에 딜이 둘 이상이면 다른 딜의 사유와 선호 시간이 트리거 딜의 제안으로
저장될 수 있었다. **예외도 로그도 남지 않아** 화면상으로는 완전히 정상으로 보인다.
회귀 테스트(같은 회사 open deal 2건)로 고정했다.

### 5.2 데이터 정합성

| # | 결함 | 조치 |
|---|---|---|
| 5 | 시간대 없는 문자열이 단계마다 다르게 해석(**9시간 차이**) | 정규화한 값을 이후 단계에 전달 |
| 6 | 동시 승인 시 **일정 중복 등록** | 등록 앞에서 `with_for_update` 선점, 두 번째는 `409` |
| 7 | 선점 조회에 권한 조건 없음 | `team_id` + 딜 소유자 조건 추가 |

### 5.3 비용·안정성

| # | 결함 | 조치 |
|---|---|---|
| 8 | 쿨다운이 뚫려 **LLM 비용 2배** | `pg_advisory_xact_lock`으로 확인·예약 원자화 |
| 9 | `--dry-run`이 LLM 설정을 요구 | 실제 실행 시에만 검사 |
| 10 | `--owner` 동명이인이 모두 선택됨 | id 지원 + 중복 시 후보 제시 후 중단 |
| 11 | `--limit 0`·음수가 1건을 처리 | argparse 단계에서 차단 |

**8번의 성격** — 중복 실행 자체는 저장 단계의 UNIQUE 제약이 걸러냈다. 문제는 그 시점이
**LLM을 이미 두 번 태운 뒤**라는 것이었다. 비용은 결과 정합성과 별개로 방어해야 한다.

### 5.4 화면

| # | 결함 | 조치 |
|---|---|---|
| 12 | 조회 실패 시 재시도 수단 없음 | 패널에 재시도 버튼 |
| 13 | **승인 실패를 화면이 삼킴** | 오류 문구 표시 + 목록 재조회 |

13번은 테스트 중이 아니라 리뷰 대응 중에 발견했다. 등록이 실패해도 사용자에게 아무
반응이 없어, 무엇이 잘못됐는지 알 방법이 없었다.

### 5.5 코드 리뷰 결과

자동 코드 리뷰(CodeRabbit) 2회에서 **12건**이 지적됐고 **12건 모두 조치**했다.

| 회차 | Major | Minor | 계 | 상태 |
|---|---:|---:|---:|---|
| 1차 | 3 | 5 | 8 | 조치 완료 |
| 2차 | 1 | 3 | 4 | 조치 완료 |

조치 과정에서 테스트가 **376건 → 389건**으로 늘었다(+13).

## 6. sLLM 파인튜닝 평가

**해당 없음.**

본 시스템의 계약관리·일정관리 에이전트는 파인튜닝한 sLLM을 사용하지 않고 외부 LLM
API(`gpt-5.6-luna`)를 그대로 호출한다. 판단 품질은 파인튜닝이 아니라 다음 세 가지로
확보한다.

| 방법 | 내용 |
|---|---|
| 입력 통제 | 결정적 규칙으로 위험 신호를 미리 계산해 전달 |
| 출력 구조화 | 스키마 기반 구조화 출력 |
| 서버 재검증 | 업무시간·충돌·날짜·딜 ID를 서버가 다시 확인 |

> 참고: 별도의 ML 모델(딜 승산 예측, Stacking 앙상블)이 프로젝트에 존재하나 본 에이전트와
> 무관한 독립 모델이다. [머신러닝_딥러닝_학습결과서.md](../머신러닝_딥러닝_학습결과서.md) 참고.

## 7. 성능 측정

기존 `agent_run` 기록과 변경 후 조회를 각각 측정했다.

| 구간 | 변경 전 | 변경 후 |
|---|---|---|
| 캘린더 진입 → 카드 표시 | 11.5초 (중앙값), p90 16.1초 | **0.03~0.07초** |
| 카드 → 날짜 확인 | +17초 (LLM 2회) | **없음** (이미 붙어 있음) |

변경 전 7일간 `contract_management_select_candidates` 호출이 98회였고, 그중 1건은
60초를 넘겨 프론트 폴링 타임아웃으로 실패했다. **이 경로 자체가 없어졌다.**

백그라운드 파이프라인 실행 시간은 실 데이터 기준 딜당 약 14초다.

## 8. 한계와 후속 과제

| 한계 | 내용 |
|---|---|
| **브리핑 RAG 입력 미검증** | 자료요약 에이전트(이슈 #80)가 아직 연동되지 않아 브리핑 입력의 `document_summaries`가 **항상 빈 배열**이다. 따라서 이 보고서의 브리핑 결과는 **문서 근거 없이 만든 브리핑**에 대한 검증이다. 연동 후 재검증이 필요하다 |
| 반복 테스트 입력 | 계층 3은 입력 1종에 대한 20회다. 계약 단계·위험 신호 조합별 반복은 미실시 |
| 브리핑 근거 ID | 근거 ID가 누락되지 않는지는 추가 품질 검사 대상 |
| 자동화 | 계층 2~4는 수동 실행이다. 비용 때문에 CI에 넣지 않았다 |
| 프론트 테스트 | 자동화 테스트 없이 수동 확인으로 검증 |
| 회귀 감시 | 시간 후보 품질 전수 검사는 1회성 스크립트다. 정기 점검으로 만들 필요 |

## 9. 실행 명령어

`backend` 폴더에서 실행한다. 실제 LLM 테스트는 API 설정과 외부 네트워크가 필요하며
**비용이 발생한다.** 네트워크가 막히면 `llm_request_failed:ConnectError`가 발생한다.

**계층 1 — 단위 테스트**

```powershell
uv run pytest -q -p no:cacheprovider `
  tests/test_contract_management.py tests/test_schedule_management.py `
  tests/test_contract_schedule_snapshots.py tests/test_contract_next_meeting_pipeline.py `
  tests/test_contract_suggestions.py tests/test_agent_runs.py tests/test_activities.py
```

**계층 2 — 실제 LLM 개별**

```powershell
uv run pytest -s -p no:cacheprovider tests/test_contract_schedule_pipeline.py::test_select_next_meeting_candidates_with_real_llm
uv run pytest -s -p no:cacheprovider tests/test_contract_schedule_pipeline.py::test_contract_next_meeting_with_real_llm
uv run pytest -s -p no:cacheprovider tests/test_contract_schedule_pipeline.py::test_schedule_management_with_real_llm
uv run pytest -s -p no:cacheprovider tests/test_contract_schedule_pipeline.py::test_contract_briefing_with_real_llm
uv run pytest -s -p no:cacheprovider tests/test_contract_schedule_pipeline.py::test_contract_schedule_briefing_pipeline_with_real_llm
```

**계층 3 — 20회 반복**

```powershell
1..20 | ForEach-Object {
    uv run pytest -q -p no:cacheprovider tests/test_contract_schedule_pipeline.py::test_contract_schedule_briefing_pipeline_with_real_llm
}
```

**계층 4 — 실 데이터 전수** (LLM 비용 발생, 대상 확인 후 실행)

```powershell
uv run python scripts/backfill_contract_next_meeting_suggestions.py --dry-run
uv run python scripts/backfill_contract_next_meeting_suggestions.py
```
