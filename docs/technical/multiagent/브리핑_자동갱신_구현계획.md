# AI 브리핑 자동 갱신 구현 계획

## 0. 이 문서의 배경

미팅 상세의 🤖 AI 브리핑은 지금 **화면이 만든다.** 상세를 열었을 때 브리핑이 없으면
프런트엔드가 `POST /agent-runs`로 생성을 요청하고, 완료될 때까지 2초 간격으로 최대 30번
조회한다([useAiBriefing.ts](../../../frontend/src/pages/Dashboard/useAiBriefing.ts)).

그래서 두 가지가 문제다.

- 브리핑이 없는 미팅을 열면 RAG 검색과 LLM 생성이 끝날 때까지 화면이 로딩 상태로 멈춘다.
- 한 번 만들어지면 다시 만들지 않는다. 그 뒤에 올라온 자료는 브리핑에 반영되지 않는다.
  현재 문서([자료요약_브리핑_연결_수동테스트.md](./자료요약_브리핑_연결_수동테스트.md))도
  "자료 변경마다 자동으로 다시 만드는 정책은 현재 기능으로 주장하지 않는다"고 적고 있다.

이 문서는 브리핑을 **서버가 미리 만들어 두고 화면은 읽기만 하는** 구조로 바꾸는 계획이다.
구현은 이미 작업트리에 있으나 **커밋하지 않았다.** 이 계획을 확인받은 뒤에 커밋한다.

이 작업은 새 판단 정책이나 프롬프트 변경이 아니다. 브리핑을 **언제 누가 만드는가**만 바꾼다.

## 1. 목표

1. 자료 처리가 완료되면 영향받는 미팅의 브리핑을 백그라운드에서 미리 갱신한다.
2. 프런트엔드의 임시 `브리핑 새로고침` 버튼과 수동 생성 요청을 제거한다.

## 2. 지켜야 할 UX 원칙

- 미팅 상세를 열었을 때 RAG 검색이나 LLM 생성을 시작하며 기다리게 하지 않는다.
- 저장된 최신 성공 브리핑을 즉시 보여준다.
- 갱신이 진행 중이어도 기존 브리핑이 있으면 로딩 화면으로 덮지 않는다.
- 새 브리핑이 완성되면 본문·제품 자료·관련 자료를 하나의 결과로 함께 교체한다.
- 갱신에 실패하면 기존 성공 브리핑을 유지한다.
- 프런트엔드는 브리핑을 생성하는 주체가 아니라 조회하는 역할만 맡는다.

## 3. 데이터 흐름

```
자료 처리 완료
  원문 추출 → 자료요약 → 문서 청크·임베딩 저장 → DB 커밋
                                                    ↓ 커밋 성공 후에만
                                          영향받는 미래 미팅 계산
                                                    ↓
                                    agent_run 한 행씩 큐에 등록 (queued)
                                                    ↓
                              기존 agent_worker 컨테이너가 선점·실행
                                     제품 자료 직접 조회
                                   + 관련 자료 RAG 검색
                                   + 그 근거로 브리핑 본문
                                   + source_refs 검증
                                                    ↓
                              완료 시 revision 재계산 → 달라졌으면 후속 예약
                                                    ↓
                        미팅 상세 GET → 저장된 최신 성공 브리핑을 그대로 반환
```

문서 처리 트랜잭션 안에서 LLM 브리핑 생성을 기다리지 않는다. 예약은 큐에 행을 넣을 뿐이다.

## 4. 영향받는 미팅 계산

문서가 연결된 범위를 기준으로 **앞으로 예정된** 미팅만 찾는다.

| 문서의 연결 | 대상 미팅 |
| --- | --- |
| `sales_deal_id` | 그 딜의 미팅 |
| `customer_company_id` | 그 고객사의 미팅. 딜을 거쳐 회사가 정해지는 미팅 포함 |
| `product_id` | 딜 대표 제품 또는 견적 품목에 그 제품이 포함된 미팅 |

- 지금 이후에 시작하고 완료되지 않은 미팅만 본다. 과거 미팅은 재생성하지 않는다.
- 자료가 딜에만 걸려 있으면 그 딜의 미팅만 본다. 같은 고객사의 다른 딜은 건드리지 않는다.
- 팀 범위와 기존 문서·활동 접근권한을 그대로 유지한다.
- 한 번의 트리거로 예약하는 미팅은 **최대 50건**이며 가까운 미팅부터 채운다. 고객사 전체에
  걸린 자료 하나가 수백 건의 LLM 실행을 한꺼번에 만드는 것을 막기 위한 상한이다.

## 5. source revision

### 왜 필요한가

같은 미팅에 자료가 연달아 처리되면 브리핑이 여러 번 만들어진다. 반대로 "이미 실행 중이면
새 요청을 버린다"로 막으면, 실행이 시작된 뒤에 올라온 자료가 영원히 누락된다.

둘 다 피하려면 "지금 도는 중인가"가 아니라 **"검색 대상이 달라졌는가"**로 판단해야 한다.

### 무엇으로 계산하는가

이름만 `검색용 버전`인 임의의 증가 숫자를 만들지 않는다. 실제 검색 대상 상태의 **sha256
지문**을 쓴다. 입력은 다음 셋이다.

1. 미팅이 정하는 검색 범위 — `customer_company_id`, `sales_deal_id`, `customer_contact_id`,
   `product_id`, `starts_at`
2. 딜의 대표 제품과 견적 품목 제품 id 집합
3. 그 범위에서 실제로 읽히게 될 문서·파일 —
   `(document_id, file_id, version_no, processed_at)` 정렬 목록

3번 목록은 RAG 검색과 **같은 조건**으로 뽑는다(삭제 제외, 처리 완료, 문서별 최신 파일,
등록자 공개 범위). 그래서

- 자료를 지우면 목록에서 빠져 지문이 바뀐다.
- 딜·고객사·제품 연결을 바꾸면 범위에 들고 나므로 지문이 바뀐다.
- 같은 문서를 다시 올리면 새 `file_id`/`version_no`가 들어와 지문이 바뀐다.
- 재처리로 `processed_at`만 바뀌어도 지문이 바뀐다.

### 관찰 시각을 따로 둔다

지문과 함께 **`source_observed_at`**(그 상태를 관찰한 시각)을 실행 행에 적는다. 둘은 역할이
다르다.

- 지문은 "달라졌는가"를 답한다. 시각만으로는 내용이 그대로인데도 매번 다시 만들게 된다.
- 관찰 시각은 "둘 중 어느 쪽이 더 나중 상태를 봤는가"를 답한다. 지문만으로는 완료된 두
  실행의 선후를 정할 수 없다.

## 6. 중복과 경합 처리

### 중복 방지

실행 요청의 멱등키를 `uuid5(네임스페이스, "미팅ID:revision")`으로 만든다. `agent_run`의
기존 `UNIQUE (requested_by_member_id, idempotency_key)`가 중복을 결정한다.

- 메모리 debounce가 아니라 DB 제약이므로 프로세스를 다시 띄워도, worker가 여럿이어도
  같은 상태의 브리핑은 한 번만 만들어진다.
- 키가 "실행 중 여부"가 아니라 "자료 상태"에 묶여 있어, 이미 도는 실행이 있어도 자료가
  바뀌면 새 요청이 들어간다.

### 오래된 결과의 덮어쓰기 방지

화면에 세울 브리핑을 **`finished_at` 순이 아니라 `source_observed_at` 순**으로 고른다.
후보는 `status_code = 'completed'`인 실행뿐이다.

- 옛 자료로 시작한 실행이 늦게 끝나도, 더 새 자료로 만든 브리핑을 밀어내지 못한다.
- 갱신이 실패해도 마지막 성공 브리핑이 그대로 남는다. 실패는 따로만 알린다.

### 후속 갱신

실행이 끝나면 지문을 다시 계산해 비교한다. 그 사이에 자료가 또 바뀌었으면 후속 실행을
예약한다. 이 비교가 없으면 "실행 중에 들어온 자료"가 다음 트리거까지 반영되지 않는다.

## 7. 트리거

| 트리거 | 대상 |
| --- | --- |
| 미팅 등록 | 그 미팅 |
| 미팅의 담당자·고객사·딜·제품·시작 시각 변경 | 그 미팅 |
| 자료 처리 완료, 자료요약 승인 | 그 자료가 걸린 범위의 미래 미팅 |
| 자료 삭제, 자료의 딜·고객사·제품 연결 변경 | 변경 전 범위와 변경 후 범위 **양쪽** |
| 딜의 대표 제품·견적 품목·고객사 변경 | 그 딜의 미래 미팅 |

미팅 등록은 [activities.py](../../../backend/app/api/activities.py)의 `create_activity`에
**이미 있는 트리거를 그대로 재사용한다.** 중복 구현하지 않는다.

자료 연결을 바꾸면 그 자료를 잃는 미팅과 새로 얻는 미팅이 동시에 생기므로 변경 전 범위를
먼저 붙잡아 두고 양쪽을 갱신한다.

## 8. 화면 동작

`useAiBriefing.ts`에서 다음을 제거한다.

- 브리핑이 없을 때 `POST /agent-runs`로 자동 생성하는 로직
- `refreshRequest`, `refresh()` 반환값, 수동 새로고침용 polling
- `브리핑 새로고침` 버튼

조회 동작은 이렇게 한다.

- 상세 진입 시 GET 한 번으로 저장된 최신 성공 브리핑을 즉시 표시한다.
- 갱신 중(`refreshing`)이면 제목 옆에 `최신 자료 반영 중`만 작게 붙이고 본문을 가리지 않는다.
  그 상태일 때만 5초 간격 GET으로 결과를 교체하며, 이 polling은 실행을 만들지 않는다.
- 결과가 한 번도 없을 때만 `AI 브리핑 준비 중`을 보여준다.
- 갱신 실패는 한 줄 안내로만 알리고 이전 브리핑을 그대로 둔다.

## 9. 스키마 영향

**새 테이블도 새 컬럼도 만들지 않는다.** 기존 `agent_run`의 `idempotency_key`,
`request_hash`, `source_refs`와 기존 worker로 전부 해결한다.

- 멱등성 → 기존 `UNIQUE (requested_by_member_id, idempotency_key)`
- revision·관찰 시각 저장 → 기존 `source_refs` (JSONB)
- 실행 → 기존 `agent_worker` 컨테이너. 배포 스크립트가 이미 띄우고 있다.

따라서 **이 작업 때문에 필요한 마이그레이션은 없다.** 다만 같은 브랜치의 pgvector 검색은
`20260912_0031_document_vectors.sql` 적용이 선행되어야 한다(별도 작업).

## 10. 지켜야 할 경계

- 자료 처리가 **커밋된 뒤에만** 예약한다. 그 전에 예약하면 아직 저장 중인 청크가 검색돼
  미완성 근거를 인용한다.
- 문서 처리 실패는 브리핑 갱신을 발생시키지 않는다.
- 외부 임베딩·LLM 장애가 문서 원문과 요약 저장을 롤백시키지 않는다. 예약 실패도 마찬가지다.
- 삭제된 문서, 이전 파일 버전, 타 팀 자료, 현재 사용자가 볼 수 없는 자료가 관련 자료나
  브리핑 근거로 노출되지 않는다. 저장된 근거를 화면에 세울 때 권한·삭제를 다시 검사한다.
- 새 실행 실패 때문에 마지막 성공 브리핑을 잃지 않는다.
- worker가 여러 개여도 동일 revision의 중복 생성과 오래된 실행의 덮어쓰기를 막는다.

- 자료 처리 성공 후 영향받는 미래 미팅만 갱신 예약

- 새 revision 후속 실행 예약
- 새 실행 실패 시 이전 성공 브리핑 유지
- 문서 삭제·연결 변경 시 재생성
- 타 팀·권한 없는 문서 제외
- 미팅 상세 진입 시 `POST /agent-runs` 호출 없음
- 새로고침 버튼 미렌더
- 갱신 중에도 기존 브리핑과 제품 자료·관련 자료가 즉시 보임
- 최초 브리핑만 준비 중 상태 표시

### 실행하지 못한 검사

실제 DB를 쓰는 통합 테스트는 돌리지 못했다. pgvector 전용 로컬 DB(`127.0.0.1:55439`)가 떠
있지 않고 이 환경에 Docker가 없다. 그래서 scope·revision 쿼리는 가짜 세션과 컴파일된 SQL
문자열 검증으로 확인했다. `_company_scope`·`_product_scope`의 서브쿼리가 실제 데이터에서
의도대로 걸리는지는 전용 DB를 띄운 뒤 한 번 더 확인해야 한다.

## 13. 확인받을 것

### 13.1 커밋을 어떻게 나눌지

이 작업은 같은 작업트리에 있던 **기존 pgvector RAG WIP 위에 얹혀 있다.** 그 WIP(하이브리드
검색, 자료 열람 권한, 제품 자료·근거 표시)와 이 작업의 변경이 같은 hunk·같은 줄에 섞여
있어, 기능별로 나눈 각 커밋이 개별적으로 동작하게 만들 수 없다.

확인된 사례 둘.

- `search_chunks`에서 pgvector 재작성(WIP)과 `document_scopes(..., product_ids)`(WIP)가 한
  hunk다. 갈라도 `document_scopes`가 인자를 아직 못 받아 import되지 않는다.
- `activity_documents.py`에서 `member=None` 추가(WIP)와 함수 이름 변경(이 작업)이 한 줄이다.

또 `contract_schedule_snapshots.py`(WIP)가 이 작업에서 바뀐 이름을 호출하고, 이 작업의
엔드포인트 제거는 WIP의 `BriefingMaterials`가 있어야 성립해서 순환 의존이 생긴다.

원인은 작업 방식이다. WIP 위에 바로 얹어 편집하면서 WIP의 중간 상태(새로고침 버튼,
`refreshRequest`, `list_for_activity`)를 덮어썼다. 지금 4분할을 하려면 존재한 적 없는 중간
상태를 손으로 재구성해야 한다.

**선택지**

1. 주제별 3커밋 — 리뷰하기 좋게 갈리고 시리즈 전체는 테스트를 통과하지만, 중간 커밋 하나만
   체크아웃하면 깨진다(bisect 불가).
2. 1커밋 — 모든 커밋이 항상 동작하지만 34개 파일이 한 덩어리라 리뷰가 어렵다.
3. WIP 중간 상태를 재구성해 4분할 — 깔끔하지만 검증된 적 없는 이력을 만드는 것이고 손작업
   오류 위험이 있다.

### 13.2 남은 판단거리

- `MAX_ACTIVITIES_PER_TRIGGER = 50` 상한이 적절한지. 그 이상 미팅이 걸린 팀에서는 먼 미팅이
  다음 트리거까지 갱신되지 않는다.
- 미팅의 `product_id`만 바꿔도 revision이 바뀌어 실행이 하나 더 돈다. 제품 자료 범위는 딜
  기준이라 결과는 같다. 과다 갱신을 감수하고 안전하게 둘지, 지문에서 뺄지.
