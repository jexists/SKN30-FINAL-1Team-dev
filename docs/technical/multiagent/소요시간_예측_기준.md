# 미팅 소요 시간 예측 기준과 근거

기준일: 2026-09-01 · 대상 필드 `next_meeting_suggestion.duration_minutes`

> 처음 읽는다면 [소요시간_예측_기준_v2.md](./소요시간_예측_기준_v2.md)(쉬운 설명)를 먼저
> 보세요. 같은 내용을 그림과 예시로 풀어 썼습니다. 이 문서는 함수 이름·임계값까지 적은
> 기준 문서입니다.

계약관리 에이전트가 "이 미팅에 몇 분이 필요한가"를 정하는 기준과, 그렇게 정한 근거를
남긴다. 값이 어디서 나와 어디까지 강제되는지, 위험 신호 태그와 고객 접촉 간격이 그 값에
어떤 경로로 들어가는지, 그리고 아직 반영하지 않은 것이 무엇인지를 함께 적는다.

전체 그림은 [계약_일정_에이전트_아키텍처.md](./계약_일정_에이전트_아키텍처.md),
입출력 계약은 [계약에이전트_설계.md](./계약에이전트_설계.md) ·
[일정관리에이전트_설계.md](./일정관리에이전트_설계.md)를 따른다.

## 1. 무엇을 정하는 값인가

`duration_minutes` 는 **확보해야 하는 회의 길이(분)** 다. 언제 만날지가 아니라 얼마나
오래 만날지다. 선호 기간과 자주 섞이므로 구분해 둔다.

```
"9월 1일 ~ 9월 10일 사이에서   60분짜리를   찾아라"
  └──────────────────────┘    └────────┘
        선호 기간                소요 시간
   (일정관리가 뒤질 범위)      (이 문서의 대상)
```

| | |
|---|---|
| 정하는 곳 | `contract_management.propose_next_meeting` (1차 실행, LLM) |
| 쓰는 곳 | `schedule_management` — 이 길이가 통째로 비어 있는 시간만 후보로 낸다 |
| 허용 범위 | 5 ~ 480분 (`NextMeetingSuggestion.duration_minutes`, `AgentRunCreate.duration_minutes`) |
| 값이 없을 때 | 60분 (`build_schedule_snapshot` 의 `duration_minutes or 60`) |

전달 경로는 에이전트 간 직접 호출이 아니라 `agent_run` 기록이다. 1차 실행의
`output_snapshot.next_meeting_suggestion.duration_minutes` 를 일정관리 실행이
`parent_run_id` 로 이어받는다.

## 2. 왜 규칙이 아니라 LLM이 정하나

이 시스템의 기본 원칙은 **"뺄셈은 서버가, 판단은 AI가"** 다. 계약 만료까지 며칠인지는
서버가 계산하고, 그게 급한지는 AI가 해석한다.

소요 시간은 뺄셈 쪽이 아니다. 딜 데이터 어디에도 "이 미팅은 몇 분짜리"라는 사실이 없다.
필요한 시간을 가르는 것은 날짜가 아니라 **안건의 무게**다.

```
"견적 수락 여부만 확인"      →  30분
"요구사항을 처음부터 정리"    →  90분
```

두 안건은 위험 신호도 딜 단계도 같을 수 있다. 그래서 코드로 계산하지 않고, 안건(`reason`)을
쓴 주체가 그 자리에서 같이 정하게 한다.

대신 **검증 가능한 것만 서버가 강제한다** — 후보의 길이가 이 값과 정확히 같은지는 달력만
보면 알 수 있으므로 6장처럼 결정적으로 맞춘다.

## 3. 판단 기준 (프롬프트 `propose_next_meeting.v4`)

기준은 `backend/app/agents/contract_management.py` 두 곳에 나눠 적혀 있다.

| 위치 | 무엇을 적나 |
|---|---|
| `PROPOSE_NEXT_MEETING_SYSTEM_PROMPT` | **왜** 고민해야 하는지 — 습관적으로 같은 값을 쓰지 마라, 판단이 안 서면 `reason` 을 다시 읽어라 |
| `NextMeetingSuggestion.duration_minutes` 의 `description` | **얼마인지** — 아래 구간표 |

두 곳에 나눈 이유가 있다. 필드 `description` 은 구조화 출력 스키마에 실려 **값을 채우는
자리 바로 옆에서** 읽히고, 시스템 프롬프트는 출력 전체의 태도를 정한다. 구간표만 있으면
표에 없는 안건에서 기본값으로 돌아가고, 태도만 있으면 숫자가 흩어진다.

### 구간표

| 안건 성격 | 시간 | 예 |
|---|---:|---|
| 확인·서명처럼 단순한 건 | 30분 | 견적 수락 여부 확인, 계약서 서명 |
| 일반 상담·협의 | 60분 | 통상적인 후속 미팅 |
| 요구사항 정리, 쟁점이 여럿 | 90분 이상 | 도입 범위 재정의, 미해결 C/S 동반 |
| 오래 끊겼다가 다시 만나는 자리 | 60~90분 | 상황을 다시 듣는 시간이 필요하다 (5장) |

> `v3` → `v4` 는 소요 시간 기준을 바꾼 것이 아니다. 회의록에 다음 약속이 명시돼 있으면
> 그 날짜를 **선호 기간**에 포함하라는 문단이 추가됐다. 같은 프롬프트를 공유하므로 버전만
> 함께 올라간다.

마지막 줄만 안건이 아니라 **관계의 상태**를 기준으로 삼는다. 나머지 셋과 성격이 다르지만
같은 표에 둔 이유는, 이 경우 안건 자체는 가벼워 보여도(예: "근황 확인") 실제로는 배경을
다시 맞추는 시간이 붙기 때문이다.

## 4. 태그 중요도 — 위험 신호가 시간에 반영되는 경로

여기서 "태그"는 서버가 결정적 규칙으로 붙이는 **위험 신호 코드**(`risk_signals[].code`)와
그 심각도(`severity`)다. 계산 위치는 `contract_schedule_snapshots._deal_risk_signals()` 와
`_support_risk_signals()` 이고, 일곱 코드는 `RiskCode` 로 고정돼 있다.

### 태그가 소요 시간에 미는 방향

| 태그 | 조건 | 소요 시간에 주는 신호 |
|---|---|---|
| `contract_expiring` | 계약 만료 30일 이내 (7일 이내 high) | 대개 **짧다** — 갱신 의사 확인이 안건이면 30분 |
| `quote_expiring` | 견적 유효기간 14일 이내 (3일 이내 high) | 대개 **짧다** — 수락 여부 확인. 재협상이면 길어진다 |
| `delivery_delay_risk` | 예상 납품일 지남 (high) | **중간~길다** — 원인·일정 재조정 설명이 붙는다 |
| `unresolved_support` | 미해결 C/S (긴급이면 high) | **길다** — 쟁점이 여러 개인 자리가 된다 |
| `missing_contract_information` | 계약 단계인데 계약번호·금액 없음 | **짧다** — 확인 항목을 채우는 자리 |
| `follow_up_overdue` | 마지막 접촉 30일 경과 | **길다** — 5장의 간격 기준으로 60~90분 |
| `contract_revisit_due` | 계약 체결 7일 경과 (14일 high) | **중간** — 체결 후 점검 |

### 이 표를 코드에 넣지 않은 이유

위 방향은 **매핑 규칙이 아니라 경향**이다. 코드에는 태그→분 단위 변환표가 없고, 앞으로도
넣지 않을 생각이다.

같은 `quote_expiring` 이라도 "서명만 남았다"와 "가격을 다시 협상해야 한다"는 필요한 시간이
두 배 넘게 차이 난다. 태그는 **"딜에 무슨 일이 있었나"** 를 말하고, 소요 시간은 **"만나서
무엇을 이야기할 것인가"** 를 말한다. 둘은 1:1이 아니다. 태그로 분을 결정하면 안건이 무엇이든
같은 값이 나오는데, 그건 정확히 v2 이전에 관측된 실패 모습이다(7장).

그래서 서버는 **태그와 그 근거(`detail`)만 입력으로 넘기고**, 시간은 LLM이 `reason` 과 함께
정한다. 태그가 여러 개 붙었을 때 어떻게 합칠지도 규칙으로 정하지 않는다 — "두 개면 +15분"
같은 합산은 근거가 없고, 태그 둘이 실제로는 같은 안건 하나인 경우가 흔하다(견적 만료와
계약 정보 누락이 한자리에서 정리된다).

### severity 는 시간보다 급함에 먼저 쓰인다

`severity` 는 0차 선별(어느 딜을 지금 보여줄지)과 선호 기간의 폭(급하면 이번 주, 여유
있으면 2주)에 먼저 작용한다. **급한 미팅이 곧 긴 미팅은 아니다** — 오히려 급한 건은
확인 한 가지인 경우가 많아 짧아진다. 두 축을 섞지 않는다.

## 5. 고객 간격 반영 로직

"간격"은 두 가지를 뜻하고, 계산 주체는 둘 다 서버다.

### ① 마지막 접촉 간격 (`days_since_contact`)

```python
# contract_schedule_snapshots._deal_risk_signals()
reference_at = last_activity_at or datetime.combine(deal.opened_on, ...)
days_since_contact = (now - reference_at).days
if days_since_contact >= 30:        # _FOLLOW_UP_OVERDUE_AFTER_DAYS
    → follow_up_overdue (medium), detail = "days_since_contact=45"
```

활동이 하나도 없는 딜은 **딜을 연 날(`opened_on`)** 을 기준으로 삼는다. 신규 딜이 만들어지자
마자 "오래 연락 안 함"으로 잡히는 것을 막기 위해서다.

### ② 계약 체결 후 경과 (`days_since_signed`)

```python
if days_since_signed >= 14:   → contract_revisit_due (high)
elif days_since_signed >= 7:  → contract_revisit_due (medium)
detail = "contract_signed_on=2026-08-20"
```

### 간격이 분(minute)으로 이어지는 경로

```
[서버]  일수를 계산       days_since_contact = 45
   ↓    태그 + detail 로 스냅샷에 담는다
[LLM]   태그를 읽고       "45일 끊겼다 → 상황을 다시 들어야 한다"
   ↓    안건과 같이 본다   reason: "도입 범위 재확인"
        → duration_minutes = 90
```

프롬프트에서 이 경로를 받는 문장은 하나다 — *"오래 끊겼다가 다시 만나는 자리는 상황을
다시 듣는 시간이 필요하므로 60~90분으로 잡는다."*

### 일수를 계단식으로 분에 매핑하지 않은 이유

`30일 → 60분 / 60일 → 75분 / 90일 → 90분` 같은 표를 만들 수는 있지만, 그 계단의 근거가
없다. 간격이 필요한 시간에 영향을 준다는 것은 관측되지만(오래 끊길수록 배경 설명이 붙는다),
**어느 지점에서 15분이 더 필요해지는지는 데이터가 없다.** 근거 없는 계단을 코드에 박으면
나중에 실측이 생겼을 때 무엇을 고쳐야 하는지도 흐려진다.

대신 **실제 일수를 `detail` 로 그대로 넘긴다.** 45일과 200일은 같은 태그지만 다른 숫자로
도착하고, LLM이 안건과 함께 본다.

### 이 로직의 구멍

| 구멍 | 내용 |
|---|---|
| 30일 미만은 신호가 없다 | 25일 만에 만나는 자리도 배경 재확인이 필요할 수 있으나, 태그가 안 붙어 간격 정보가 전혀 전달되지 않는다 |
| `contract_revisit_due` 는 일수를 안 준다 | `detail` 이 날짜(`contract_signed_on`)라 LLM이 다시 빼야 한다. `follow_up_overdue` 만 일수를 직접 준다 — 형식을 맞추는 게 다음 개선 후보다 |
| 접촉의 질을 구분하지 않는다 | 30초 통화와 두 시간 방문이 똑같이 "마지막 접촉"으로 간격을 초기화한다 |
| 회사 단위가 아니라 딜 단위다 | 같은 회사의 다른 딜로 지난주에 만났어도, 이 딜의 활동이 없으면 "오래 끊김"으로 읽힌다 |

## 6. 서버가 강제하는 것

값 자체는 LLM이 정하지만, **그 값이 지켜지는지는 결정적으로 검사한다.**
(`backend/app/agents/schedule_management.py`)

| 함수 | 하는 일 |
|---|---|
| `_required_duration()` | 스냅샷의 `duration_minutes` 를 읽는다. `bool` 이거나 5~480 밖이면 `None` — 길이를 강제하지 않는다 |
| `_with_duration()` | 후보의 종료 시각을 `시작 + duration` 으로 다시 쓴다. 짧으면 늘리고 길면 줄인다 |

`_with_duration` 이 **다른 검사보다 먼저** 도는 것이 핵심이다. LLM이 60분 요청에 30분
후보를 내면 뒤 30분은 업무시간 검사도 충돌 검사도 보지 않는다. 그대로 승인하면 실제 회의가
남의 일정 위로 밀고 들어가는데 예외도 로그도 남지 않는다. **검사받는 구간과 승인 시 실제로
등록될 구간이 같아야** 검사가 뜻을 갖는다.

`bool` 방어가 따로 있는 이유는 파이썬에서 `bool` 이 `int` 의 하위형이기 때문이다. `True` 가
1분으로 읽히면 모든 후보가 1분으로 줄어든다.

값이 없거나 범위 밖일 때 **기본값으로 늘리지 않는** 것도 의도한 선택이다. 선호 시간대를
사용자가 직접 넣는 실행에는 소요 시간이 비어 올 수 있는데, 기준이 없는데 임의로 늘리면
없던 충돌을 만든다.

## 7. 근거 — 프롬프트 기준을 넣기 전과 후

기준을 넣기 전(`propose_next_meeting.v1`)에는 `duration_minutes` 에 대한 지시가 프롬프트에
전혀 없었다. 결과는 **한 값에 몰림**이었다.

| | v1 (기준 없음) | v2 (기준 명시) |
|---|---|---|
| 완료된 1차 제안 | 105건 중 **101건이 30분** | — |
| 같은 입력 30건 재실행 | 30분 30건 (**1가지 값**) | 30분 7 · 60분 19 · 90분 4 (**3가지 값**) |
| 선호 기간 폭 | 약 30분 | 평균 10일 |

값이 흩어진 것이 아니라 **안건에 따라 갈렸다** — 단순 확인 건은 v2에서도 30분에 그대로
남았다. 커밋 `9adc669` 에 비교 조건이 함께 남아 있다.

한 가지 덧붙이면, 일정 후보가 0개가 되는 실패(실행 89건 중 2건)의 원인은 소요 시간이 아니라
**선호 기간의 폭**이었다. 계약관리가 30분짜리 한 칸을 기간으로 준 경우다. 두 값은 같은
프롬프트에서 같이 정해지지만 실패 모습이 다르다 — 소요 시간은 "몰림", 선호 기간은 "0개".

재현 방법은 [계약_일정_에이전트_테스트보고서.md](./계약_일정_에이전트_테스트보고서.md) 9절에 있다.

## 8. 아직 반영하지 않는 것

| 항목 | 지금 | 왜 아직 아닌가 |
|---|---|---|
| **활동 액션 태그** (`activity_action_tag`) | `Activity` 모델에는 있으나 어느 스냅샷에도 담지 않는다 | 첫 전화·데모·제품교육 11종은 미팅 종류를 그대로 말해 주는 값이다. "지난 데모는 평균 90분이었다" 같은 근거가 될 수 있으나, 실제 소요 시간 실측이 없어(아래) 평균을 낼 대상이 없다 |
| **실제 소요 시간 피드백** | 없다 | 승인된 `activity` 의 `ends_at - starts_at` 은 제안 값이 그대로 저장된 것이라 실측이 아니다. **지금은 예측 정확도를 잴 수 없다** — 재는 방법을 먼저 만들어야 한다 |
| **이동·준비 시간** | 없다 | 후보는 회의 시간만 잡는다. 병원 방문의 왕복 이동이 일정에 잡히지 않는다 |
| **사용자별 기본 소요 시간** | 없다 | [일정관리에이전트_설계.md](./일정관리에이전트_설계.md) 의 메모리 항목(회의별 기본 소요 시간, 일정 사이 여유)은 설계에만 있고 미구현이다 |
| **참석자 수** | 없다 | 스냅샷에 참석자가 없다. 의사결정권자 동석 여부는 `reason` 문장으로만 간접 전달된다 |
| **30일 미만 접촉 간격** | 전달 안 됨 | 5장 참고 |

## 9. 이 기준을 바꿀 때

1. **프롬프트 문구를 바꾸면 `PROPOSE_NEXT_MEETING_PROMPT_VERSION` 을 올린다.** 안 올리면
   실행 이력에서 어느 기준으로 나온 값인지 구분할 수 없다.
2. **시스템 프롬프트와 필드 `description` 을 같이 본다.** 3장처럼 역할이 나뉘어 있어 한쪽만
   고치면 다른 쪽이 반대로 유도한다.
3. **분포로 검증한다.** 같은 입력 30건 이상을 두 프롬프트로 돌려 값의 분포를 비교한다.
   한 값에 몰리면(v1처럼) 기준이 안 읽힌 것이고, 단순 확인 건까지 길어지면 과교정이다.
4. **서버 강제 범위(5~480)를 넘기려면 `AgentRunCreate.duration_minutes` 와
   `_MIN/_MAX_DURATION_MINUTES` 를 함께 맞춘다.** 한쪽만 바꾸면 검증이 조용히 꺼진다.
