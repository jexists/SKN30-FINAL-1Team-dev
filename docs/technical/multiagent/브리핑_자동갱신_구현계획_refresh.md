## 1. 왜 "계획"인데 구현이 있나

동작하는 구현이 `jiyu-park/briefing-document-rag` **작업트리에 커밋되지 않은 채** 있다.
파일 35개이고 그 상태에서 백엔드 1,467개·프런트엔드 115개 테스트가 통과했다.

그런데 그 35개에는 **다른 작업(pgvector 하이브리드 검색)의 미커밋 변경이 섞여 있다.** 두 작업이
같은 파일을 공유해서, 그대로 커밋하면 서로 다른 목적의 변경이 한 PR 에 들어간다.

그래서 이 문서는 **"그 35개 중 무엇을 가져오고, 무엇을 새로 쓰고, 무엇을 두고 갈지"**를
정한 것이다. 이 PR 은 그중 **3.1·3.2 를 가져온 결과**를 계획서와 함께 담는다.

### 1.1 이 PR 에 들어 있지 않은 것

3.3 "새로 작성한다" 다섯 항목 중 **`useAiBriefing` 재작성은 이번 PR 에 포함하고, 나머지 네
항목은 후속 PR 로 미룬다.** 2026-09-13 로컬 화면 테스트에서 이 훅을 빼면 자동 갱신 완료를
화면이 따라가지 못한다는 것을 확인했으므로, 백엔드 예약과 같은 배포 단위에서 끝낸다.

| 미달 항목 | 지금 동작 | 계획한 동작 |
| --- | --- | --- |
| 지문 재료 (2.1) | **자료 범위만 본다** | 영업 건 값·접촉 이력·미해결 C/S·미팅 제목·장소·종료 시각까지 본다 |
| 위험 신호 | 넣지 않는다 | `code`·`severity` 를 넣고 `detail` 은 뺀다 |
| 트리거 | 자료 3 · 미팅 1 · 영업 건 1 | 단계 이동과 C/S 2 곳을 더한다 |
| 예약 범위 | 영업 건은 그 딜의 미팅만 | 영업 건·C/S 는 그 고객사의 미래 미팅 전체 |
| 주기 점검 (2.3) | 없다 | 하루 한 번 훑어 날짜로 켜지는 경고를 잡는다 |

**그래서 이 PR 만으로는 "자료를 올리면 브리핑이 갱신되고 열린 상세 화면도 완료를 따라간다"까지
된다.** 금액·단계·C/S 를 고쳐도 브리핑이 옛 내용으로 남는 범위는 7장 커밋 5·6 이 해결한다.

### 1.2 로컬 화면 테스트에서 발견한 누락과 해결

백엔드 게시 응답은 **게시할 성공본**과 **가장 최근 실행**을 분리한다. 이전 성공본 뒤에서 새
실행이 돌면 `status="completed"`, `content=<이전 성공본>`, `refreshing=true` 가 함께 내려온다.

현재 `useAiBriefing` 은 두 군데에서 이 계약과 맞지 않는다.

1. `ai_briefing == null` 이면 여전히 `POST /agent-runs` 로 실행을 만든다. 서버가 미리 만들고
   화면은 읽기만 한다는 책임 경계를 다시 깨뜨린다.
2. `status == queued/running` 일 때만 폴링한다. 이전 성공본이 있으면 `status` 는
   `completed` 이므로 `refreshing=true` 여도 재조회하지 않는다. 새 실행이 끝나도 드로어를
   다시 열기 전까지 이전 본문과 `최신 자료 반영 중` 표시가 남는다.

**이번 PR 에서 다음 상태 기계로 고친다.**

| 시점 | 동작 | 화면 |
| --- | --- | --- |
| 상세 진입 | `GET /activities/{id}` 1회 | 저장된 게시본을 즉시 표시 |
| 브리핑 없음 | 추가 요청 없음 | `AI 브리핑 준비 중` |
| `refreshing === true` | 5초 뒤 GET 반복 | 마지막 성공 본문과 상태 태그 유지 |
| 갱신 성공 | 마지막 GET 응답으로 교체, 폴링 종료 | 새 본문 표시, 상태 태그 제거 |
| 갱신 실패 | 마지막 GET 응답으로 교체, 폴링 종료 | 이전 본문 유지, 실패 안내 표시 |
| 드로어 닫기·일정 변경 | 타이머와 늦은 응답 취소 | 닫힌 화면에 상태를 반영하지 않음 |

폴링 조건은 `status` 가 아니라 오직 `ai_briefing.refreshing === true` 다. 폴링 중에는
`loading=true` 로 되돌리지 않아 본문을 스켈레톤으로 가리지 않는다. 최초 GET 실패만 기존 오류
영역에 표시한다. 갱신 중 일시적인 조회 실패는 마지막 성공 본문을 보존하고 5초 뒤 GET을 다시
시도한다. `AbortController`와 취소 가능한 타이머를 함께 써서 드로어가 닫힌 뒤 요청이나 타이머가
남지 않게 한다. 상세 진입부터 폴링 종료까지 화면에서 `POST /agent-runs` 는 한 번도 보내지 않는다.

## 2. 무엇을 만드나

**지금 문제** — 미팅 상세의 AI 브리핑을 화면이 만든다. 상세를 열었을 때 브리핑이 없으면 그
자리에서 자료를 검색하고 LLM 을 호출한다. 그래서 처음 여는 미팅은 기다려야 하고, 한 번
만들어진 브리핑은 그 뒤 자료를 올려도 그대로 굳는다.

**바꿀 것** — 서버가 미리 만들어 두고 화면은 읽기만 한다.

```
업무 변경(자료 처리·승인·수정·삭제 · 미팅 수정 · 영업 건 수정 · 단계 이동 · C/S 상태)
        ↓ 커밋된 뒤에만
영향받는 미래 미팅을 찾아 작업 큐에 한 줄 넣는다
        ↓
기존 worker 가 집어가 브리핑을 만든다
        ↓
미팅 상세 GET 은 저장된 최신 성공 브리핑을 그대로 읽는다
```

브리핑 생성 자체(프롬프트·입력 범위·출처 검증)는 **건드리지 않는다.** 언제 만드는가만 바뀐다.

여기서 정할 것이 셋이다. **언제 다시 만드나**(2.1), **여러 개 중 무엇을 보여주나**(2.2),
**아무도 안 고쳤는데 내용이 달라지는 경우**(2.3).

### 2.1 중복 — 재료가 같으면 다시 만들지 않는다

갱신 계기가 여러 곳이라 한 미팅에 몰린다. 자료 올리고 → 금액 고치고 → 시간 바꾸면 같은
브리핑을 세 번 만든다. 매번 RAG 검색과 LLM 호출이 붙는다.

그래서 **브리핑에 들어갈 재료를 지문 하나로 압축해 "주문번호"로 쓴다.**

- 재료가 그대로면 → 같은 주문번호 → DB 가 "이미 접수된 주문"이라며 튕겨낸다.
- 재료가 바뀌면 → 새 주문번호 → 새로 만든다.

"바뀌었는지 판단"과 "중복 막기"를 값 하나로 해결한다. 그래서 상태 테이블이 없어도 된다.

주문번호는 `uuid5(브리핑 네임스페이스, "미팅ID:지문")` 이고 기존
`UNIQUE (requested_by_member_id, idempotency_key)` 가 판정한다. 요청자는 트리거를 누른 사람이
아니라 **미팅 담당자**다 — 누가 고치든 같은 미팅이면 한 행으로 모인다.

#### 지문에 넣는 재료

데이터를 모으는 곳이 둘이다. 브리핑 **본문**을 만드는 쪽과, **지문**을 만드는 쪽이다.

| | 무엇을 만드나 |
| --- | --- |
| 본문 | LLM 에 보낼 브리핑 입력 (`build_briefing_snapshot`) |
| 지문 | "바뀌었나" 를 판단할 해시 (`source_revision`) |

**이 둘이 보는 필드 목록이 다르면 어긋난다.** 양쪽 다 문제다.

- 본문에만 있고 지문에 없으면 → 값이 바뀌어도 지문은 그대로 → 갱신되지 않고 **브리핑이 옛
  내용으로 남는다.** 작업트리 구현의 금액·C/S·미팅 제목이 이 경우였다.
- 지문에만 있고 본문에 없으면 → 값이 바뀔 때마다 새로 만드는데 **결과물은 똑같다.** LLM 값만
  쓴다.

그래서 **지문은 쿼리를 따로 짜지 않고, 브리핑 본문이 쓰는 수집 함수를 그대로 호출한다**
(`_open_deals`, `_deal_summary`, `_last_activity_by_deal`, `_unresolved_support_signals`).
목록이 하나로 묶여 있어야, 나중에 본문에 필드를 더해도 지문이 따라온다. 각자 쿼리를 짜면 한쪽만
고치고 다른 쪽을 잊는 일이 반복된다.

자료만 예외다. 본문은 검색 **결과**를 쓰지만 지문은 검색 **대상 목록**을 쓴다 — 지문을 계산할
때마다 임베딩과 벡터 검색을 부를 수는 없기 때문이다(6장).

그래서 지문에 넣을 재료는 다음과 같다. **브리핑 본문에 들어가는 값은 모두 들어 있다.**

| 재료 | 값 |
| --- | --- |
| 미팅 | 고객사·영업 건·담당자·상품, 제목·장소·시작·종료 시각 |
| 영업 건 | 그 고객사의 진행 중 영업 건 전체 — 제목·단계·금액·계약 종료일·견적 유효기한·납품 예정일 |
| 접촉 이력 | 영업 건별 최근 활동 시각, 영업 건을 연 날짜 |
| C/S | 그 고객사의 미해결 요청 목록 |
| 위험 신호 | 켜진 신호의 종류와 심각도만 (숫자 제외) |
| 상품 | 미팅·영업 건·견적 품목에서 나온 상품 ID |
| 자료 | 검색 대상 자료 목록(문서·파일·버전·처리 시각). 담당자가 볼 수 있는 것만 |

위험 신호("계약 만료 임박", "30일째 연락 없음")는 **켜졌다는 사실만 넣고 숫자는 뺀다.**

| | 지문에 | 왜 |
| --- | --- | --- |
| `code`·`severity` (`follow_up_overdue`, `medium`) | **넣는다** | 켜졌다↔꺼졌다는 딜 하나당 평생 몇 번뿐이다 |
| `detail` (`days_since_contact=30`) | **뺀다** | 날마다 `31`, `32` 로 바뀌어 **매일 전체를 다시 만들게 된다** |

이 구분이 없으면 둘 중 하나가 된다. 숫자까지 넣으면 아무도 안 고쳐도 매일 전체 재생성이고,
신호를 통째로 빼면 임계값을 넘어도 지문이 그대로라 **경고가 영영 브리핑에 안 들어간다.**

#### 트리거

재료를 바꾸는 경로마다 있어야 한다. 굵은 것이 새로 붙일 것이다.

| 경로 | 지금 | 바꿀 것 |
| --- | --- | --- |
| 자료 처리·승인·수정·삭제 | 있다 | — |
| `PATCH /activities/{id}` | 고객사·영업 건·담당자·상품·시작 시각 | **제목·장소·종료 시각 추가** |
| `PATCH /sales-deals/{id}` | 대표 제품·고객사·견적 품목 | **금액·단계·계약 종료일·견적 유효기한·납품 예정일·제목 추가** |
| `POST /sales-deals/{id}/move` | 없다 | **신규** |
| `POST`·`PATCH /support-requests` | 없다 | **신규** |

영업 건과 C/S 는 **그 고객사의 미래 미팅 전체**를 예약한다. 브리핑이 그 회사의 진행 중 영업
건을 다 보기 때문이다. 자료는 지금처럼 자료가 걸린 범위만 본다.

생성 횟수는 는다. 금액·단계는 자료보다 자주 바뀌고 회사 범위로 퍼진다. 운영에서 문제가 되면
예약 상한이나 지연 예약을 후속으로 검토한다.

#### 예시

미팅 `a1f3` 의 지문이 `3c9f…` 인 상태에서 시작한다. worker 는 2 초마다 큐를 보고 브리핑 한
건은 수십 초에 끝난다.

| 시각 | 무슨 일이 | 지문 | 결과 |
| --- | --- | --- | --- |
| `09:12:00` | 자료 `DOC-42` 재처리 완료 | `3c9f…` → `8d12…` | 새 실행 예약 |
| `09:12:03` | 같은 저장 훅이 한 번 더 호출됨 | 그대로 | 같은 주문번호 → **건너뜀** |
| `09:12:20` | 영업 건 금액 5,000 → 6,000 만 | `8d12…` → `c04e…` | 앞 실행이 도는 중이어도 **새 실행 예약** |
| `09:12:38` | 앞 실행 완료 | — | `8d12…` 를 본 결과. 뒤에 더 새것이 있어 화면에는 안 뜬다 |
| `09:13:05` | 뒤 실행 완료 | — | 가장 나중 상태를 본 결과라 **화면에 뜬다** |

겹치는 경우는 드물다. 보통은 예약 → 완료 → 다음 변경 순서로 지나간다. 생성 중에 값을 또
고쳤을 때만 위처럼 되고, 그때 옛 결과가 최신을 덮지 않게 하는 것이 2.2 다.

### 2.2 게시 — 가장 나중 상태를 본 성공작을 띄운다

지금은 `finished_at` 내림차순이고 `queued`·`running`·`failed` 도 후보에 있다. 두 가지로 깨진다.

**(1) 늦게 끝난 옛 실행이 최신을 덮는다.**

| 실행 | 자료를 읽은 시각 | 끝난 시각 |
| --- | --- | --- |
| A | 10:00 | 10:40 |
| B | 10:20 | 10:25 |

`finished_at` 순이면 A 가 이기는데, A 가 본 자료는 20 분 낡았다. **"언제 끝났나"가 아니라
"언제 자료를 봤나"로 고르면** B 가 이긴다.

**(2) 실패가 성공을 가린다.** 갱신하다 실패하면 멀쩡히 보이던 브리핑이 화면에서 사라진다.
**성공한 실행만 후보로 두면** 직전 성공본이 그대로 남는다.

그래서 실행이 입력을 만들 때 관찰 시각(`source_observed_at`)을 남기고, 게시는 **완료된 실행 중
그 값이 가장 큰 것**을 고른다. 가장 최근 실행은 따로 돌려줘서, 게시본을 띄운 채 `최신 자료
반영 중`·갱신 실패를 함께 보여준다.

지문과 시각을 나눈 이유는 역할이 다르기 때문이다. **지문은 "달라졌는가", 시각은 "어느 쪽이 더
나중 상태를 봤는가"**를 답한다. 둘 다 기존 `source_refs` JSONB 에 들어가므로 **새 컬럼이 없다.**

### 2.3 주기 점검 — 아무도 안 고쳤는데 경고가 켜지는 날

계약 종료일이 `10-15` 로 **그대로**여도, 9월 15일에는 조용하다가 9월 16일이 되면 "30일 남음" 에
걸려 경고가 새로 켜진다. 이날 **아무도 아무것도 안 고쳤으므로 트리거가 걸릴 일이 없다.** 그냥
두면 그 경고는 영영 브리핑에 들어가지 않는다.

**그래서 하루 한 번 미래 미팅을 훑어 지문을 다시 계산한다.** 달라진 미팅만 예약한다.

| | |
| --- | --- |
| 어디에 | `agent_worker.run_forever` 가 이미 `LEASE_SECONDS` 마다 도는 정리 블록을 갖고 있다. 같은 자리에 하루 간격을 하나 더 둔다 |
| 무엇을 | 미래·미완료 미팅의 지문을 다시 계산하고, 직전 실행과 다른 것만 `schedule_activities` 에 넘긴다 |
| 비용 | **대부분의 날은 예약 0 건이다.** 훑는 동안 DB 쿼리만 돌고 LLM·임베딩은 부르지 않는다 |

2.1 의 "숫자는 빼고 신호 종류만 넣는다" 와 **짝이다.** 숫자까지 넣었다면 이 점검이 매일 전체를
다시 만들고, 신호를 통째로 뺐다면 이 점검이 매일 돌아도 지문이 그대로라 아무것도 하지 않는다.
둘이 같이 있어야 **경고가 실제로 켜진 미팅만** 다시 만든다.

### 실제 Postgres 검증 — 여기서 버그를 하나 잡았다

흉내 낸 세션으로는 못 보는 것을 보려고 로컬 DB(`docs/technical/local-test-database.md`)에서
`tests/test_briefing_refresh_local_database.py` 를 새로 만들어 돌렸다. **통과했고, 통과하기까지
실제 버그를 하나 고쳤다.**

> **작업트리 구현은 자동 갱신을 한 번도 큐에 넣지 못한다.**
> `schedule_activities` 가 `prompt_version=""` 로 행을 넣는데, baseline 의
> `agent_run_prompt_version_check` 가 빈 문자열을 거부한다. 그 실패를 바로 아래
> `except IntegrityError` 가 **"다른 worker 가 먼저 넣었다"로 오해하고 삼킨다.** 그래서 오류도
> 로그도 없이 예약이 0 건이 된다.
>
> 기존 `agent_runs.create` 와 같이 `_prompt_version(BRIEFING_AGENT_CODE)` 를 쓰도록 고쳤다.
> 실제 값은 `prepare_claimed` 가 입력을 만들며 다시 쓴다.

이 버그는 **흉내 낸 세션으로는 영원히 안 보인다.** DB 제약이 없는 가짜 세션에서는 빈 문자열도
그대로 들어가기 때문이다. 계획서가 P2 에 "실제 DB 고유 제약 검증"을 둔 이유가 이것이다.

새 테스트가 실제 DB 에서 확인하는 것은 넷이다.

| 확인 | 내용 |
| --- | --- |
| 중복 방지의 주체 | 같은 재료로 두 번 예약하면 행이 하나다. 같은 멱등키를 직접 넣으면 **UNIQUE 가 거부**한다 |
| 지문 기록 | 예약 시점에 `source_revision` 이 남아, 아직 실행되지 않은 작업도 같은 조회로 찾힌다 |
| 재료 변경 | 미팅 시작 시각을 바꾸면 멱등키가 달라져 새 실행이 생긴다 |
| 게시 규칙 | 늦게 끝났어도 **옛 자료를 본 실행은 뽑히지 않는다.** 그 뒤 갱신이 실패해도 마지막 성공본이 남는다 |

로컬 DB 는 9 월 7 일에 만든 뒤 마이그레이션이 밀려 있었다. 저장소 SQL 중 `0026`·`0028`·`0029`
·`0030`·`0031` 을 적용해 맞췄다(나머지는 이미 적용돼 있었다).

배포 전에 남은 확인.

- 자료요약·미팅분석·보고서작성 에이전트 **실통합** 회귀(외부 LLM 포함)를 돌린다.
- 아래 두 가지는 **이번 변경과 무관한 기존 실패**다. 고치지 않았고, 따로 다뤄야 한다.

| 실패 | 원인 |
| --- | --- |
| `test_models::test_models_match_configured_database` | DB 의 `agent_run` 에 `delegation_state`·`apply_status`·`base_report_version`·`base_generation_input_version` 이 있는데(`sql/20260901_0018`) ORM `AgentRun` 이 그 넷을 선언하지 않는다. 모델을 건드리지 않았는데도 난다 |
| `test_contract_schedule_pipeline` 의 실 LLM 3 건 | 테스트가 스냅샷에 `document_summaries` 를 넣는데 `_BriefingLLMInput` 이 `extra="forbid"` 로 거부한다. 두 파일 모두 이번 변경 대상이 아니다 |
- **날짜만 지났을 때 지문이 그대로인지** 확인한다. 여기가 깨지면 매일 전체 미팅이 다시 생성된다.
- 반대로 **임계값을 넘는 날에는 지문이 바뀌는지** 확인한다(2.3). 여기가 깨지면 경고가 영영 안 들어간다.
- 영업 건 한 건을 고쳤을 때 같은 고객사의 다른 미래 미팅도 예약되는지 확인한다.

## 7. 커밋 분할 — 판단 3번

기능별로 넷으로 나눈다. 각 커밋이 단독으로 동작하고 테스트가 통과하는 순서다.

| # | 커밋 | 내용 | 단독 동작 |
| --- | --- | --- | --- |
| 1 | `feat(documents): 자료 범위를 상품과 열람 권한까지 넓힌다` | `document_access` 신규, `document_scopes` 선택 인자 | 가능. 기존 호출부 결과 불변 |
| 2 | `feat(agents): 자료·업무 변경 시 브리핑을 미리 갱신한다` | `briefing_refresh.py`, 지문 기록, 후속 훅, 트리거(자료 3 · 미팅 1 · 영업 건 1), 단위 테스트와 로컬 DB 통합 테스트 | 가능 |
| 3 | `fix(activities): 성공한 최신 브리핑만 보여준다` | 게시 규칙 | 가능 |
| 4 | `refactor(dashboard): 브리핑을 조회 전용으로 바꾼다` | 생성 POST 제거, `refreshing` 기준 5초 GET 폴링, 이전 본문 보존, 닫을 때 취소, 갱신 상태 표시와 화면 회귀 테스트 | 가능 |
| 5 | `feat(agents): 브리핑 내용이 바뀌는 값을 모두 갱신 대상에 넣는다` | 지문 재료 확장, 단계 이동·C/S 트리거, 회사 범위 예약 (1.1) | 2 가 있어야 의미가 있다 |
| 6 | `feat(agents): 날짜로 켜지는 위험 신호를 주기 점검으로 잡는다` | 주기 점검(2.3), 테스트 | 5 가 있어야 의미가 있다 |

**이 PR 은 1~4 만 담는다.** 5·6 은 후속 PR 이다(1.1).

3 을 2 와 나눈 이유는 **게시 규칙만으로도 지금 버그 하나를 고치기 때문이다.** 지금은 갱신이
실패하면 이전 성공 브리핑이 화면에서 사라진다. 자동 갱신 없이도 의미가 있고 따로 되돌릴 수 있다.

## 8. 스키마와 배포

- **새 테이블·컬럼 없음.** 기존 `agent_run` 의 `idempotency_key`·`request_hash`·`source_refs`
  를 그대로 쓴다.
- **마이그레이션 없음.**
- 예약은 DB 큐에 쌓이므로 **worker 컨테이너가 떠 있어야** 갱신이 실제로 돈다. 배포 스크립트가
  이미 띄운다.
- 롤백은 커밋 되돌리기로 끝난다. 남는 `agent_run` 행은 기존 실행 기록과 같은 형태다.
