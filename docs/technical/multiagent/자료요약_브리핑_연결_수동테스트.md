# 자료요약 ↔ 브리핑 연결 수동 테스트 절차

| 항목 | 내용 |
|---|---|
| 제품 | SalesLuv |
| 대상 | 미팅 상세의 `📎 관련 자료` · `📦 제품 자료` · `🤖 AI 브리핑` |
| 브랜치 | `jiyu-park/briefing-rag-context` |
| 작성 기준일 | 2026-09-02 |

자동 테스트로는 잡히지 않는 **연결 관계와 화면 표시**를 사람이 확인하는 절차다.
단위 테스트는 `backend/tests/test_activity_documents.py`,
`backend/tests/test_sales_context.py` 가 맡는다.

---

## 0. 먼저 알아야 할 것

이 기능은 **세 갈래가 서로 독립**이다. 하나가 실패해도 나머지는 떠야 정상이다.

| 화면 | 무엇을 보여주나 | 무엇에 의존하나 |
|---|---|---|
| `📎 관련 자료` | 이 **딜·고객사**에 연결된 자료 | DB 조회만 |
| `📦 제품 자료` | 이 미팅이 다루는 **상품**에 연결된 자료 | DB 조회만 |
| `🤖 AI 브리핑` | LLM 요약문 | LLM 호출 |

자료 목록은 미팅을 열 때마다 새로 조회하므로 **자료를 나중에 올려도 즉시 반영**된다.
반면 브리핑은 미팅당 한 번만 만들어지고 **재생성되지 않는다** — 3절에서 다시 다룬다.

### 자료실 업로드의 제약

업로드 화면에서 고를 수 있는 연결 대상은 **딜 또는 상품 하나뿐**이다(배타적).
**고객사를 직접 고르는 칸은 없다.** 그래서 고객사 범위는 딜을 거쳐 판정한다.

```text
이 고객사의 딜들을 먼저 찾고 → 그 딜들에 붙은 자료를 가져온다
```

## 1. 사전 준비

### 1.1 서버 실행

```bash
cd backend && uv run uvicorn app.main:app --port 8000
```

> `--reload` 는 빼는 편이 낫다. 백엔드 파일이 하나라도 바뀌면 서버가 재시작되고,
> 그동안 화면에는 "서버에 연결할 수 없습니다" 가 뜬다. Windows 에서는 재시작이
> `PermissionError [WinError 5]` 로 실패해 서버가 아예 죽기도 한다.

### 1.2 서버가 살아 있는지 확인

```bash
curl -s http://127.0.0.1:8000/api/health/db
```

`{"status":"ok","database":"connected"}` 가 나와야 한다.

### 1.3 테스트 자료 준비

`LP100_자료요약_브리핑_최소테스트.txt` 같은 합성 자료를 쓴다.
실제 고객 정보가 든 파일은 쓰지 않는다.

## 2. 테스트 A — `📎 관련 자료` (딜 연결)

### 절차

1. **자료실 → 업로드**
2. 연결 대상을 **딜**로 고른다 — 예: `SL-DL-2026-0046`
   - ⚠️ **상품이 아니라 딜이다.** 상품에 걸면 아래쪽 `📦 제품 자료` 로 간다
3. 요약 처리가 끝날 때까지 기다린다 (자료실 목록에서 상태 확인)
4. 캘린더에서 **그 딜에 연결된 미팅**을 연다
5. `📎 관련 자료` 확인

### 통과 기준

- 파일 이름이 목록에 뜬다
- `자료요약 보기` 를 누르면 자료요약 Agent 가 만든 요약이 펼쳐진다
- 같은 파일을 여러 번 올렸다면 **최신 버전 한 줄만** 뜬다

### 범위 확인 (선택)

같은 **고객사의 다른 딜** 미팅을 열어도 이 자료가 떠야 한다.
딜을 거쳐 고객사 범위를 판정하는 부분이 동작하는지 보는 항목이다.

---

## 3. 테스트 B — `📦 제품 자료` (상품 연결)

### 절차

1. 자료실 업로드에서 연결 대상을 **상품**으로 고른다 — 예: `LP100`
2. 요약 처리 완료 후, **그 상품을 파는 딜**의 미팅을 연다
3. `📦 제품 자료` 확인

### 통과 기준

- `📎 관련 자료` 가 아니라 `📦 제품 자료` 쪽에 뜬다
- 같은 상품을 파는 **다른 고객사 미팅에도** 뜬다 (이것이 의도된 동작이다)

### 알아둘 것

제품 자료는 **고객사를 가리지 않는다.** 카탈로그·스펙처럼 공용으로 쓰는 자료를
위한 자리다. LP100 딜이 10개면 10개 미팅 전부에 같은 파일이 뜬다.

상품은 세 곳에서 모은다 — **미팅 자체 · 딜 · 딜의 견적 품목**.

---

## 4. 테스트 C — `🤖 AI 브리핑` 과 인용 표시

### 사전 조건

미팅에 **담당자 연락처가 연결돼 있어야** 한다. 없으면
`담당자 연락처가 연결되지 않아 AI 브리핑을 만들 수 없습니다` 가 뜨고 시작조차 안 한다.

> 연락처는 필수값이 아니다. AI 추천 일정은 **딜에 적힌 담당자를 복사**하므로,
> 딜에 담당자가 없으면 일정에도 안 들어간다. 그때는 일정을 수정해 직접 넣는다.

### 절차

1. 자료를 딜에 연결하고 요약까지 끝낸다
2. **그 뒤에** 새 미팅을 만든다 — 순서가 중요하다
3. 미팅 상세를 연다 (여는 순간 브리핑이 생성된다)
4. 브리핑 본문과 `📎 관련 자료` 를 함께 본다

### 통과 기준

- 브리핑 본문에 자료 내용이 반영된다
- 브리핑이 인용한 자료 줄에 `브리핑에 인용됨` 뱃지가 붙는다

### ⚠️ 브리핑은 한 번만 만들어진다

미팅당 브리핑은 **최초 1회**만 생성되고 이후 재생성되지 않는다. 그래서

- 자료를 **나중에** 올리면 → 자료 목록에는 뜨지만 **브리핑 본문은 옛날 그대로**다
- 생성이 한 번 실패하면 → **그 미팅은 영구히 실패 상태**로 남는다

브리핑까지 확인하려면 **자료를 먼저 붙이고 미팅을 새로 만든다.**
기존 미팅으로 다시 보려면 해당 `agent_run` 행을 지워야 한다.

## 5. 실패했을 때 — 어디서 끊겼는지 찾기

### 5.1 화면 증상으로 1차 판별

| 증상 | 원인 | 조치 |
|---|---|---|
| 서버에 연결할 수 없습니다 | 백엔드 꺼짐 / 재시작 중 | 1.2 로 확인 후 재실행 |
| 담당자 연락처가 연결되지 않아… | 일정에 연락처 없음 | 일정 수정해 연락처 연결 |
| 이 고객사·딜에 연결된 자료가 없습니다 | 자료가 딜·고객사에 안 붙음 | 자료실에서 연결 확인 |
| 브리핑 생성에 실패했습니다 | LLM 오류 | 5.3 으로 원인 확인 |

### 5.2 자료가 안 뜰 때 — 검색만 따로 확인

브리핑을 거치지 않고 조회 단계만 끊어서 볼 수 있다.

```bash
curl -H "Authorization: Bearer $TOKEN" \
  "$API/documents/briefing-context?q=LP100&sales_deal_id=<딜ID>&customer_company_id=<고객사ID>"
```

`sources` 가 비면 조회 단계에서 끝난 것이다. 이때 확인할 것:

- 자료에 딜 또는 상품이 연결돼 있는가
- 파일 처리 상태가 `completed` 인가 (OCR·요약 미완이면 제외된다)

### 5.3 브리핑이 실패할 때 — 실행 기록 확인

```sql
select agent_code, status_code, error_message, evidence,
       extract(epoch from (finished_at - started_at)) as secs
from agent_run
order by coalesce(finished_at, started_at) desc nulls last
limit 10;
```

| 값 | 해석 |
|---|---|
| `llm_request_failed:ReadTimeout` | LLM 응답 지연. `LLM_TIMEOUT_SECONDS` 확인 (`secs` 가 설정값과 같으면 확실) |
| `evidence.chunk_count = 0` | 자료를 못 찾음 → 5.2 로 |
| `evidence.chunk_count > 0` 인데 근거 없음 | LLM 이 인용을 생략함 |
| `deal_model_unavailable` | ML 모델 파일 문제. 이 기능과 무관 |
| 오늘자 행이 아예 없음 | 실행 생성 자체가 실패. 서버 로그 확인 |

### 5.4 서버 로그에 `IntegrityError` 가 보일 때

DB 제약 위반이다. 링크(`sqlalche.me/e/20/gkpj`)만 보지 말고 **그 위쪽의
`sqlalchemy.exc.IntegrityError` 줄**에서 제약 이름을 확인한다.

`report` · `agent_run` 의 nullable JSONB 칸은 SQL NULL 만 허용하는 CHECK 가 걸려 있다.
모델에서 `JSONB(none_as_null=True)` 가 빠지면 JSON `null` 이 저장되어 위반이 난다.

> ⚠️ 이 CHECK 제약들은 마이그레이션 파일에 없고 운영 DB 에만 존재한다.
> 로컬에서 스키마를 새로 만들면 재현되지 않으니 주의한다.

## 6. 정리 — 순서만 지키면 된다

```text
자료 업로드 → 딜(또는 상품) 연결 → 요약 완료 대기 → 미팅 생성 → 미팅 열기
                                                    ↑
                                        브리핑까지 볼 거면 이 순서를 지킨다
```

자료 목록만 확인할 거라면 **기존 미팅을 열어도 된다.** 열 때마다 다시 조회한다.
