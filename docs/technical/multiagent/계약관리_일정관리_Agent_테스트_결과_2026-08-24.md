# 계약관리·일정관리 Agent 테스트 결과

- 실행일: 2026-08-24
- 실행 위치: `backend/`
- 대상: `contract_management`, `schedule_management`, Agent 실행 서비스 및 백엔드 회귀 테스트
- 관련 설계: [계약관리·일정관리 Agent 평가 데이터셋 설계](계약관리_일정관리_Agent_평가_데이터셋_설계.md)

## 1. 결론

계약관리·일정관리 Agent의 현재 단위 테스트와 Agent 실행 서비스 테스트는 **16개 모두 통과**했다. 백엔드 전체 회귀 테스트는 DB 접근을 허용한 최종 실행에서 **167개 중 166개 통과, 1개 실패**했다.

남은 실패는 Agent 로직의 실패가 아니라 실제 PostgreSQL DB와 SQLAlchemy 모델 메타데이터의 테이블 목록 불일치다. DB에는 `customer_contact_assignee` 테이블이 존재하지만 현재 모델 메타데이터에는 존재하지 않는다.

따라서 현 상태는 다음과 같이 판정한다.

| 영역 | 결과 | 판정 |
|---|---:|---|
| 계약관리 Agent 단위 테스트 | 통과 | 현재 구조화 출력 경계 정상 |
| 일정관리 Agent 단위 테스트 | 통과 | 현재 구조화 출력과 요청 검증 정상 |
| Agent 실행 서비스 테스트 | 통과 | 현재 실행 생성·분기·저장 동작 정상 |
| 백엔드 전체 회귀 테스트 | 1건 실패 | DB와 ORM 모델 스키마 정합성 확인 필요 |
| 평가 데이터셋 기반 품질 평가 | 미실행 | 평가 케이스와 자동 평가기 구현 필요 |

## 2. 실행 환경 보정

최초 실행에서는 테스트 코드와 무관한 두 가지 환경 문제가 발견됐다.

### 2.1 `uv` 캐시 접근 실패

기본 사용자 캐시 경로에서 다음 오류가 발생했다.

```text
Failed to initialize cache at C:\Users\playdata2\AppData\Local\uv\cache
액세스가 거부되었습니다. (os error 5)
```

테스트 프로세스에만 저장소 내부 캐시를 지정했다.

```powershell
$env:UV_CACHE_DIR='D:\FieldMed_dev\SKN30-FINAL-1Team-dev\.tmp-uv-cache'
```

### 2.2 `DEBUG=release` 설정 충돌

시스템 환경변수 `DEBUG=release`가 Pydantic의 boolean `debug` 설정으로 읽혀 테스트 수집이 중단됐다.

```text
ValidationError: debug
Input should be a valid boolean, input_value='release'
```

테스트 프로세스에만 다음 값을 지정했다.

```powershell
$env:DEBUG='false'
```

애플리케이션 코드나 `.env` 파일은 변경하지 않았다.

## 3. Agent 대상 테스트

### 3.1 실행 명령

```powershell
$env:UV_CACHE_DIR='D:\FieldMed_dev\SKN30-FINAL-1Team-dev\.tmp-uv-cache'
$env:DEBUG='false'
uv run pytest tests/test_contract_management.py tests/test_schedule_management.py tests/test_agent_runs.py -q
```

### 3.2 결과

```text
16 passed, 1 warning in 2.51s
```

### 3.3 확인된 내용

#### 계약관리 Agent

- `ContractManagementOutput` 구조화 schema로 LLM 경계를 호출한다.
- 입력 snapshot이 LLM 입력에 전달된다.
- 허용되지 않은 위험 심각도 `critical`을 거부한다.
- 현재 허용 심각도는 `low`, `medium`, `high`다.

#### 일정관리 Agent

- `ScheduleManagementOutput` 구조화 schema로 LLM 경계를 호출한다.
- 일정 후보의 제목, 유형, 시작·종료 시각, 우선순위를 구조화해 반환한다.
- UTC offset이 없는 일정 요청을 거부한다.
- 잘못된 선호 기간을 요청 검증 단계에서 차단한다.

#### Agent 실행 서비스

- 계약관리와 일정관리 실행을 올바른 Agent 구현으로 분기한다.
- 실행 입력 snapshot과 출력 snapshot을 저장하는 현재 흐름이 동작한다.
- 계약관리 요청에는 `customer_company_id`가 필요하다.
- 일정관리 요청에는 딜, 담당자, 선호 기간, 소요 시간과 활동 유형이 필요하다.
- 지원하지 않는 입력 필드를 거부한다.
- 계약관리 실행과 일정관리 부모 실행 관계에 대한 현재 테스트가 통과한다.

## 4. 백엔드 전체 회귀 테스트

### 4.1 샌드박스 실행

동일 환경으로 전체 테스트를 실행했을 때 결과는 다음과 같았다.

```text
165 passed, 2 failed, 1 warning in 5.43s
```

실패한 두 테스트는 다음과 같다.

- `tests/test_health.py::test_health_db_connects`
- `tests/test_models.py::test_models_match_configured_database`

두 실패 모두 샌드박스의 외부 DB 연결 `PermissionError` 때문에 발생했다. 코드 결함과 환경 차단을 구분하기 위해 DB 접근 권한으로 재실행했다.

### 4.2 DB 접근 허용 후 최종 실행

```powershell
$env:UV_CACHE_DIR='D:\FieldMed_dev\SKN30-FINAL-1Team-dev\.tmp-uv-cache'
$env:DEBUG='false'
uv run pytest -q
```

최종 결과:

```text
166 passed, 1 failed, 3 warnings in 4.57s
```

DB 상태 검사 `test_health_db_connects`는 재실행에서 통과했다. 따라서 설정된 PostgreSQL 연결 자체는 정상이다.

## 5. 최종 실패 분석

실패 테스트:

```text
tests/test_models.py::test_models_match_configured_database
```

실패 원인:

```text
DB에만 존재하는 추가 테이블: customer_contact_assignee
```

테스트는 실제 DB `public` schema의 테이블 집합과 `Base.metadata`에 등록된 SQLAlchemy 모델 테이블 집합이 완전히 같은지 비교한다. 실제 DB에만 `customer_contact_assignee`가 있어 assertion이 실패했다.

가능한 원인은 다음 중 하나다.

1. 해당 테이블 모델이 현재 코드에서 누락됐다.
2. 모델이 존재하지만 모델 import 집합에 등록되지 않았다.
3. 과거 migration으로 생성된 테이블이 현재 도메인에서 폐기됐지만 DB에 남아 있다.
4. 현재 작업 브랜치의 모델·migration과 연결된 DB schema 버전이 다르다.

이 테스트 실행에서는 원인을 확정하거나 DB·모델을 수정하지 않았다. DB 테이블 삭제는 파괴적 작업이며, 모델 추가도 사용자 요청 범위를 넘어가므로 별도 확인이 필요하다.

## 7. 평가 데이터셋 설계 대비 검증 범위

현재 통과한 테스트는 구현의 기본 schema와 실행 경계를 확인한다. 평가 설계 문서에서 정의한 사용자 시나리오의 의미 품질 전체를 검증하는 것은 아니다.

| 평가 항목 | 현재 검증 여부 | 설명 |
|---|---|---|
| 구조화 출력 schema | 일부 검증 | 기본 생성과 enum 거부 확인 |
| 입력 요청 검증 | 검증 | 필수값, 시간 offset, 지원하지 않는 입력 확인 |
| 계약 위험 정확도 | 미검증 | 만료·납기·미해결 C/S별 정답 케이스 없음 |
| C/S 독립 데이터 활용 | 미검증 | 계약관리 snapshot의 실제 C/S 케이스 테스트 부족 |
| 일정 충돌 정확도 | 미검증 | 담당자·동행자·종일·경계 시간별 oracle 테스트 부족 |
| C/S 후속 일정 반영 | 미검증 | 일정관리 snapshot에 `support_followups`가 아직 없음 |
| 환각·근거 충실성 | 미검증 | 고정 데이터셋과 의미 평가기 없음 |
| 권한·팀 격리 | 일부 검증 | 실행 서비스의 일부 경로만 검증 |
| Agent의 업무 데이터 불변 | 일부 검증 | 현재 실행 흐름은 제안 반환 구조이나 시나리오별 검증 부족 |
| stale 승인 재검증 | 일부 검증 | 전체 사용자 시나리오 기반 평가 미구현 |

따라서 **현재 Agent 코드 테스트 통과**와 **평가 데이터셋 품질 기준 충족**은 별개다. 후자를 판정하려면 설계 문서의 JSONL 케이스와 자동 평가기를 추가해야 한다.

## 8. 권장 후속 작업

우선순위 순으로 다음 작업을 권장한다.

1. `customer_contact_assignee`가 유효 테이블인지 확인하고 모델·migration·DB 중 정합성 기준을 결정한다.
2. 계약 위험 코드와 심각도 규칙을 enum과 결정론적 기준으로 고정한다.
3. 일정관리 Tool/API snapshot에 검증된 `support_followups`를 추가한다.
4. 계약관리 C/S 시나리오와 일정 충돌 시나리오를 우선 20건씩 JSONL로 작성한다.
5. Pydantic schema, 근거 ID와 시간 충돌 자동 평가기를 구현한다.
6. 이후 권장 규모인 Agent별 60건, 총 120건으로 평가 데이터를 확장한다.

## 9. 최종 판정

- **Agent 관련 현재 자동 테스트:** 통과
- **백엔드 회귀 상태:** 조건부 통과 — DB/ORM 테이블 정합성 1건 실패
- **실제 DB 연결:** 정상
- **평가 데이터셋 기반 품질 목표 달성 여부:** 아직 판정 불가
- **업무 데이터 또는 DB 변경:** 수행하지 않음
