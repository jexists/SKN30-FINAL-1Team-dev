# 계약·일정·브리핑 에이전트 테스트

## 1. 테스트 목적

다음 네 단계와 전체 연결을 확인한다.

1. 계약 에이전트가 담당자의 여러 딜 중 다음 미팅 제안이 필요한 딜을 선별한다.
2. 계약 에이전트가 선별된 딜의 다음 미팅을 제안한다.
3. 일정관리 에이전트가 겹치지 않는 시간을 추천한다.
4. 사용자가 첫 후보를 승인하면 계약 브리핑을 만든다.

## 2. 실행 결과

- 실행일: 2026-08-25
- 관련 단위 테스트: `68 passed`
- 실제 LLM 개별·통합 테스트: `5 passed in 40.64s`
- 실제 LLM 전체 흐름 반복 테스트: `20/20 passed`
- 반복 테스트의 실제 외부 LLM 호출: 60회
- 실제 DB 쓰기: 없음

전체 흐름 반복 테스트는 1~4단계 중 "계약 1차 제안 → 일정 추천 → 계약 브리핑" 세 단계만 돈다.
포트폴리오 선별(1단계)은 개별 테스트로만 확인했고 아직 반복 테스트에는 포함하지 않았다.

| 테스트 | 결과 | 확인 내용 |
|---|---:|---|
| 포트폴리오 선별 | 통과 | 위험 신호가 겹치거나 심각도가 높은 딜을 우선 선별, 약한 신호의 딜은 제외 |
| 계약 1차 제안 | 통과 | 위험, 부족한 정보, 다음 미팅 제안 |
| 일정 추천 | 통과 | 기간, 업무시간, 소요 시간, 일정 충돌 |
| 계약 브리핑 | 통과 | 승인 미팅, 계약 요약, 근거와 부족한 정보 |
| 전체 흐름 | 통과 | 첫 후보 승인과 `activity_id` 전달 |

### 전체 흐름 20회 반복 결과

같은 입력으로 실제 LLM 전체 흐름을 20회 실행했다. 각 회차는 계약 제안, 일정 추천, 브리핑을 한 번씩 호출했다.

| 항목 | 결과 |
|---|---:|
| 성공 | 20회 |
| 실패 | 0회 |
| 성공률 | 100% |
| LLM 호출 | 60회 |
| 총 테스트 시간 | 374.99초 |
| 평균 | 18.75초 |
| 가장 빠른 실행 | 14.44초 |
| 가장 느린 실행 | 24.34초 |

20회 동안 다음 오류는 없었다.

- 외부 LLM 연결 오류
- 출력 형식 오류
- 일정 후보 없음
- 빈 계약 브리핑
- 첫 후보와 승인 결과 불일치
- 승인된 `activity_id` 전달 실패

이 결과는 테스트에 사용한 한 가지 입력에 대한 결과다. 다른 계약 단계, 위험 신호, 일정 충돌 조건은 별도 입력으로 검사해야 한다.

단위 테스트에서 Starlette `TestClient` 관련 경고가 1건 나왔다. 이번 기능과 관계없는 라이브러리 변경 예정 경고다.

## 3. 실제 LLM 결과 요약

### 포트폴리오 선별

- 위험 신호가 겹치는 딜(계약 만료 + 미해결 C/S)과 심각도가 높은 딜(견적 만료 임박)을 선별했다.
- 신호가 약한 딜(medium 단일 신호, 후속 조치 지연)은 후보에서 뺐다.
- 입력에 없는 딜 ID를 만들지 않았다.
- 선별 이유(`reason`)가 근거 신호를 정확히 인용했다.

### 계약 1차 제안

- 견적 만료 임박을 높은 위험으로 판단했다.
- 입력에 없는 미팅 날짜는 만들지 않고 `null`로 반환했다.
- 참석자와 미팅 일시를 부족한 정보로 표시했다.
- 내부 이메일은 LLM 입력에서 빠졌다.

### 일정 추천

- 개별 테스트는 60분 후보 5개를 만들었다.
- 전체 테스트는 30분 후보 4개를 만들었다.
- 기존 일정 `09:00~10:00`과 겹치지 않게 첫 후보를 `10:00`에 배치했다.
- 모든 후보가 요청 기간과 `09:00~18:00` 안에 있었다.
- 내부 담당자 ID는 LLM 입력에서 빠졌다.

후보는 최대 10개이며 항상 10개를 만들지는 않는다.

### 사용자 승인

전체 테스트는 첫 번째 후보를 사용자가 승인한 것으로 처리했다.

- 선택 번호: 1
- 선택 시간: `2026-09-01 10:00~10:30`
- 등록 결과: `activity-created-from-candidate-1`

선택한 후보의 제목과 시간이 브리핑 입력에 그대로 전달됐다.

### 계약 브리핑

- 계약 단계, 금액, 견적 만료일과 승인 미팅을 요약했다.
- 입력에 없는 계약 기간, 결제 조건, 납품 조건은 부족한 정보로 표시했다.
- 전체 테스트에서는 영업 건, 일정, 문서 ID가 근거에 포함됐다.
- 개별 테스트에서는 문서 ID만 근거로 나온 실행이 있었다.

브리핑 문장은 입력에 근거했지만, 근거 ID가 빠지지 않는지는 추가 품질 검사 대상이다.

## 4. 검증 기준

문장 전체가 같은지는 검사하지 않는다. LLM 출력은 실행마다 달라질 수 있다.

- 출력 형식이 맞는가
- 필수 값이 비어 있지 않은가
- 입력에 없는 사실을 만들지 않았는가
- 개인정보가 LLM에 전달되지 않았는가
- 일정이 요청 기간과 업무시간 안에 있는가
- 기존 일정과 겹치지 않는가
- 사용자가 승인한 후보가 브리핑에 연결되는가
- 확인할 수 없는 정보가 `missing_information`에 들어가는가

## 5. 실행 명령어

`backend` 폴더에서 실행한다.

```powershell
$env:DEBUG='false'
$env:UV_CACHE_DIR='.uv-cache'
$env:PYTHONIOENCODING='utf-8'
[Console]::OutputEncoding = [Text.Encoding]::UTF8
```

관련 단위 테스트:

```powershell
uv run pytest -p no:cacheprovider tests/test_contract_management.py tests/test_schedule_management.py tests/test_contract_schedule_snapshots.py tests/test_agent_runs.py tests/test_activities.py
```

포트폴리오 선별:

```powershell
uv run pytest -s -p no:cacheprovider tests/test_contract_schedule_pipeline.py::test_select_next_meeting_candidates_with_real_llm
```

계약 1차 제안:

```powershell
uv run pytest -s -p no:cacheprovider tests/test_contract_schedule_pipeline.py::test_contract_next_meeting_with_real_llm
```

일정 추천:

```powershell
uv run pytest -s -p no:cacheprovider tests/test_contract_schedule_pipeline.py::test_schedule_management_with_real_llm
```

계약 브리핑:

```powershell
uv run pytest -s -p no:cacheprovider tests/test_contract_schedule_pipeline.py::test_contract_briefing_with_real_llm
```

전체 흐름:

```powershell
uv run pytest -s -p no:cacheprovider tests/test_contract_schedule_pipeline.py::test_contract_schedule_briefing_pipeline_with_real_llm
```

전체 흐름 20회 반복:

```powershell
1..20 | ForEach-Object {
    uv run pytest -q -p no:cacheprovider tests/test_contract_schedule_pipeline.py::test_contract_schedule_briefing_pipeline_with_real_llm
}
```

실제 LLM 테스트는 API 설정과 외부 네트워크가 필요하며 비용이 발생한다. 네트워크가 막히면 `llm_request_failed:ConnectError`가 발생한다.
