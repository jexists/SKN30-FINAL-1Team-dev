# SalesLuv 미팅·보고서 에이전트 구조

기준일: 2026-09-10. 현재 구현과 확인된 한계를 정리한다. [구조도 HTML](./미팅_내용분석_보고서작성_에이전트_구조_보고서.html)은 같은 요청 단위 구조를 요약한다.

## 1. 전체 흐름

~~~text
한 회사의 미팅 원문 + 선택 딜 N개
  ↓
입력 준비 [일반 코드]
  원문 구간·CRM·이전 확정본을 AgentRun 입력으로 고정
  ↓
내용분석 에이전트
  원문을 공통 / 딜별 / 미해결 / 범위 밖으로 분류
  위험 후보만 조건부 검토 1회
  필요하면 CRM 추가 조회 → 미해결 구간만 재분석
  ↓
공통 근거 장부
  ├─ 딜별 13개 특성 [구조화 LLM] → 로컬 ML → 참고 태그
  └─ 보고서 작성 [요청당 Supervisor 1개]
       └─ writer unit → v1·r1 → 지적 위치 repair 1회 → 선택적 v2 → HUMAN EDIT
  ↓
AgentRun 임시 결과 저장 → 화면에서 복구·수정 → 사용자가 최종 확정
  ↓
Report·ReportDeal·ReportSource·ReportSubmission을 한 트랜잭션으로 저장
  ├─ 해당 딜의 계약관리 파이프라인
  └─ 미팅 보고서 → 일일 보고서 → 주간 보고서 → 월간 보고서
~~~

업무 입력은 원문·회사·고객·선택 딜이다. 생성 버튼은 canonical `Report`를 미리 만들지 않고 전체 입력을 `/report-generations`에 보낸다. 결과는 복구 기한이 있는 `AgentRun` 후보이며 글자를 입력할 때마다 자동 호출하지 않는다. 같은 사용자·업무 범위의 최신 실행은 재접속 후 서버에서 다시 조회한다.

`meeting_processing`이 미팅당 한 번 근거를 고정하면 worker가 `meeting_report_writing`과 `meeting_analysis` 자식 실행을 만들어 보고서작성과 특성/ML을 병렬 처리한다. 보고서작성에 ML 결과를 사용하지 않는다. 요청을 받은 서버 트리거가 `meeting`/`daily`/`weekly`/`monthly` 종류를 이미 알고 해당 작성 역할을 결정하므로, Supervisor가 종류를 추측하는 분류 호출은 없다. 전체 연결·저장·시간 제한을 맡는 처리 서비스는 Supervisor LLM이 아니라 일반 코드다.

## 2. 내용분석 에이전트

서버가 원문을 문장·줄바꿈 기준으로 나누고 ID와 문자 위치를 붙인다. LLM은 원문을 재작성하지 않고 각 구간의 귀속만 반환한다.

| 분류 | 의미 |
|---|---|
| `meeting_context` | 참석자·장소 등 미팅 배경 |
| `company_context` | 회사·고객의 공통 배경 |
| `all_selected_deals` | 모든 선택 딜에 적용된다고 명시한 내용 |
| `deal` | 지정된 딜 하나 또는 여러 개의 내용 |
| `unresolved` | 어느 딜인지 확인되지 않은 내용 |
| `out_of_scope` | 선택 딜·미팅 범위 밖의 내용 |

초기 입력에는 선택 딜의 이름·설명·제품·단계와 기본 CRM을 제공한다. 최초 귀속 후 전체 딜 배정·같은 제품의 다른 딜·같은 단락의 후속 구간을 위험 후보로 골라 1회 검토한다. 후보가 없거나 선택 딜이 하나면 생략한다. 이후 미해결 구간이 있으면 LangChain `create_agent`가 필요한 도구를 선택한다.

- `trade_history`: 같은 회사의 과거 완료 거래.
- `previous_reports`: 같은 딜의 이전 제출·승인 보고서.
- `product_details`: 선택 딜의 제품 상세.

같은 조회는 빈 결과도 캐시한다. 새 정보가 없으면 미해결 상태를 유지하고, 이미 분류된 구간은 추가 조회 단계에서 바꾸지 않는다. 구간 누락·중복·선택 밖 딜은 코드로 검증한다. 공통/딜별 의미가 올바른지는 이 형식 검사만으로 보장되지 않는다.

## 3. 특성 생성과 ML

딜별 근거·공통 배경·해당 딜 CRM으로 구조화 LLM을 한 번 호출한다. 확인되지 않은 값은 Unknown이다.

| 영역 | 특성 |
|---|---|
| 권한·구매 절차 | Authority, Purch_dept, Budgt_alloc, Forml_tend, RFP |
| 경쟁·의향·요구 | Competitors, Posit_statm, Scope, Needs_def |
| CRM·거래 관계 | Source, Client, Cross_sale, Deal_type |

Source는 각 딜 컨텍스트에 고정된 유효 코드(고객 코드 우선, 없으면 딜 코드)를 Referral, Event, Online form, Joint past, Media, Other 중 하나로 변환한다. 따라서 고객 코드가 없고 선택 딜마다 유입경로가 달라도 서로 섞이지 않는다. 기본 이전 보고서 묶음은 특성 입력에서 제외하지만, 내용분석이 추가 조회한 해당 딜의 자료는 참고할 수 있다.

동시 처리는 최대 3딜이다. 특성 생성 뒤 최신 develop의 로컬 `deal_baseline.predict`를 호출한다. 한 딜의 ML 실패가 다른 딜을 중단시키지 않으며, 이미 생성한 특성은 보존한다. 모델 파일은 별도 배포 산출물이고 이 PR에 포함하지 않는다.

## 4. 보고서작성

API와 서버가 `report_kind`, scope·ID·기간, 입력 schema와 동결 자료를 먼저 확정한다. 보고서 요청마다 request-local `StateBackend`, configured model과 `create_deep_agent(...)` Supervisor를 하나 만들고 `ainvoke(...)`를 한 번 호출한다. Supervisor는 허용된 상태 안에서 다음 writer·reviewer task와 종료를 판단하지만 원자료를 읽거나 본문·검토·최종 JSON을 직접 쓰지 않는다.

| 구성 | 역할 |
|---|---|
| 서버 경계 | `meeting`/`daily`/`weekly`/`monthly` 종류와 scope·ID·기간·schema를 검증하고 source를 동결 |
| 요청별 Supervisor | 의미 있는 작업 지시와 정확한 `work_unit_id`로 선택 writer·공통 reviewer에 SDK `task` 위임, 결과를 본 뒤 `finish_report(candidate_version)`로 허용 후보 선택 |
| 선택 writer | 미팅 scope별 또는 기간 `body`의 근거 기반 내부 계획과 초안·지적 위치 수정 작성 |
| 공통 reviewer | 정확한 draft와 plan을 원자료·공통/종류 SKILL에 대조해 구조화 issue 반환 |
| 서버 실행 코드 | unit과 version을 검증하고 v1/v2 조립·후보 자격 제한, preview와 선택된 후보의 API schema 변환 |
| 필수 Skill | 하위 그래프의 `SkillsMiddleware`와 실제 `read_file`로 공통+선택 유형 규칙 읽기 |

~~~text
검증된 요청 + 동결 source + 고정 report_kind
  → 요청별 DeepAgents Supervisor 1개 / ainvoke 1회
  → 선택 writer task(s): SKILL·배정 근거 읽기 → 짧은 plan + unit 초안
  → 서버 검증·조립 → draft v1
  → 공통 reviewer task: 원자료 + plan + 정확한 v1 → review r1
     ├─ issue 없음 → Supervisor가 finish_report(1) 선택
     └─ issue 있음 → 지적 scope·location별 writer repair 최대 1회
          → 서버 검증·조립 → draft v2
          → 검증된 최신 draft를 사람이 확인·편집
          → 구조·범위 검증을 통과한 최신 후보 선택, 남은 issue는 화면 경고; 두 번째 repair 없음
~~~

미팅 writer는 배정 scope의 evidence ledger만 읽으며, deal scope에서 필요한 경우에만 정확한 딜의 CRM과 이번 미팅 전 불변 제출본 최신 5건을 배경으로 읽는다. 공통·미지정 내용은 따로 보존하고 원 STT나 더 오래된 DB 보고서를 새로 조회하지 않는다. 기간 입력 조립은 `period_sources.py`의 일반 코드다. 일일에는 동결 미팅 묶음·직접 활동과 첨부를, 주간·월간에는 각각 바로 아래 일일·주간 불변 제출본과 첨부를 전달하며 하위 원출처를 다시 탐색하지 않는다.

`harness.py`는 설치된 [`deepagents==0.7.11`](https://reference.langchain.com/python/deepagents/)의 실제 `create_deep_agent`와 SDK `task`를 사용한다. LangChain `create_agent`로 선택 writer와 공통 reviewer runnable을 한 번씩 compile해 요청 안의 task에서 재사용하고, 두 runnable만 Supervisor의 subagent middleware에 등록한다. 요청 간 Supervisor·child cache, 여덟 역할 registry, phase별 Supervisor 전달 체계는 두지 않는다. 프로젝트가 `CompiledSubAgent`를 직접 만들지 않는다. 부모·자식은 기존 `configured_chat_model()`을 사용하며 SDK 기본 모델이나 전역 profile로 바꾸지 않는다.

Supervisor에는 전체 workflow, 현재 허용 역할·stage·version, 다음에 필요한 판단을 설명하는 지시를 준다. Supervisor가 만든 task description의 작성·검토·수정 목적을 보존하고 정확한 `work_unit_id`를 요구하며, 신뢰할 수 있는 kind·scope·ID·period·version context는 별도 `SERVER_ASSIGNMENT` envelope로 덧붙여 검증한다. 현재 근거·CRM·과거 본문은 task 문장에 복사하지 않고 요청에 묶인 reader closure에서 읽는다. 모델 응답과 실제 tool 실행 양쪽에서 역할·파일·scope·딜 ID·version을 검사하며 general-purpose·sibling writer·중복 repair, 쓰기·셸·네트워크·DB 도구를 차단한다.

요청별 `StateBackend`의 `/skills`에는 아래 공통+선택 유형 MD와 선택 참고 파일만 읽기 전용으로 넣는다. `/artifacts/writer/<work_unit_id>.json`, `/artifacts/drafts/v1.json`, `/artifacts/reviews/r1.json`, 선택적인 `/artifacts/drafts/v2.json`, `/artifacts/final.json`은 고정 목적 도구가 schema·ID·version을 검증한 뒤에만 쓴다. task별 필수 read 이력도 분리해 재사용된 child나 동시 요청의 읽기가 서로 통과 조건을 빌리지 못하게 한다. 호스트 디렉터리, 범용 파일 쓰기, checkpointer/store 또는 다른 역할 SKILL은 제공하지 않는다. 최종 API 결과는 Supervisor prose가 아니라 서버가 보관한 검증 완료 draft object에서 조립한다.

기획 HTML, 아키텍처·API·DB 문서, 과거 평가 자료는 사람이 읽는 문서이며 모델 skill/source로 등록하지 않는다. 의료영업 전용 구버전 전제나 과거 MD 복사본을 추가하지 않는다.

### 도구와 서버 함수 구분

| 소비자 | 실제 도구/함수 | 자료 경계 |
|---|---|---|
| 보고서 Supervisor | SDK `task`, `finish_report(candidate_version)` | 선택 writer·공통 reviewer만 위임하고, child 결과를 본 뒤 서버가 허용한 후보만 명시적으로 선택; general-purpose 금지 |
| 보고서 하위 역할 | `read_file` | 위 공통+역할 MD/허용 reference만 |
| 미팅 하위 역할 | `read_meeting_evidence(scope)` | 작성/수정 한 scope, 검토의 서버 지정 scope만; 근거·첨부·필수 ID |
| 미팅 딜 역할/검토 | `read_deal_crm(scope, sales_deal_id)`, `read_previous_reports(scope, sales_deal_id)` | scope에 고정된 정확한 딜, 현재 사실과 과거 배경 분리 |
| 기간 하위 역할 | `read_report_context()`, `read_report_sources(source_id=None)` | 동결 맥락 및 전체/정확한 선택 ID 자료, 재조회·다른 기간 금지 |
| writer/reviewer | `WriterArtifact`, `ReportReview` | writer의 `work_unit_id`·base version·plan·draft 또는 review의 draft version·round·`location/evidence/action` issue 검증 |
| writer/reviewer | `read_validated_draft`, `read_writer_plans`, `read_validated_review` | 현재 task에 허용된 정확한 draft version·writer plan·review round만 읽기 |
| 내용분석 refinement | `read_company_trade_history()`, `read_previous_deal_reports(sales_deal_id)`, `read_deal_product_details(sales_deal_id)` | 기존 선택 딜/동결 CRM 경계 유지; 보고서 도구로 확대하지 않음 |
| 서버 일반 코드 | `create_meeting_tools`의 준비 reader, `_prepare_scopes`, `period_sources.build_source/run_context/source_units` | 입력 분리·검증·포장 함수이며 그 자체는 SDK tool 호출 아님 |
| 서버 일반 코드 | 보고서 조립·검증·리뷰 경로 해석·확정/저장 | 모델 도구로 제공하지 않음 |

Review r1은 정확한 v1과 writer plan을 허용 원자료에 대조하고 issue를 `location/evidence/action`으로만 반환한다. issue가 있으면 해당 scope·location을 v1 기준으로 한 번만 수정하고, 하나 이상 성공한 replacement를 한 번에 v2로 조립한다. AI 재검토 없이 구조·범위 검증을 통과한 최신 후보를 사람이 확인·편집한다. r1 issue는 수정 전 검토 메모로, 끝내지 못한 review·repair는 실제 실행 실패로 구분해 `AgentRun.evidence`에 보존한다. 입력·설정·인증·권한·무결성·취소 오류와 재시도 불가 공급자 HTTP 4xx는 fallback으로 숨기지 않고 전파한다. 임의 웹 검색·셸 실행·DB 수정 도구는 제공하지 않는다.

미팅 보고서는 세 부분으로 반환한다.

- `deal_reports[]`: 딜별 본문과 근거 ID.
- `common_report`: 공통 본문. 한 번 작성하고 모든 딜 보고서에 함께 보관·전달.
- `unassigned_report`: 미해결·범위 밖 내용을 정리한 확인 필요 본문과 근거 ID. 바꿔쓰기를 허용하며 원문 그대로의 인용을 보장하지 않는다.

미지정 구간은 공통사항 아래의 최종 확인 필요 섹션이며, 사용자가 본문을 직접 고칠 수 있다. 이를 특정 딜에 다시 배정하는 별도 에이전트 실행은 없다. 과거 보고서는 변경 가능한 `ReportDeal`이 아니라 이번 미팅 전에 제출된 불변 `ReportSubmission` 중 같은 딜의 최근 5건을 한 번에 읽고, 본문은 건당 최대 8,000자로 제한한다. 과거 약속의 이행은 이번 원문에 근거가 있을 때만 서술하도록 한다.

## 5. 저장·화면·기간 보고서

- 생성·재생성은 `AgentRun.output_snapshot`만 바꾸고 `Report`·`ReportDeal`을 자동으로 만들거나 수정하지 않는다.
- 화면은 같은 사용자와 논리 범위(미팅 ID 또는 보고 종류·기간)의 최신 queued/running/completed/partial/failed 실행을 복구해 후보를 직접 표시한다.
- 공통·딜별·미지정 본문과 제목은 화면의 임시 편집 상태다. 사용자가 최종 확정하면 전체 최종값과 선택한 `agent_run_id`를 `/reports/finalize`에 한 번 보내며, 보고서·딜·출처·불변 제출본을 같은 트랜잭션으로 저장한다.
- 수정 요청된 보고서는 `report_id`·기대 버전·기대 상태를 함께 보내 CAS로 재확정한다. 확정 요청은 멱등키로 응답 유실 재시도를 보호한다.
- 확정했거나 복구 기한이 지난 생성 실행은 원문·CRM·AI 본문을 지우고 요청 해시·모델·프롬프트·토큰·상태 같은 감사 메타데이터만 남긴다.
- 실행 상태가 completed여도 일부 보고서·ML이 실패할 수 있다. `errors`와 딜별 오류까지 확인한다.
- 미팅 보고서를 제출하면 해당 딜 계약관리 파이프라인을 큐잉한다. 생성·임시저장이 계약 확정을 뜻하지 않는다.
- 기간 출처는 `content.activities`에 선택된 하위 보고서 ID로 결정한다. 서버는 같은 팀의 조회 권한·작성자 상태·보고서 종류·기간·제출 상태를 검사하고 실제 제출본을 읽는다. 화면이 보낸 본문을 근거로 신뢰하지 않는다. 일일은 미팅, 주간은 일일, 월간은 주간 보고서를 참고하며 화면의 연결 보고서도 같은 계층을 따른다.
- 미팅·일일·주간·월간 보고서는 모두 줄글 본문 하나만 저장·표시한다. 저장된 다중 필드 보고서는 마이그레이션에서 승인된 값만 순서대로 본문에 옮기고, 런타임에서 구 양식을 복원하지 않는다.
- 기간 보고서는 `body` 하나를 작성해 v1 검토를 거치고, 지적 위치를 한 번 수정한 뒤 사람이 최종 편집한다. 일일의 미팅 묶음에는 딜·공통·미지정 본문을 중복 없이 담고, 주간·월간에는 바로 아래 기간 제출본의 본문을 담는다. 현재 본문·작성자 요청·검증된 첨부는 기존 입력 계약에 따라 반영한다. 미팅·계약 수를 딜 본문 수로 세지 않으며, 강조 소제목과 사람의 최종 편집을 지원한다.
- 하위 제출본의 `pending`·`approved`를 허용하고 반려·미제출 편집은 제외한다. 일일은 미팅의 `report_date`, 주간은 일일의 `report_date`, 월간은 주간의 기간 겹침을 검사한다. 월경계 주간은 해당 월에 속하는 사실만 집계하도록 범위를 전달한다. 미팅일은 생성·확정 요청에 고정하고, 늦은 제출이나 이후 일정 변경으로 바꾸지 않는다.
- 생성 시 제출 ID·revision·hash를 고정하고 확정 때 같은 출처인지 다시 검증한다. 새 제출이나 검토 상태 변경으로 출처가 달라지면 409로 재생성을 요구한다. 출처 메타데이터는 실행 원문 삭제 뒤에도 `AgentRun.source_refs`와 새 제출 스냅샷에 남는다. 과거 제출본·해시는 변경하지 않으며 구형 기간 생성 실행은 재생성해야 확정할 수 있다.
- 화면의 하위 보고서 조회는 첫 API 페이지에서 끊지 않는다. 생성 당시 선택과 제출본 식별을 고정해 조회 갱신이 작성 중인 본문이나 생성 근거를 바꾸지 않도록 한다. 선택한 출처와 입력의 접수 제한은 아래 기준으로 검사하며 초과분을 조용히 잘라내지 않는다.

### 입력 제한과 사용자 수정

파일은 업로드 전에, 글자 수와 요청 JSON은 생성·확정 전에 화면에서 검사한다. 서버도 같은 경계를 검사하므로 화면 검사를 우회한 요청은 거부한다. 파일에서 추출한 글자 수는 추출이 끝난 뒤, 생성 작업을 등록하기 전에 확인한다.

| 입력 | 접수 기준 |
|---|---|
| 원문·첨부 파일 | 빈 파일 거부, 미팅·보고서당 첨부 최대 10개. 음성은 서버 설정 `stt_max_bytes`(기본 25MiB), 이미지·PDF는 `upload_max_bytes`(기본 50MiB) 적용 |
| 원문 텍스트 | 직접 입력과 원문용 첨부의 추출문을 합쳐 50,000자. 공백 정리와 구분 줄바꿈을 포함해 계산 |
| 첨부 추출문 | 첨부당 50,000자. 참고 첨부도 개별 한도와 첨부 JSON 한도 적용 |
| 생성·HITL 본문 | 각 본문 50,000자. 미팅의 딜별·공통·미지정 본문도 각각 적용하며 생성 전 빈 초안은 허용 |
| 제목·작성자 요청 | 제목 254자, 작성자 요청 2,000자 |
| 요청 JSON | `template_snapshot`·`content`·`attachments` 각각 직렬화한 UTF-8 기준 256KiB |
| 선택 출처 | 보고서·직접 활동을 합쳐 최대 100개 |

프론트는 인증된 `/api/report-attachments/limits`에서 현재 파일 용량 설정 두 값을 받아 적용한다. 파일 확장자·MIME·시그니처, 첨부 소유권·만료와 출처 권한·날짜·버전은 서버가 검사한다. OCR 서비스의 조건부 전송 한도는 별도이며, 모든 PDF의 업로드 한도로 취급하지 않는다.

기간 작성 단계에 있던 자료 128개·자료당 직렬화 60,000자·전체 입력 180,000자 제한은 제거했다. 요청 JSON 한도는 서버가 조회해 고정하는 하위 보고서 본문 전체에 적용하는 한도가 아니며, 모델의 컨텍스트 한도를 보장하는 수치도 아니다. 일일←미팅, 주간←일일, 월간←주간 참조와 r1→필요 위치 repair 1회→HUMAN EDIT 상한을 유지한다. 사람이 수정한 문장은 AI로 다시 검증하지 않고 입력 형식·크기·권한과 확정 조건만 검사한다.

## 6. 시간 제한·스트리밍·로그

| 항목 | 설정 |
|---|---|
| 공급자 1회 호출 | 기본 180초(환경 설정 최대 300초). 보고서 요청 전체 deadline이 아님 |
| 내용분석 | 300초, 모델 24회, 추가 조회 8회 |
| 보고서작성 | 요청 전체 1,200초(`REPORT_TIMEOUT_SECONDS`), 기존 미팅 처리 1,200초와 일치. 같은 deadline 안에서 더 짧은 provider 제한과 유한한 child task 제한을 적용하고, 최초 writer unit + r1 + 지적 scope별 repair 최대 1회 + finish에 맞춰 모델·도구 호출 상한을 work unit 수로 계산 |
| 미팅 전체 처리 | 1,200초 |
| 화면·SSE 대기 | 최대 25분 |
| 임시 생성 payload | 완료 뒤 24시간 복구, 확정 또는 만료 시 원문·CRM·AI 본문 제거 |

미팅 화면은 SSE로 실제 단계와 딜·공통·미지정 본문 미리보기를 표시한다. 수정본은 교체하며, 연결이 끊기면 같은 실행을 조회한다. 내부 추론을 노출하거나 새 실행을 자동 생성하지 않는다. 기간 보고서는 상태 조회와 최종 결과 반영 방식이다.

로그에는 실행 ID·딜 ID, 단계·오류 종류·발생 위치와 시간, 공급자가 반환한 실제 토큰 사용량을 남긴다. 보고서 SDK callback이 실제 모델·도구·위임 횟수를 기록한다. 서버 summary의 `call_count`는 단계 실행 수이고 `model_call_count`는 SDK 모델 호출 수라 구분한다. 토큰 미반환/실패 호출은 추정하지 않으며 LangSmith tracing은 끈다. 누락 근거 ID·검증 위치·귀속 변경 전후도 기록하되 원문·응답 전체·도구 인자·키는 기록하지 않는다. 정확한 실패 문장은 로그에서 복원할 수 없다.

실행은 DB 큐, lease, heartbeat, lost-lease CAS로 관리한다. worker 재시작과 중복 선점은 이 경계에서 복구하며, LLM/검토 전체 제한시간은 재시도하지 않는다. 실제 연결·읽기 오류와 429·5xx만 제한적으로 재시도한다.

## 7. 검증과 후속 고도화

회귀검사 대상은 요청당 `create_deep_agent`·`ainvoke` 각 1회, 실제 SDK `task` 순서, 선택 writer·공통 reviewer만의 역할 제한, task별 필수 MD/source 읽기, scope·ID·version·schema 검증, r1→repair 1회 상한과 유효 v1 fallback이다. 이 오프라인 계약검사는 실 공급자 tool calling 호환성이나 문장 품질 측정 결과가 아니다. 화면 검사는 조회 갱신 때 편집 내용과 생성 출처가 보존되는지, 미팅일이 복구되는지, 소제목과 연결 보고서가 표시되는지를 별도로 확인한다. 실제 문장 품질은 별도의 골든셋 평가로 구분한다.

2026-09-08의 상품 연결 골든셋 비교에서 단계별 참조 B는 53/53건을 생성했다. 직접 참조 C는 52/53건을 생성했고 월간 입력 199,604자가 당시 적용한 180,000자 제한을 넘어 LLM 호출 전에 실패했다. 이 제한은 현재 제거했지만 과거 평가 결과는 변경하지 않는다. 주간 생성 사용량은 B 114,911토큰, C 371,505토큰이었다. 이 기록을 근거로 기간 보고서의 단계별 참조를 선택했다. 원본·평가 파일은 로컬에 보관하며, 해당 수치는 최신 develop에 반영한 이번 PR 코드의 신규 전수 실행 결과가 아니다. Judge 오판과 순서 편향, 사람 교정 없이 자동 제출한 조건 때문에 누락 해소나 전체 품질 우열을 단정하지 않는다.

아래는 2026-08-31 미팅 중심 합성 실행의 과거 기준이다. 위 기간보고서 골든셋과 표본이 다르며, 이번 PR의 품질 재측정으로 해석하지 않는다.

이 과거 미팅 골든셋의 유료 실행은 `02e6c87`에 커밋된 구현 기준이다. 로컬 `golden-quality-v5-20260831-review1/manifest.json`의 소스 해시로 식별한다. `run.py --score`는 저장 결과만 재채점하며 `--run`은 유료 실행이다. **이번 리뷰 수정 후 모델 품질을 재측정한 결과는 아니다.**

표본은 C01·C08 각 1~4차, C03 1~3차, C10 4차의 12회 미팅·36딜로 고정했다. 모델 `gpt-5.6-luna`, 동시 실행 3개, 원문 구간 111개·필드 468개·필수 사실 46개다.

| 항목 | 결과 |
|---|---:|
| 근거 범위·딜 일치 | 94/111 = 84.7% |
| 특성 필드 정확도 | 350/468 = 74.8% |
| 13개 특성이 모두 맞은 딜 | 0/36 |
| 보고서 생성 | 12/12회, 36/36딜 성공 |
| 필수 사실 의미·귀속 보존 | 38/46 = 82.6% |
| 미팅당 평균 토큰 | 101,019 |
| 전체 지연 p50 / p95 | 56.1초 / 95.7초 |

필수 사실은 AI가 직접 비교한 의미 검수이며 사람의 확정 판정이 아니다. 동결 CRM·합성 이전 메모를 사용했고 DB 저장·화면까지의 전체 시험은 아니다. 표본은 무작위가 아니며 전체 성능으로 일반화하지 않는다. 원문·계정·실행 로그는 로컬에 보관하고 커밋하지 않는다.

검토 직전·직후 정확 일치는 87/111 → 93/111이다. 오답 8개를 고쳤으나 정답 2개가 바뀌었다(실제 의미 오류 1, 범주 표현 차이 1). 기존 추가조회에서 1개가 더 맞았다. 실행 간 지표 변화 전체를 검토의 인과효과로 해석하지 않는다.

남은 고도화:

1. 딜 전용 내용을 공통으로 확대하거나, 문맥상 후속 행동을 미지정으로 보내는 귀속 오류.
2. Unknown의 과잉 추정과 범주 경계. 대표 직함만으로 승인 권한을 확정하지 않는 등 판정 기준 구체화.
3. 검토가 모호한 내용을 특정 딜로 확정하지 않도록 변경 근거 기준 강화.
4. 과거 이력과 현재의 진전을 모순되게 쓰거나 불필요한 미확인 문장을 반복하는 보고서 품질.
5. 일일/주간/월간을 포함한 `원문글 → 최종글` 텍스트 표본의 후속 사람 품질 검사.
