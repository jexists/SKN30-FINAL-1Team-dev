# SalesLuv 미팅·보고서 에이전트 구조

기준일: 2026-09-03. 현재 구현과 확인된 한계를 정리한다. [구조도 HTML](./미팅_내용분석_보고서작성_에이전트_구조_보고서.html)은 선행 구현 스냅샷이며, 최신 검토 구조와 검증 기준은 이 문서를 따른다.

## 1. 전체 흐름

~~~text
한 회사의 미팅 원문 + 선택 딜 N개
  ↓
입력 준비 [일반 코드]
  원문 구간·CRM·이전 확정본을 AgentRun 입력으로 고정
  ↓
내용분석 에이전트
  원문을 공통 / 딜별 / 미해결 / 범위 밖으로 분류
  위험 후보만 조건부 검토 1회
  필요하면 CRM 추가 조회 → 미해결 구간만 재분석
  ↓
공통 근거 장부
  ├─ 딜별 13개 특성 [구조화 LLM] → 로컬 ML → 참고 태그
  └─ 보고서 Deep Agents Supervisor
       └─ task 위임 → 역할별 Subagent 작성 → 조립·검토·필요 시 최대 1회 재작성
  ↓
AgentRun 임시 결과 저장 → 화면에서 복구·수정 → 사용자가 최종 확정
  ↓
Report·ReportDeal·ReportSource·ReportSubmission을 한 트랜잭션으로 저장
  ├─ 해당 딜의 계약관리 파이프라인
  └─ 미팅 → 일일 → 주간 → 월간 보고서
~~~

업무 입력은 원문·회사·고객·선택 딜이다. 생성 버튼은 canonical `Report`를 미리 만들지 않고 전체 입력을 `/report-generations`에 보낸다. 결과는 복구 기한이 있는 `AgentRun` 후보이며 글자를 입력할 때마다 자동 호출하지 않는다. 같은 사용자·업무 범위의 최신 실행은 재접속 후 서버에서 다시 조회한다.

내용분석은 미팅당 한 번, 보고서작성과 특성 생성은 그 뒤에 병렬로 실행한다. 보고서작성에 ML 결과를 사용하지 않는다. 요청을 받은 서버 트리거가 `meeting`/`daily`/`weekly`/`monthly` 종류를 이미 알고 해당 작성 역할을 결정하므로, Supervisor가 종류를 추측하는 분류 호출은 없다. 전체 연결·저장·시간 제한을 맡는 처리 서비스는 Supervisor LLM이 아니라 일반 코드다.

## 2. 내용분석 에이전트

서버가 원문을 문장·줄바꿈 기준으로 나누고 ID와 문자 위치를 붙인다. LLM은 원문을 재작성하지 않고 각 구간의 귀속만 반환한다.

| 분류 | 의미 |
|---|---|
| `meeting_context` | 참석자·장소 등 미팅 배경 |
| `company_context` | 회사·고객의 공통 배경 |
| `all_selected_deals` | 모든 선택 딜에 적용된다고 명시한 내용 |
| `deal` | 지정된 딜 하나 또는 여러 개의 내용 |
| `unresolved` | 어느 딜인지 확인되지 않은 내용 |
| `out_of_scope` | 선택 딜·미팅 범위 밖의 내용 |

초기 입력에는 선택 딜의 이름·설명·제품·단계와 기본 CRM을 제공한다. 최초 귀속 후 전체 딜 배정·같은 제품의 다른 딜·같은 단락의 후속 구간을 위험 후보로 골라 1회 검토한다. 후보가 없거나 선택 딜이 하나면 생략한다. 이후 미해결 구간이 있으면 LangChain `create_agent`가 필요한 도구를 선택한다.

- `trade_history`: 같은 회사의 과거 완료 거래.
- `previous_reports`: 같은 딜의 이전 제출·승인 보고서.
- `product_details`: 선택 딜의 제품 상세.

같은 조회는 빈 결과도 캐시한다. 새 정보가 없으면 미해결 상태를 유지하고, 이미 분류된 구간은 추가 조회 단계에서 바꾸지 않는다. 구간 누락·중복·선택 밖 딜은 코드로 검증한다. 공통/딜별 의미가 올바른지는 이 형식 검사만으로 보장되지 않는다.

## 3. 특성 생성과 ML

딜별 근거·공통 배경·해당 딜 CRM으로 구조화 LLM을 한 번 호출한다. 확인되지 않은 값은 Unknown이다.

| 영역 | 특성 |
|---|---|
| 권한·구매 절차 | Authority, Purch_dept, Budgt_alloc, Forml_tend, RFP |
| 경쟁·의향·요구 | Competitors, Posit_statm, Scope, Needs_def |
| CRM·거래 관계 | Source, Client, Cross_sale, Deal_type |

Source는 각 딜 컨텍스트에 고정된 유효 코드(고객 코드 우선, 없으면 딜 코드)를 Referral, Event, Online form, Joint past, Media, Other 중 하나로 변환한다. 따라서 고객 코드가 없고 선택 딜마다 유입경로가 달라도 서로 섞이지 않는다. 기본 이전 보고서 묶음은 특성 입력에서 제외하지만, 내용분석이 추가 조회한 해당 딜의 자료는 참고할 수 있다.

동시 처리는 최대 3딜이다. 특성 생성 뒤 최신 develop의 로컬 `deal_baseline.predict`를 호출한다. 한 딜의 ML 실패가 다른 딜을 중단시키지 않으며, 이미 생성한 특성은 보존한다. 모델 파일은 별도 배포 산출물이고 이 PR에 포함하지 않는다.

## 4. Deep Agents 보고서작성

공통 Supervisor는 보고서 문장을 직접 쓰지 않는다. 서버가 확정한 보고서 종류에 맞는 역할 Subagent에게 Deep Agents의 `task`로 작성을 위임하고, 결과를 조립·검토한 뒤 최종 후보를 반환한다.

| 구성 | 역할 |
|---|---|
| 서버 트리거 | `meeting`/`daily`/`weekly`/`monthly` 요청 경로로 작성 역할을 결정 |
| 공통 Supervisor | `task` 위임, Subagent 결과 조립, 검토 요청, 최종 후보 반환. 본문은 직접 작성하지 않음 |
| 미팅 작성 Subagent | 선택 딜별 본문과 공통·미지정 본문을 작성 |
| 기간 작성 Subagent | 서버가 선택한 daily/weekly/monthly 역할로 하위 확정본을 종합 |
| 필수 Skill | 역할별 `SKILL.md` 전문을 Subagent 시스템 프롬프트에 매 실행 주입 |
| 역할별 도구 | 미팅은 근거·딜 CRM·이전 보고서, 기간은 선택된 하위 보고서 조회만 연결 |
| 검토 | 작성 후보의 사실 보존·누락·혼입 이슈를 수정 제안으로 반환 |

~~~text
서버가 역할 확정
  → Supervisor가 task 위임
  → 역할 Subagent가 필수 SKILL.md + 필요 도구로 작성
  → Supervisor가 조립·검토
     ├─ 수정 불필요 → 현재 초안 반환
     └─ 수정 제안 있음 → Subagent 최대 1회 재작성 → 최신 초안 반환
~~~

미팅은 선택한 N개 딜에 각각 하나씩, 공통·미지정 영역에 하나의 작성 task를 사용한다. 기간 보고서는 요청 종류에 해당하는 작성 task 하나를 사용한다. 검토 이슈가 있으면 같은 역할에 재작성을 최대 한 번만 요청한다.

`read_meeting_evidence`, `read_deal_crm`, `read_previous_reports`, `read_report_sources`는 외부 API나 DB를 새로 호출하지 않고, 이미 권한 검사를 거쳐 동결된 런타임 입력을 읽는 로컬 Python 함수다. 다만 모델이 도구를 요청하고 결과를 받아 계속 작성하는 각 단계의 provider 모델 호출은 별도다. 따라서 위임 횟수, 로컬 도구 호출 횟수, provider 모델 호출 횟수를 구분해 기록하며 원문과 도구 인자는 로그에 남기지 않는다.

의미·표현·위험 문구 검토는 초안을 더 나아지게 하는 advisory 단계이지 런타임 차단 게이트가 아니다. 최대 재작성 횟수에 도달하면 의미 이슈가 남아도 렌더링 가능한 최신 초안을 정상 `completed`로 반환하고 사용자가 수정·확정한다. provider 호출 실패, 파싱 불능, 선택 딜 ID·필수 본문·길이 같은 기계적 UI 계약을 만족하지 못한 경우만 실행 실패로 처리한다. 임의 웹 검색·셸 실행·DB 수정 도구는 제공하지 않는다.

보고서는 세 부분으로 반환한다.

- `deal_reports[]`: 딜별 본문과 근거 ID.
- `common_report`: 공통 본문. 한 번 작성하고 모든 딜 보고서에 함께 보관·전달.
- `unassigned_report`: 미해결·범위 밖 원문을 그대로 인용한 확인 필요 내용.

미지정 구간은 공통사항 아래의 최종 확인 필요 섹션이며, 사용자가 본문을 직접 고칠 수 있다. 이를 특정 딜에 다시 배정하는 별도 에이전트 실행은 없다. 과거 보고서는 변경 가능한 `ReportDeal`이 아니라 이번 미팅 전에 제출된 불변 `ReportSubmission` 중 같은 딜의 최근 5건을 한 번에 읽고, 본문은 건당 최대 8,000자로 제한한다. 과거 약속의 이행은 이번 원문에 근거가 있을 때만 서술하도록 한다.

## 5. 저장·화면·기간 보고서

- 생성·재생성은 `AgentRun.output_snapshot`만 바꾸고 `Report`·`ReportDeal`을 자동으로 만들거나 수정하지 않는다.
- 화면은 같은 사용자와 논리 범위(미팅 ID 또는 보고 종류·기간)의 최신 queued/running/completed/partial/failed 실행을 복구해 후보를 직접 표시한다.
- 공통·딜별·미지정 본문과 제목은 화면의 임시 편집 상태다. 사용자가 최종 확정하면 전체 최종값과 선택한 `agent_run_id`를 `/reports/finalize`에 한 번 보내며, 보고서·딜·출처·불변 제출본을 같은 트랜잭션으로 저장한다.
- 수정 요청된 보고서는 `report_id`·기대 버전·기대 상태를 함께 보내 CAS로 재확정한다. 확정 요청은 멱등키로 응답 유실 재시도를 보호한다.
- 확정했거나 복구 기한이 지난 생성 실행은 원문·CRM·AI 본문을 지우고 요청 해시·모델·프롬프트·토큰·상태 같은 감사 메타데이터만 남긴다.
- 실행 상태가 completed여도 일부 보고서·ML이 실패할 수 있다. `errors`와 딜별 오류까지 확인한다.
- 미팅 보고서를 제출하면 해당 딜 계약관리 파이프라인을 큐잉한다. 생성·임시저장이 계약 확정을 뜻하지 않는다.
- 일일·주간·월간도 같은 생성·확정 경계를 사용한다. 서버가 보고서 종류를 확정하고, 공통 Supervisor가 해당 daily/weekly/monthly Subagent에게 미팅·일일·주간 확정본의 종합을 위임한다.
- 미팅·일일·주간·월간 보고서는 모두 줄글 본문 하나만 저장·표시한다. 저장된 다중 필드 보고서는 마이그레이션에서 승인된 값만 순서대로 본문에 옮기고, 런타임에서 구 양식을 복원하지 않는다.
- 기간 보고서는 `body` 하나만 생성하며 ‘내일 계획’ 같은 고정 항목을 억지로 만들지 않는다. 제출·승인된 하위 자료의 권한·기간을 검사하고, 미팅별 공통 내용을 중복 없이 종합한다. 월 경계의 사실을 분리할 근거가 없으면 월 전체 실적으로 단정하지 않는다.

## 6. 시간 제한·스트리밍·로그

| 항목 | 설정 |
|---|---|
| LLM 요청 | 기본 180초. 기존 환경변수 값은 별도 확인 필요 |
| 내용분석 | 300초, 모델 24회, 추가 조회 8회 |
| 보고서작성 | 900초. 위임·모델·검토·재작성 한도는 작성 모듈의 `MAX_REVIEWS`, `MAX_REPAIRS` 및 단계별 `*_MODEL_CALL_LIMIT` 상수로 계산 |
| 미팅 전체 처리 | 1,200초 |
| 화면·SSE 대기 | 최대 25분 |
| 임시 생성 payload | 완료 뒤 24시간 복구, 확정 또는 만료 시 원문·CRM·AI 본문 제거 |

미팅 화면은 SSE로 실제 단계와 딜·공통·미지정 본문 미리보기를 표시한다. 수정본은 교체하며, 연결이 끊기면 같은 실행을 조회한다. 내부 추론을 노출하거나 새 실행을 자동 생성하지 않는다. 기간 보고서는 상태 조회와 최종 결과 반영 방식이다.

로그에는 실행 ID·딜 ID, 단계·오류 종류·발생 위치, 시간·검토 한도, `delegation_count`·`tool_call_count`·`model_call_count`, 공급자가 반환한 토큰 사용량을 구분해 남긴다. 누락 근거 ID·검증 위치·귀속 변경 전후도 기록하되 원문·응답 전체·도구 인자·키는 기록하지 않는다. 정확한 실패 문장은 로그에서 복원할 수 없다.

실행은 DB 큐, lease, heartbeat, lost-lease CAS로 관리한다. worker 재시작과 중복 선점은 이 경계에서 복구하며, LLM/검토 전체 제한시간은 재시도하지 않는다. 실제 연결·읽기 오류와 429·5xx만 제한적으로 재시도한다.

## 7. 검증과 후속 고도화

이번 구조 변경은 브라우저 E2E 검사 대상이 아니다. 핵심 하네스의 역할 선택·`task` 위임·필수 Skill 주입·도구 범위·최대 1회 재작성·기계 계약만 코드 테스트한다. 작성 품질은 에이전트에게 제공한 원문과 반환된 최종글을 `원문글 → 최종글`의 텍스트로 나란히 정리해 후속 품질 검사에서 판단한다.

아래 품질 수치는 구조 변경 전 합성 실행을 재채점한 과거 기준이며, 현재 Deep Agents 구조의 실제 LLM 품질 재측정으로 해석하지 않는다.

합성 골든셋의 마지막 유료 실행은 `02e6c87`에 커밋된 구현 기준이다. 로컬 `golden-quality-v5-20260831-review1/manifest.json`의 소스 해시로 식별한다. `run.py --score`는 저장 결과만 재채점하며 `--run`은 유료 실행이다. **이번 리뷰 수정 후 모델 품질을 재측정한 결과는 아니다.**

표본은 C01·C08 각 1~4차, C03 1~3차, C10 4차의 12회 미팅·36딜로 고정했다. 모델 `gpt-5.6-luna`, 동시 실행 3개, 원문 구간 111개·필드 468개·필수 사실 46개다.

| 항목 | 결과 |
|---|---:|
| 근거 범위·딜 일치 | 94/111 = 84.7% |
| 특성 필드 정확도 | 350/468 = 74.8% |
| 13개 특성이 모두 맞은 딜 | 0/36 |
| 보고서 생성 | 12/12회, 36/36딜 성공 |
| 필수 사실 의미·귀속 보존 | 38/46 = 82.6% |
| 미팅당 평균 토큰 | 101,019 |
| 전체 지연 p50 / p95 | 56.1초 / 95.7초 |

필수 사실은 AI가 직접 비교한 의미 검수이며 사람의 확정 판정이 아니다. 동결 CRM·합성 이전 메모를 사용했고 DB 저장·화면까지의 전체 시험은 아니다. 표본은 무작위가 아니며 전체 성능으로 일반화하지 않는다. 원문·계정·실행 로그는 로컬에 보관하고 커밋하지 않는다.

검토 직전·직후 정확 일치는 87/111 → 93/111이다. 오답 8개를 고쳤으나 정답 2개가 바뀌었다(실제 의미 오류 1, 범주 표현 차이 1). 기존 추가조회에서 1개가 더 맞았다. 실행 간 지표 변화 전체를 검토의 인과효과로 해석하지 않는다.

남은 고도화:

1. 딜 전용 내용을 공통으로 확대하거나, 문맥상 후속 행동을 미지정으로 보내는 귀속 오류.
2. Unknown의 과잉 추정과 범주 경계. 대표 직함만으로 승인 권한을 확정하지 않는 등 판정 기준 구체화.
3. 검토가 모호한 내용을 특정 딜로 확정하지 않도록 변경 근거 기준 강화.
4. 과거 이력과 현재의 진전을 모순되게 쓰거나 불필요한 미확인 문장을 반복하는 보고서 품질.
5. 일일/주간/월간을 포함한 `원문글 → 최종글` 텍스트 표본의 후속 사람 품질 검사.
