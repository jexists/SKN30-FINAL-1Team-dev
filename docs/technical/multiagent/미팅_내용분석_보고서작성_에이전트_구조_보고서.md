# SalesLuv 미팅·보고서 에이전트 구조

기준일: 2026-09-09. 현재 구현과 확인된 한계를 정리한다. [구조도 HTML](./미팅_내용분석_보고서작성_에이전트_구조_보고서.html)은 선행 구현 스냅샷이며, 최신 검토 구조와 검증 기준은 이 문서를 따른다.

## 1. 전체 흐름

~~~text
한 회사의 미팅 원문 + 선택 딜 N개
  ↓
입력 준비 [일반 코드]
  원문 구간·CRM·이전 확정본을 AgentRun 입력으로 고정
  ↓
내용분석 에이전트
  원문을 공통 / 딜별 / 미해결 / 범위 밖으로 분류
  위험 후보만 조건부 검토 1회
  필요하면 CRM 추가 조회 → 미해결 구간만 재분석
  ↓
공통 근거 장부
  ├─ 딜별 13개 특성 [구조화 LLM] → 로컬 ML → 참고 태그
  └─ 보고서 작성
       └─ 근거 범위별 작성 → 검토 1회 → 필요 시 수정 1회
  ↓
AgentRun 임시 결과 저장 → 화면에서 복구·수정 → 사용자가 최종 확정
  ↓
Report·ReportDeal·ReportSource·ReportSubmission을 한 트랜잭션으로 저장
  ├─ 해당 딜의 계약관리 파이프라인
  └─ 미팅 보고서 → 일일 보고서 → 주간 보고서 → 월간 보고서
~~~

업무 입력은 원문·회사·고객·선택 딜이다. 생성 버튼은 canonical `Report`를 미리 만들지 않고 전체 입력을 `/report-generations`에 보낸다. 결과는 복구 기한이 있는 `AgentRun` 후보이며 글자를 입력할 때마다 자동 호출하지 않는다. 같은 사용자·업무 범위의 최신 실행은 재접속 후 서버에서 다시 조회한다.

내용분석은 미팅당 한 번, 보고서작성과 특성 생성은 그 뒤에 병렬로 실행한다. 보고서작성에 ML 결과를 사용하지 않는다. 요청을 받은 서버 트리거가 `meeting`/`daily`/`weekly`/`monthly` 종류를 이미 알고 해당 작성 역할을 결정하므로, Supervisor가 종류를 추측하는 분류 호출은 없다. 전체 연결·저장·시간 제한을 맡는 처리 서비스는 Supervisor LLM이 아니라 일반 코드다.

## 2. 내용분석 에이전트

서버가 원문을 문장·줄바꿈 기준으로 나누고 ID와 문자 위치를 붙인다. LLM은 원문을 재작성하지 않고 각 구간의 귀속만 반환한다.

| 분류 | 의미 |
|---|---|
| `meeting_context` | 참석자·장소 등 미팅 배경 |
| `company_context` | 회사·고객의 공통 배경 |
| `all_selected_deals` | 모든 선택 딜에 적용된다고 명시한 내용 |
| `deal` | 지정된 딜 하나 또는 여러 개의 내용 |
| `unresolved` | 어느 딜인지 확인되지 않은 내용 |
| `out_of_scope` | 선택 딜·미팅 범위 밖의 내용 |

초기 입력에는 선택 딜의 이름·설명·제품·단계와 기본 CRM을 제공한다. 최초 귀속 후 전체 딜 배정·같은 제품의 다른 딜·같은 단락의 후속 구간을 위험 후보로 골라 1회 검토한다. 후보가 없거나 선택 딜이 하나면 생략한다. 이후 미해결 구간이 있으면 LangChain `create_agent`가 필요한 도구를 선택한다.

- `trade_history`: 같은 회사의 과거 완료 거래.
- `previous_reports`: 같은 딜의 이전 제출·승인 보고서.
- `product_details`: 선택 딜의 제품 상세.

같은 조회는 빈 결과도 캐시한다. 새 정보가 없으면 미해결 상태를 유지하고, 이미 분류된 구간은 추가 조회 단계에서 바꾸지 않는다. 구간 누락·중복·선택 밖 딜은 코드로 검증한다. 공통/딜별 의미가 올바른지는 이 형식 검사만으로 보장되지 않는다.

## 3. 특성 생성과 ML

딜별 근거·공통 배경·해당 딜 CRM으로 구조화 LLM을 한 번 호출한다. 확인되지 않은 값은 Unknown이다.

| 영역 | 특성 |
|---|---|
| 권한·구매 절차 | Authority, Purch_dept, Budgt_alloc, Forml_tend, RFP |
| 경쟁·의향·요구 | Competitors, Posit_statm, Scope, Needs_def |
| CRM·거래 관계 | Source, Client, Cross_sale, Deal_type |

Source는 각 딜 컨텍스트에 고정된 유효 코드(고객 코드 우선, 없으면 딜 코드)를 Referral, Event, Online form, Joint past, Media, Other 중 하나로 변환한다. 따라서 고객 코드가 없고 선택 딜마다 유입경로가 달라도 서로 섞이지 않는다. 기본 이전 보고서 묶음은 특성 입력에서 제외하지만, 내용분석이 추가 조회한 해당 딜의 자료는 참고할 수 있다.

동시 처리는 최대 3딜이다. 특성 생성 뒤 최신 develop의 로컬 `deal_baseline.predict`를 호출한다. 한 딜의 ML 실패가 다른 딜을 중단시키지 않으며, 이미 생성한 특성은 보존한다. 모델 파일은 별도 배포 산출물이고 이 PR에 포함하지 않는다.

## 4. 보고서작성

작성 순서는 일반 실행 코드가 정한다. 미팅은 근거 범위를 나누어 작성하고, 기간 보고서는 해당 종류의 하위 보고서를 종합한다. 작성 이후 검토는 한 번만 수행하며 수정이 필요하면 한 번 수정한다.

| 구성 | 역할 |
|---|---|
| 서버 트리거 | `meeting`/`daily`/`weekly`/`monthly` 요청에 맞는 작성 경로 선택 |
| 실행 코드 | 작성·검토·수정 호출과 최종 후보 조립, 기계적 출력 검증 |
| 미팅 작성 | 선택 딜별 본문과 공통·미지정 본문 작성 |
| 기간 작성 | 일일은 미팅, 주간은 일일, 월간은 주간 제출본을 종합 |
| 필수 Skill | 보고서 종류별 `SKILL.md`의 작성 규칙 적용 |
| 검토 | 사실 보존·누락·혼입 이슈를 수정 제안으로 반환 |

~~~text
서버가 보고서 종류와 근거 범위를 확정
  → 해당 작성 규칙과 고정 입력으로 초안 작성
  → 검토 1회
     ├─ 수정 불필요 → 현재 초안 반환
     └─ 수정 필요 → 최대 1회 수정 → 유효한 초안 반환
~~~

미팅의 딜별 작성 입력은 해당 딜에 귀속된 근거와 CRM, 같은 딜의 이전 제출본을 사용한다. 공통·미지정 내용은 따로 보존한다. 기간 입력 조립은 `period_sources.py`의 일반 코드다. 일일에는 미팅 묶음을, 주간·월간에는 각각 일일·주간 제출본을 전달하며 주간·월간 작성에 모든 미팅 본문을 다시 추가하지 않는다.

`read_meeting_evidence`, `read_deal_crm`, `read_previous_reports`는 권한 검사를 거쳐 고정된 런타임 입력을 읽는 로컬 함수다. 공급자 모델 요청의 사용량과 종료 사유를 기록한다. 기간 보고서의 근거 선택·고정은 모델에 맡기지 않고 서버의 `report_sources.py`에서 처리한다.

의미·표현 검토는 수정 제안을 위한 단계다. 의미 이슈가 남아도 수정은 한 번만 수행하고 유효한 초안을 사용자에게 반환한다. 유효 초안을 만든 뒤 검토·수정에서 503 같은 공급자 오류나 파싱·출력 형식 오류가 발생하면 초안을 보존해 완료할 수 있다. 미팅 수정본의 출력 계약 위반도 기존 유효 초안을 보존하며, 검토까지 정상 완료한 결과와 구분한다. 최초 작성 실패와 입력·권한·설정 오류 또는 취소는 이 초안 보존 경로로 숨기지 않는다. 입력 제한은 아래의 접수 단계에서 검사하며, 기간 작성 에이전트에 별도의 문자 수 제한을 두지 않는다. 임의 웹 검색·셸 실행·DB 수정 도구는 제공하지 않는다.

미팅 보고서는 세 부분으로 반환한다.

- `deal_reports[]`: 딜별 본문과 근거 ID.
- `common_report`: 공통 본문. 한 번 작성하고 모든 딜 보고서에 함께 보관·전달.
- `unassigned_report`: 미해결·범위 밖 내용을 정리한 확인 필요 본문과 근거 ID. 바꿔쓰기를 허용하며 원문 그대로의 인용을 보장하지 않는다.

미지정 구간은 공통사항 아래의 최종 확인 필요 섹션이며, 사용자가 본문을 직접 고칠 수 있다. 이를 특정 딜에 다시 배정하는 별도 에이전트 실행은 없다. 과거 보고서는 변경 가능한 `ReportDeal`이 아니라 이번 미팅 전에 제출된 불변 `ReportSubmission` 중 같은 딜의 최근 5건을 한 번에 읽고, 본문은 건당 최대 8,000자로 제한한다. 과거 약속의 이행은 이번 원문에 근거가 있을 때만 서술하도록 한다.

## 5. 저장·화면·기간 보고서

- 생성·재생성은 `AgentRun.output_snapshot`만 바꾸고 `Report`·`ReportDeal`을 자동으로 만들거나 수정하지 않는다.
- 화면은 같은 사용자와 논리 범위(미팅 ID 또는 보고 종류·기간)의 최신 queued/running/completed/partial/failed 실행을 복구해 후보를 직접 표시한다.
- 공통·딜별·미지정 본문과 제목은 화면의 임시 편집 상태다. 사용자가 최종 확정하면 전체 최종값과 선택한 `agent_run_id`를 `/reports/finalize`에 한 번 보내며, 보고서·딜·출처·불변 제출본을 같은 트랜잭션으로 저장한다.
- 수정 요청된 보고서는 `report_id`·기대 버전·기대 상태를 함께 보내 CAS로 재확정한다. 확정 요청은 멱등키로 응답 유실 재시도를 보호한다.
- 확정했거나 복구 기한이 지난 생성 실행은 원문·CRM·AI 본문을 지우고 요청 해시·모델·프롬프트·토큰·상태 같은 감사 메타데이터만 남긴다.
- 실행 상태가 completed여도 일부 보고서·ML이 실패할 수 있다. `errors`와 딜별 오류까지 확인한다.
- 미팅 보고서를 제출하면 해당 딜 계약관리 파이프라인을 큐잉한다. 생성·임시저장이 계약 확정을 뜻하지 않는다.
- 기간 출처는 `content.activities`에 선택된 하위 보고서 ID로 결정한다. 서버는 같은 팀의 조회 권한·작성자 상태·보고서 종류·기간·제출 상태를 검사하고 실제 제출본을 읽는다. 화면이 보낸 본문을 근거로 신뢰하지 않는다. 일일은 미팅, 주간은 일일, 월간은 주간 보고서를 참고하며 화면의 연결 보고서도 같은 계층을 따른다.
- 미팅·일일·주간·월간 보고서는 모두 줄글 본문 하나만 저장·표시한다. 저장된 다중 필드 보고서는 마이그레이션에서 승인된 값만 순서대로 본문에 옮기고, 런타임에서 구 양식을 복원하지 않는다.
- 기간 보고서는 `body` 하나를 작성하고 검토 1회·필요 시 수정 1회를 거친다. 일일의 미팅 묶음에는 딜·공통·미지정 본문을 중복 없이 담고, 주간·월간에는 하위 기간 제출본의 본문을 담는다. 현재 본문·작성자 요청·검증된 첨부는 기존 입력 계약에 따라 반영한다. 미팅·계약 수를 딜 본문 수로 세지 않으며, 강조 소제목과 사람의 최종 편집을 지원한다.
- 하위 제출본의 `pending`·`approved`를 허용하고 반려·미제출 편집은 제외한다. 일일은 미팅의 `report_date`, 주간은 일일의 `report_date`, 월간은 주간의 기간 겹침을 검사한다. 월경계 주간은 해당 월에 속하는 사실만 집계하도록 범위를 전달한다. 미팅일은 생성·확정 요청에 고정하고, 늦은 제출이나 이후 일정 변경으로 바꾸지 않는다.
- 생성 시 제출 ID·revision·hash를 고정하고 확정 때 같은 출처인지 다시 검증한다. 새 제출이나 검토 상태 변경으로 출처가 달라지면 409로 재생성을 요구한다. 출처 메타데이터는 실행 원문 삭제 뒤에도 `AgentRun.source_refs`와 새 제출 스냅샷에 남는다. 과거 제출본·해시는 변경하지 않으며 구형 기간 생성 실행은 재생성해야 확정할 수 있다.
- 화면의 하위 보고서 조회는 첫 API 페이지에서 끊지 않는다. 생성 당시 선택과 제출본 식별을 고정해 조회 갱신이 작성 중인 본문이나 생성 근거를 바꾸지 않도록 한다. 선택한 출처와 입력의 접수 제한은 아래 기준으로 검사하며 초과분을 조용히 잘라내지 않는다.

### 입력 제한과 사용자 수정

파일은 업로드 전에, 글자 수와 요청 JSON은 생성·확정 전에 화면에서 검사한다. 서버도 같은 경계를 검사하므로 화면 검사를 우회한 요청은 거부한다. 파일에서 추출한 글자 수는 추출이 끝난 뒤, 생성 작업을 등록하기 전에 확인한다.

| 입력 | 접수 기준 |
|---|---|
| 원문·첨부 파일 | 빈 파일 거부, 미팅·보고서당 첨부 최대 10개. 음성은 서버 설정 `stt_max_bytes`(기본 25MiB), 이미지·PDF는 `upload_max_bytes`(기본 50MiB) 적용 |
| 원문 텍스트 | 직접 입력과 원문용 첨부의 추출문을 합쳐 50,000자. 공백 정리와 구분 줄바꿈을 포함해 계산 |
| 첨부 추출문 | 첨부당 50,000자. 참고 첨부도 개별 한도와 첨부 JSON 한도 적용 |
| 생성·HITL 본문 | 각 본문 50,000자. 미팅의 딜별·공통·미지정 본문도 각각 적용하며 생성 전 빈 초안은 허용 |
| 제목·작성자 요청 | 제목 254자, 작성자 요청 2,000자 |
| 요청 JSON | `template_snapshot`·`content`·`attachments` 각각 직렬화한 UTF-8 기준 256KiB |
| 선택 출처 | 보고서·직접 활동을 합쳐 최대 100개 |

프론트는 인증된 `/api/report-attachments/limits`에서 현재 파일 용량 설정 두 값을 받아 적용한다. 파일 확장자·MIME·시그니처, 첨부 소유권·만료와 출처 권한·날짜·버전은 서버가 검사한다. OCR 서비스의 조건부 전송 한도는 별도이며, 모든 PDF의 업로드 한도로 취급하지 않는다.

기간 작성 단계에 있던 자료 128개·자료당 직렬화 60,000자·전체 입력 180,000자 제한은 제거했다. 요청 JSON 한도는 서버가 조회해 고정하는 하위 보고서 본문 전체에 적용하는 한도가 아니며, 모델의 컨텍스트 한도를 보장하는 수치도 아니다. 일일←미팅, 주간←일일, 월간←주간 참조와 검토 1회·필요 시 수정 1회 흐름은 유지한다. 사람이 수정한 문장은 AI로 다시 검증하지 않고 입력 형식·크기·권한과 확정 조건만 검사한다.

## 6. 시간 제한·스트리밍·로그

| 항목 | 설정 |
|---|---|
| LLM 요청 | 기본 180초. 기존 환경변수 값은 별도 확인 필요 |
| 내용분석 | 300초, 모델 24회, 추가 조회 8회 |
| 보고서작성 | 모델 요청마다 180초. 작성 후 검토 1회·필요 시 수정 1회, 단계별 오류 처리 |
| 미팅 전체 처리 | 1,200초 |
| 화면·SSE 대기 | 최대 25분 |
| 임시 생성 payload | 완료 뒤 24시간 복구, 확정 또는 만료 시 원문·CRM·AI 본문 제거 |

미팅 화면은 SSE로 실제 단계와 딜·공통·미지정 본문 미리보기를 표시한다. 수정본은 교체하며, 연결이 끊기면 같은 실행을 조회한다. 내부 추론을 노출하거나 새 실행을 자동 생성하지 않는다. 기간 보고서는 상태 조회와 최종 결과 반영 방식이다.

로그에는 실행 ID·딜 ID, 단계·오류 종류·발생 위치와 시간, 공급자가 반환한 토큰 사용량·종료 사유를 남긴다. 보고서의 위임 횟수나 로컬 근거 조회 횟수는 별도 계측하지 않는다. 누락 근거 ID·검증 위치·귀속 변경 전후도 기록하되 원문·응답 전체·도구 인자·키는 기록하지 않는다. 정확한 실패 문장은 로그에서 복원할 수 없다.

실행은 DB 큐, lease, heartbeat, lost-lease CAS로 관리한다. worker 재시작과 중복 선점은 이 경계에서 복구하며, LLM/검토 전체 제한시간은 재시도하지 않는다. 실제 연결·읽기 오류와 429·5xx만 제한적으로 재시도한다.

## 7. 검증과 후속 고도화

코드 검사는 작성 역할·근거 범위·Skill 적용·검토와 수정 횟수·출처 동결·권한·날짜·확정 충돌을 확인한다. 화면 검사는 조회 갱신 때 편집 내용과 생성 출처가 보존되는지, 미팅일이 복구되는지, 소제목과 연결 보고서가 표시되는지를 확인한다. 실제 문장 품질은 별도의 골든셋 평가로 구분한다.

2026-09-08의 상품 연결 골든셋 비교에서 단계별 참조 B는 53/53건을 생성했다. 직접 참조 C는 52/53건을 생성했고 월간 입력 199,604자가 당시 적용한 180,000자 제한을 넘어 LLM 호출 전에 실패했다. 이 제한은 현재 제거했지만 과거 평가 결과는 변경하지 않는다. 주간 생성 사용량은 B 114,911토큰, C 371,505토큰이었다. 이 기록을 근거로 기간 보고서의 단계별 참조를 선택했다. 원본·평가 파일은 로컬에 보관하며, 해당 수치는 최신 develop에 반영한 이번 PR 코드의 신규 전수 실행 결과가 아니다. Judge 오판과 순서 편향, 사람 교정 없이 자동 제출한 조건 때문에 누락 해소나 전체 품질 우열을 단정하지 않는다.

아래는 2026-08-31 미팅 중심 합성 실행의 과거 기준이다. 위 기간보고서 골든셋과 표본이 다르며, 이번 PR의 품질 재측정으로 해석하지 않는다.

이 과거 미팅 골든셋의 유료 실행은 `02e6c87`에 커밋된 구현 기준이다. 로컬 `golden-quality-v5-20260831-review1/manifest.json`의 소스 해시로 식별한다. `run.py --score`는 저장 결과만 재채점하며 `--run`은 유료 실행이다. **이번 리뷰 수정 후 모델 품질을 재측정한 결과는 아니다.**

표본은 C01·C08 각 1~4차, C03 1~3차, C10 4차의 12회 미팅·36딜로 고정했다. 모델 `gpt-5.6-luna`, 동시 실행 3개, 원문 구간 111개·필드 468개·필수 사실 46개다.

| 항목 | 결과 |
|---|---:|
| 근거 범위·딜 일치 | 94/111 = 84.7% |
| 특성 필드 정확도 | 350/468 = 74.8% |
| 13개 특성이 모두 맞은 딜 | 0/36 |
| 보고서 생성 | 12/12회, 36/36딜 성공 |
| 필수 사실 의미·귀속 보존 | 38/46 = 82.6% |
| 미팅당 평균 토큰 | 101,019 |
| 전체 지연 p50 / p95 | 56.1초 / 95.7초 |

필수 사실은 AI가 직접 비교한 의미 검수이며 사람의 확정 판정이 아니다. 동결 CRM·합성 이전 메모를 사용했고 DB 저장·화면까지의 전체 시험은 아니다. 표본은 무작위가 아니며 전체 성능으로 일반화하지 않는다. 원문·계정·실행 로그는 로컬에 보관하고 커밋하지 않는다.

검토 직전·직후 정확 일치는 87/111 → 93/111이다. 오답 8개를 고쳤으나 정답 2개가 바뀌었다(실제 의미 오류 1, 범주 표현 차이 1). 기존 추가조회에서 1개가 더 맞았다. 실행 간 지표 변화 전체를 검토의 인과효과로 해석하지 않는다.

남은 고도화:

1. 딜 전용 내용을 공통으로 확대하거나, 문맥상 후속 행동을 미지정으로 보내는 귀속 오류.
2. Unknown의 과잉 추정과 범주 경계. 대표 직함만으로 승인 권한을 확정하지 않는 등 판정 기준 구체화.
3. 검토가 모호한 내용을 특정 딜로 확정하지 않도록 변경 근거 기준 강화.
4. 과거 이력과 현재의 진전을 모순되게 쓰거나 불필요한 미확인 문장을 반복하는 보고서 품질.
5. 일일/주간/월간을 포함한 `원문글 → 최종글` 텍스트 표본의 후속 사람 품질 검사.
