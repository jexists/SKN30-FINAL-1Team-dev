# SalesLuv 미팅·보고서 에이전트 구조

기준일: 2026-08-31. 현재 구현과 확인된 한계를 정리한다. [구조도 HTML](./미팅_내용분석_보고서작성_에이전트_구조_보고서.html)에서 전체 흐름을 볼 수 있다.

## 1. 전체 흐름

~~~text
한 회사의 미팅 원문 + 선택 딜 N개
  ↓
입력 준비 [일반 코드]
  원문 구간·CRM·이전 보고서·수정 버전 고정
  ↓
내용분석 에이전트
  원문을 공통 / 딜별 / 미해결 / 범위 밖으로 분류
  필요하면 CRM 추가 조회 → 미해결 구간만 재분석
  ↓
공통 근거 장부
  ├─ 딜별 13개 특성 [구조화 LLM] → 로컬 ML → 참고 태그
  └─ 딜별 보고서 [Deep Agent] → 작성·검토·수정
  ↓
실행 결과 저장 → 보고서 초안에 반영 → 사용자가 수정·제출
  ├─ 해당 딜의 계약관리 파이프라인
  └─ 미팅 → 일일 → 주간 → 월간 보고서
~~~

업무 입력은 원문·회사·고객·선택 딜이다. 실제 화면은 연결된 딜별 Report 초안을 먼저 저장하고, 생성 버튼을 누르면 `report_ids`로 미팅 처리를 요청한다. 글자를 입력할 때마다 자동 호출하지 않는다.

내용분석은 미팅당 한 번, 보고서작성과 특성 생성은 그 뒤에 병렬로 실행한다. 보고서작성에 ML 결과를 사용하지 않는다. 전체 연결·저장·시간 제한을 맡는 미팅 처리 서비스는 Supervisor LLM이 아니라 일반 코드다.

## 2. 내용분석 에이전트

서버가 원문을 문장·줄바꿈 기준으로 나누고 ID와 문자 위치를 붙인다. LLM은 원문을 재작성하지 않고 각 구간의 귀속만 반환한다.

| 분류 | 의미 |
|---|---|
| `meeting_context` | 참석자·장소 등 미팅 배경 |
| `company_context` | 회사·고객의 공통 배경 |
| `all_selected_deals` | 모든 선택 딜에 적용된다고 명시한 내용 |
| `deal` | 지정된 딜 하나 또는 여러 개의 내용 |
| `unresolved` | 어느 딜인지 확인되지 않은 내용 |
| `out_of_scope` | 선택 딜·미팅 범위 밖의 내용 |

초기 입력에는 선택 딜의 이름·설명·제품·단계와 기본 CRM을 제공한다. 미해결 구간이 있으면 LangChain `create_agent`가 필요한 도구를 선택한다.

- `trade_history`: 같은 회사의 과거 완료 거래.
- `previous_reports`: 같은 딜의 이전 제출·승인 보고서.
- `product_details`: 선택 딜의 제품 상세.

같은 조회는 빈 결과도 캐시한다. 새 정보가 없으면 미해결 상태를 유지하고, 이미 분류된 구간은 추가 조회 단계에서 바꾸지 않는다. 구간 누락·중복·선택 밖 딜은 코드로 검증한다. 공통/딜별 의미가 올바른지는 이 형식 검사만으로 보장되지 않는다.

## 3. 특성 생성과 ML

딜별 근거·공통 배경·해당 딜 CRM으로 구조화 LLM을 한 번 호출한다. 확인되지 않은 값은 Unknown이다.

| 영역 | 특성 |
|---|---|
| 권한·구매 절차 | Authority, Purch_dept, Budgt_alloc, Forml_tend, RFP |
| 경쟁·의향·요구 | Competitors, Posit_statm, Scope, Needs_def |
| CRM·거래 관계 | Source, Client, Cross_sale, Deal_type |

Source는 고객 CRM의 여섯 코드(Referral, Event, Online form, Joint past, Media, Other)로 확정한다. 기본 이전 보고서 묶음은 특성 입력에서 제외하지만, 내용분석이 추가 조회한 해당 딜의 자료는 참고할 수 있다.

동시 처리는 최대 3딜이다. 특성 생성 뒤 최신 develop의 로컬 `deal_baseline.predict`를 호출한다. 한 딜의 ML 실패가 다른 딜을 중단시키지 않으며, 이미 생성한 특성은 보존한다. 모델 파일은 별도 배포 산출물이고 이 PR에 포함하지 않는다.

## 4. 보고서작성 Deep Agent

`deepagents==0.7.11`의 `create_deep_agent`를 사용한다. 모델이 계획을 세우고, 근거를 읽고, 필요하면 딜별 초안 작성을 위임한다. 위임은 선택 사항이다.

| 구성 | 역할 |
|---|---|
| 주 작성자 | 딜별 줄글과 공통·미지정 본문 조립 |
| `read_meeting_evidence` | 고정된 원문 근거·CRM·같은 딜의 이전 보고서 조회 |
| `task` | 필요한 딜의 초안 작성을 하위 작성자에게 위임 |
| `review_report` | 구조 검사 후 별도 LLM 의미 검토 |
| 작성 스킬 | 사실·주체·부정·조건·시점을 보존하는 작성 기준 |

~~~text
근거 확인·계획 → 필요 시 딜별 위임 → 초안
  ↓
구조 검사: 딜·근거 ID·미지정 원문 인용
  ↓
의미 검토: 사실 왜곡·누락·딜 혼입
  ├─ 오류 → 위치·누락 근거·수정 행동을 전달 → 재작성
  └─ 통과 → 같은 초안 반환
~~~

검토 없이 종료한 출력은 최종 검사에서 거부한다. 검토자도 같은 모델을 쓰므로 독립 정답 판정을 대신하지 않는다. 임의 웹 검색·셸 실행·DB 수정 도구는 없고, 메모는 가상 파일의 `/scratch/`에만 쓴다.

보고서는 세 부분으로 반환한다.

- `deal_reports[]`: 딜별 본문과 근거 ID.
- `common_report`: 공통 본문. 한 번 작성하고 모든 딜 보고서에 함께 보관·전달.
- `unassigned_report`: 미해결·범위 밖 원문을 그대로 인용한 확인 필요 내용.

사용자는 미지정 구간의 딜을 지정해 후속 작업을 다시 실행할 수 있다. 과거 보고서는 같은 딜의 최근 5건, 본문 최대 8,000자씩 읽으며, 미팅·생성·수정 시점이 모두 이번 미팅 이전인 자료로 제한한다. 과거 약속의 이행은 이번 원문에 근거가 있을 때만 서술하도록 한다.

## 5. 저장·화면·기간 보고서

- 실행 완료 후 `/agent-runs/{id}/apply`로 여러 딜 초안을 함께 반영한다. 사람이 편집한 본문은 보존하고 버전 충돌을 검사한다.
- 공통·미지정 본문 수정은 전용 API로 해당 미팅의 딜 보고서 전체에 원자적으로 반영한다.
- 실행 상태가 completed여도 일부 보고서·ML이 실패할 수 있다. `errors`와 딜별 오류까지 확인한다.
- 미팅 보고서를 제출하면 해당 딜 계약관리 파이프라인을 큐잉한다. 생성·임시저장이 계약 확정을 뜻하지 않는다.
- 일일·주간·월간은 사용자의 생성 요청으로 실행한다. 각각 미팅·일일·주간 보고서를 읽는 공통 기간 Deep Agent를 사용한다.
- 새 일일보고서는 줄글 본문 하나다. ‘내일 계획’을 강제로 만들지 않는다. 기존 다중 필드 양식도 지원한다.
- 기간 보고서는 제출·승인된 하위 자료의 권한·기간을 검사하고, 미팅별 공통 내용을 중복 없이 종합한다. 월 경계의 사실을 분리할 근거가 없으면 월 전체 실적으로 단정하지 않는다.

## 6. 시간 제한·스트리밍·로그

| 항목 | 설정 |
|---|---|
| LLM 요청 | 기본 180초. 기존 환경변수 값은 별도 확인 필요 |
| 내용분석 | 300초, 모델 24회, 추가 조회 8회 |
| 보고서작성 | 900초, 모델 호출 예산 100회, 검토 10회 |
| 미팅 전체 처리 | 1,200초 |
| 화면·SSE 대기 | 최대 25분 |

미팅 화면은 SSE로 실제 단계와 딜·공통·미지정 본문 미리보기를 표시한다. 수정본은 교체하며, 연결이 끊기면 같은 실행을 조회한다. 내부 추론을 노출하거나 새 실행을 자동 생성하지 않는다. 기간 보고서는 상태 조회와 최종 결과 반영 방식이다.

로그에는 실행 ID·딜 ID, 단계·오류 종류·발생 위치, 시간·호출·검토 한도, 공급자가 반환한 토큰 사용량을 남긴다. 원문·응답 전체·키는 기록하지 않는다. 따라서 실패한 초안의 정확한 문장·근거 ID를 복원하는 상세 추적은 아직 부족하다.

현재 실행과 미리보기는 FastAPI 프로세스 안에서 관리한다. 영속 작업 큐·다중 worker 간 공유·재시작 복구는 이번 범위가 아니다.

## 7. 검증과 후속 고도화

기능 검사:

- 백엔드: **675 passed / 8 skipped**. 실제 LLM 5건·DB 연동 3건은 기본 검사에서 제외.
- 프론트: **19개 테스트**, 타입·린트·포맷·빌드 통과. JS 청크 크기 경고는 남아 있음.
- 브라우저 HTML 회귀 테스트 2개는 이번 PR 준비 중 재실행하지 않았다.
- 실제 ML 파일의 로딩·계약 검사와 예측 확인. 모델 파일은 Git 제외.

합성 골든셋 12회 미팅·36딜 표본의 실제 호출 결과:

| 항목 | 결과 |
|---|---:|
| 근거 범위·딜 일치 | 84/111 = 75.7% |
| 특성 필드 정확도 | 342/468 = 73.1% |
| 13개 특성이 모두 맞은 딜 | 0/36 |
| 보고서 생성 | 11/12회 성공 |
| 필수 사실 의미·귀속 보존 | 30/46 = 65.2% |
| 미팅당 평균 토큰 | 103,077 |
| 전체 지연 p50 / p95 | 55.5초 / 122.0초 |

필수 사실은 AI가 직접 비교한 의미 검수이며 사람의 확정 판정이 아니다. 동결 CRM·합성 이전 메모를 사용했고 DB 저장·화면까지의 전체 시험은 아니다. 표본은 무작위가 아니며 전체 성능으로 일반화하지 않는다. 원문·계정·실행 로그는 로컬에 보관하고 커밋하지 않는다.

후속 브랜치에서 다룰 문제:

1. 딜 전용 내용을 공통으로 확대하거나, 문맥상 후속 행동을 미지정으로 보내는 귀속 오류.
2. Unknown의 과잉 추정과 범주 경계. 대표 직함만으로 승인 권한을 확정하지 않는 등 판정 기준 구체화.
3. 검토 미통과 조기 종료, 같은 오류 반복, 실패 초안의 안전한 진단 기록.
4. 과거 이력과 현재의 진전을 모순되게 쓰거나 불필요한 미확인 문장을 반복하는 보고서 품질.
5. 전체 골든셋·반복 실행·누적 생성 이력·일일/주간/월간의 실제 품질 검증.
6. 정적 검토에서 발견한 미팅 전환 시 공통 메모 dirty 상태와 늦은 저장 응답 처리. 브라우저 재현 후 회귀 검사 필요.
