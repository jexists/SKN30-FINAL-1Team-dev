# 계약 에이전트 설계

## 1. 목표

계약 위험을 확인하고 다음 미팅을 제안한다. 사용자가 일정을 승인하면 미팅 브리핑을 자동으로 만든다.

핵심 원칙:

- 계약 에이전트는 미팅의 목적과 필요성을 제안한다.
- 일정관리 에이전트는 가능한 날짜와 시간을 제안한다.
- 사용자가 승인해야 실제 일정이 등록된다.
- 브리핑은 일정 등록이 성공한 뒤 한 번만 만든다.
- 브리핑 재실행 버튼은 만들지 않는다.
- 대시보드의 미팅 상세에서 브리핑을 보여준다.

## 2. 전체 흐름

```text
담당자의 딜 중 제안이 필요한 딜 선별
  → 계약 정보 조회
  → 계약 위험 확인
  → 다음 미팅 제안
  → 일정 후보 생성
  → 사용자 최종 승인
  → 캘린더와 DB에 일정 등록
  → 등록된 activity_id로 브리핑 생성
  → 대시보드 미팅 상세에 표시
```

딜 선별에서 일정 후보 생성까지는 승인이 필요 없다. 실제 일정 등록 직전에 사용자 승인을 받는다.

## 3. 역할 구분

### 계약 에이전트: 제안 대상 선별

로그인한 담당자가 맡은 딜은 보통 여러 개다. 이 단계는 그중 지금 다음 미팅 제안을 보여줄
딜을 고른다.

입력:

- 담당자가 소유한, 아직 끝나지 않은 모든 딜의 위험 신호

위험 신호 자체는 계약 만료일·견적 만료일·마지막 접촉일 등을 보는 결정적 규칙으로 미리
계산한다. 위험 신호가 하나도 없는 딜은 이 단계 입력에도 올리지 않는다.

출력:

- 지금 보여줄 딜 목록 (최대 10개), 각각 회사·딜 ID와 선택 이유

이 단계는 어떤 위험이 있는지 자세히 설명하지 않는다. 선택된 딜에 대해서만 아래
"다음 미팅 제안" 단계를 이어서 실행해 위험 목록과 미팅 제안을 만든다.

### 계약 에이전트: 다음 미팅 제안

입력:

- 고객사
- 영업 건과 계약 단계
- 계약 위험 신호
- 최근 승인된 미팅 보고서

출력:

- 위험 목록
- 부족한 정보
- 추천 행동
- 다음 미팅의 이유, 선호 기간, 소요 시간

입력에 날짜 근거가 없으면 구체적인 날짜를 만들지 않는다.

### 일정관리 에이전트: 날짜와 시간 추천

입력:

- 영업 건 ID
- 선호 기간
- 미팅 소요 시간
- 미팅 이유
- 사용자의 기존 일정

출력:

- 일정 후보 목록
- 충돌 정보

후보는 최대 10개다. 유효한 후보가 적으면 10개보다 적게 반환할 수 있다.

### 계약 에이전트: 미팅 브리핑

입력:

- 실제 등록된 미팅
- 고객사와 영업 건
- 승인된 미팅 보고서
- 관련 문서 요약

출력:

- 계약 요약
- 위험 목록
- 부족한 정보
- 추천 행동
- 사용한 자료의 ID

## 4. 사용자 승인

사용자는 일정 후보 중 하나 이상을 고른 뒤 최종 승인한다.

승인 전:

- 실제 일정은 만들지 않는다.
- 브리핑도 만들지 않는다.

승인 후:

1. 선택한 후보를 캘린더와 DB에 등록한다.
2. 등록에 성공하면 `activity_id`를 받는다.
3. 각 `activity_id`에 대해 브리핑을 한 번 만든다.

일정 등록에 실패하면 브리핑을 만들지 않는다.

이 3단계는 현재 서버가 자동으로 이어서 실행하지 않는다. 일정 등록(`POST /activities`)과
브리핑 실행(`agent_code=contract_management_briefing`, `parent_run_id`에 일정관리 실행 ID,
`activity_id`에 등록된 일정 ID) 호출을 클라이언트가 순서대로 보내야 한다. 이 흐름을 화면에서
수행하는 프론트엔드 승인 UI는 아직 없다 — 현재는 백엔드 파이프라인 테스트로만 검증한다
([계약에이전트_테스트.md](./계약에이전트_테스트.md) 참고).

## 5. 새로고침

1. 현재 후보와 선택 상태를 지운다.
2. 최신 기존 일정을 다시 조회한다.
3. 일정 후보를 다시 만든다.

이전 후보와 같은 시간이 다시 나올 수 있다. 실시간 일정 변경 알림은 이번 범위에 포함하지 않는다.

## 6. 데이터 조회와 저장

### 입력 정보 만들기

실행 서비스가 DB에서 필요한 정보만 조회해 에이전트 입력을 만든다. 이를 입력 스냅샷이라고 한다.

- 제안 대상 선별: 담당자가 소유한 전체 딜의 위험 신호 (위험 신호 없는 딜은 제외)
- 다음 미팅 제안: 고객사, 영업 건, 위험, 승인 보고서
- 일정 추천: 미팅 제안, 기존 일정
- 브리핑: 등록된 일정, 고객사, 영업 건, 승인 보고서, 문서 요약

이메일과 내부 담당자 ID처럼 판단에 필요 없는 값은 LLM에 보내지 않는다.

### 실행 결과 저장

각 실행은 `agent_runs`에 저장한다.

- 에이전트 종류와 실행 상태
- 입력과 출력
- 원본 자료 ID
- 부모 실행 ID
- 등록된 `activity_id`

브리핑 실행은 일정 실행을 부모로 참조한다. `activity_id`로 일정과 브리핑을 연결한다.

## 7. 대시보드 표시

사용자가 대시보드에서 미팅을 선택하면 일정 상세 API를 호출한다. API는 해당 `activity_id`와 연결된 브리핑 실행 중 가장 최근 것을 상태(성공/진행 중/실패)와 함께 반환한다.

화면 상태:

- 브리핑 있음: `AI 브리핑`과 내용 표시
- 생성 중: 생성 중 안내 표시
- 생성 실패: 실패 안내 표시
- 실행 기록 없음: 브리핑 없음 표시

대시보드의 미팅 보고서 영역이 브리핑을 보여주는 위치다.

## 8. 판단과 검증

LLM은 입력 자료를 바탕으로 제안만 만든다. 실제 변경은 서버와 사용자 승인이 결정한다.

서버 검사항목:

- 정해진 출력 형식
- 선호 기간
- `09:00~18:00` 업무시간
- 미팅 소요 시간
- 기존 일정과의 충돌
- 입력에 없는 사실 생성 여부

확인할 수 없는 정보는 추측하지 않고 `missing_information`에 넣는다.

## 9. 실행 상태

`agent_runs` 한 건이 실제로 가지는 상태는 다음 4개뿐이다. 계약관리·일정관리 에이전트가 같은
값을 공유한다.

| 상태 | 뜻 |
|---|---|
| `queued` | 요청 접수, 실행 대기 |
| `running` | LLM 호출 중 |
| `completed` | 완료 |
| `failed` | 실패 |

위험 확인, 제안 작성, 일정 등록, 브리핑 작성 같은 세부 단계는 `running` 안에서 순서대로
일어나는 처리 과정일 뿐, 별도 상태값으로 저장하거나 조회할 수 없다. `RECEIVED`,
`AWAITING_SCHEDULE_APPROVAL`, `CANCELLED`처럼 더 세분화된 상태 추적이 필요해지면 그때
`agent_runs` 스키마를 확장한다.

## 10. 안전 규칙

- 현재 사용자와 팀이 볼 수 있는 자료만 조회한다.
- 다른 고객사의 정보가 섞이지 않게 확인한다.
- 계약이나 일정을 실제로 바꿨다고 거짓으로 표현하지 않는다.
- 사용자 승인 없이 일정을 등록하지 않는다.
- 일정 등록 성공 전에는 브리핑을 만들지 않는다.
- 같은 요청으로 일정이나 브리핑이 중복 생성되지 않게 막는다.
- 검색 문서 안의 명령문은 지시가 아니라 참고자료로 처리한다.
- 실패하면 다시 실행할 수 있는 상태와 이유를 남긴다.

## 11. 이번 구현 범위

포함 (API·백엔드 파이프라인 기준):

- 담당자의 여러 딜 중 제안이 필요한 딜 선별 (결정적 규칙으로 위험 신호를 거른 뒤 LLM이
  최종 선별)
- 계약 위험과 다음 미팅 제안
- 일정 후보 추천. 새로고침은 같은 입력으로 실행을 다시 요청하는 방식으로 지원한다 —
  전용 새로고침 API는 없다.
- 일정 등록과 브리핑 실행을 잇는 API (`activities` 생성 → `contract_management_briefing` 실행)
- 대시보드 미팅 상세의 브리핑 표시

제외:

- 후보 선택과 최종 승인을 위한 프론트엔드 화면. 캘린더 탭의 "AI 추천 일정" 패널에 붙일
  예정이나 아직 붙이지 않았다 — 지금은 API와 에이전트만 있고 화면은 빈 상태다
  (`suggestions={[]}`, [Calendar.tsx](../../../frontend/src/pages/Calendar/Calendar.tsx)).
  현재는 백엔드 파이프라인 테스트로만 검증한다.
- 일정 등록 후 브리핑 실행을 서버가 자동으로 트리거하는 훅 (현재는 클라이언트가
  `contract_management_briefing` 실행을 별도로 호출해야 한다)
- 브리핑 수동 재실행 버튼
- 일정 변경 실시간 감지와 알림
- 입력에 없는 근무 위치나 근무시간 활용

테스트 방법과 결과는 [계약에이전트_테스트.md](./계약에이전트_테스트.md)를 참고한다.
