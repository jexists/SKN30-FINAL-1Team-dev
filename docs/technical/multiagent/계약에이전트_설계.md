# 계약 에이전트 설계

## 1. 목표

계약 위험을 확인하고 다음 미팅을 제안한다. 사용자가 일정을 승인하면 미팅 브리핑을 자동으로 만든다.

핵심 원칙:

- 제안은 트리거가 걸린 시점에 서버가 미리 계산해 저장한다. 캘린더는 저장된 결과만
  조회하므로 화면에서 LLM을 기다리지 않는다.
- 계약 에이전트는 미팅의 목적과 필요성을 제안한다.
- 일정관리 에이전트는 가능한 날짜와 시간을 제안한다.
- 사용자가 승인해야 실제 일정이 등록된다.
- 브리핑은 일정 등록이 성공한 뒤 한 번만 만든다.
- 브리핑 재실행 버튼은 만들지 않는다.
- 대시보드의 미팅 상세에서 브리핑을 보여준다.

## 2. 전체 흐름

```text
트리거 발생 (보고서 확정 · 일정 수동 등록 · 영업 딜 생성/단계 이동 · CS 처리 시작)
  → [백그라운드] 계약 정보 조회 → 계약 위험 확인 → 다음 미팅 제안
  → [백그라운드] 일정 후보 생성
  → contract_next_meeting_suggestion 에 저장
        ⋮  (사용자가 캘린더를 열 때)
  → GET /contract-next-meeting-suggestions 로 조회 (LLM 호출 없음)
  → 사용자 최종 승인
  → 캘린더와 DB에 일정 등록
  → 등록된 activity_id로 브리핑 생성
  → 미팅 상세에 표시
```

트리거부터 저장까지는 승인이 필요 없고 사용자를 기다리게 하지도 않는다. 실제 일정 등록
직전에만 사용자 승인을 받는다.

트리거는 네 가지다. 모두 영업 건 하나를 정확히 가리킨다.

| 트리거 | 접점 | 무엇을 뜻하는가 |
|---|---|---|
| 보고서 확정 | `POST /reports/{id}/submit` | 작성자가 미팅 기록을 확정했다 — 새 근거가 생겼다 |
| 일정 수동 등록 | `POST /activities` (AI 추천을 거치지 않은 등록) | 이 딜이 추천 체인을 한 번도 안 거쳤을 수 있다 |
| 영업 딜 생성·단계 이동 | `POST /sales-deals`, `POST /sales-deals/{id}/move` | 딜의 상태가 달라졌다 |
| CS 처리 시작 | `POST /support-requests/{id}/transition` (→ `in_progress`) | 미해결 C/S 위험 신호와 같은 조건이다 |

트리거 한 번이 LLM 호출 두 번이라, 같은 딜에 대해 10분 안에는 다시 돌리지 않는다
(`contract_next_meeting_pipeline._COOLDOWN`). 진행 중인 실행이 있으면 시각과 무관하게
막는다.

## 3. 역할 구분

### 계약 에이전트: 제안 대상 선별

> **캘린더 패널은 이 단계를 쓰지 않는다.** 네 트리거가 모두 영업 건 하나를 정확히
> 가리키므로, 선계산 파이프라인은 딜을 비교·랭킹하지 않고 바로 "다음 미팅 제안"부터
> 시작한다. 이 단계는 `POST /agent-runs`(`contract_management_select_candidates`)로 여전히
> 실행할 수 있고, 기존 딜을 한 번에 채우는 백필 스크립트가 대상을 고를 때 같은 규칙을 쓴다
> (`backend/scripts/backfill_contract_next_meeting_suggestions.py`).

로그인한 담당자가 맡은 딜은 보통 여러 개다. 이 단계는 그중 지금 다음 미팅 제안을 보여줄
딜을 고른다.

입력:

- 담당자가 소유한, 아직 끝나지 않은 모든 딜의 영업 단계(stage_code)와 위험 신호

위험 신호 자체는 계약 만료일·견적 만료일·마지막 접촉일 등을 보는 결정적 규칙으로 미리
계산한다. 위험 신호가 하나도 없는 딜은 이 단계 입력에도 올리지 않는다.

출력:

- 지금 보여줄 딜 목록 (최대 10개), 각각 회사·딜 ID·우선순위(priority, 1이 가장 시급)·선택 이유

이 단계는 어떤 위험이 있는지 자세히 설명하지 않는다. 선택된 딜에 대해서만 아래
"다음 미팅 제안" 단계를 이어서 실행해 위험 목록과 미팅 제안을 만든다.

**우선순위 기준**: priority 값은 LLM이 판단하되, 프롬프트에 아래 두 기준을 순서대로 명시한다.

| 순위 | 기준 | 상세 |
|---|---|---|
| 1 | 영업 단계 | 니즈 검증 < 제품 시연 평가 < 견적서 발송 < 계약서 발송 < 계약서 검토 < 계약 완료 순으로 뒤일수록 우선. 표에 없는 단계(발주 진행, 납품 완료)는 이 기준 대신 위험 심각도·신호 개수·마감 임박으로 판단 |
| 2 (동률일 때만) | 재방문 필요 신호 | 계약 체결일로부터 7일 경과 시 발생(`contract_revisit_due`, severity=medium), 14일 경과 시 severity=high로 상승. 이 신호가 있는 딜을 우선 |

이 두 기준은 "1차: 다음 미팅 제안" 단계에는 넣지 않는다 — 그 단계는 이미 회사 하나로 좁혀진
뒤라 LLM이 전체 맥락을 보고 위험 판정·미팅 필요성을 종합 판단하면 충분하다.

### 계약 에이전트: 다음 미팅 제안

입력:

- 고객사
- 영업 건과 계약 단계
- 계약 위험 신호
- 최근 확정된 업무 보고서

출력:

- 위험 목록
- 부족한 정보
- 추천 행동
- 다음 미팅의 이유, 선호 기간, 소요 시간

입력에 날짜 근거가 없으면 구체적인 날짜를 만들지 않는다.

### 일정관리 에이전트: 날짜와 시간 추천

입력:

- 영업 건 ID
- 선호 기간
- 미팅 소요 시간
- 미팅 이유
- 사용자의 기존 일정

출력:

- 일정 후보 목록
- 충돌 정보

후보는 최대 10개다. 유효한 후보가 적으면 10개보다 적게 반환할 수 있다.

### 계약 에이전트: 미팅 브리핑

입력:

- 실제 등록된 미팅
- 고객사와 영업 건
- 확정된 업무 보고서
- 관련 문서 요약

출력:

- 계약 요약
- 위험 목록
- 부족한 정보
- 추천 행동
- 사용한 자료의 ID

## 4. 사용자 승인

사용자는 일정 후보 중 하나 이상을 고른 뒤 최종 승인한다.

승인 전:

- 실제 일정은 만들지 않는다.
- 브리핑도 만들지 않는다.

승인 후:

1. 선택한 후보를 캘린더와 DB에 등록한다.
2. 등록에 성공하면 `activity_id`를 받는다.
3. 각 `activity_id`에 대해 브리핑을 한 번 만든다.

일정 등록에 실패하면 브리핑을 만들지 않는다.

2단계와 3단계는 서버가 이어서 실행한다. 클라이언트는 `POST /activities` 요청 본문에
`schedule_management_run_id`(승인한 후보를 만든 일정관리 실행 ID)만 실어 보내면 된다. 이 값이
있으면 서버가 일정 등록 커밋 직후 같은 요청 안에서 `contract_management_briefing` 실행을
큐잉하고, `activity_id`와 `parent_run_id`는 서버가 채운다. 값을 비우면(수동으로 만든 일정 등)
브리핑을 큐잉하지 않는다.

브리핑 큐잉은 일정 등록과 같은 트랜잭션이 아니다 — 일정 등록은 이미 커밋된 뒤 시도하므로,
큐잉이 실패해도(예: `schedule_management_run_id`가 없거나 이미 완료되지 않은 실행) 일정 등록
자체는 되돌리지 않는다. 이때 응답의 `briefing_queue_warning` 필드에 실패 사유를 담아 `201`로
그대로 응답한다. 클라이언트는 이 필드가 있으면 사용자에게 "브리핑 생성에 실패했다"는 안내만
보여주면 되고, 별도로 재시도할 방법은 아직 없다(브리핑 수동 재실행 버튼은 11장 참고).

이 흐름을 화면에서 수행하는 곳은 캘린더의 "AI 추천 일정" 패널이다
([SuggestionPanel](../../../frontend/src/pages/Calendar/components/SuggestionPanel/SuggestionPanel.tsx)).
카드의 "추천일에 넣기"를 누르거나 카드를 달력 칸에 끌어다 놓으면 승인이다 — 끌어다 놓은
경우 그 날짜로 덮어쓴다.

## 5. 목록이 갱신되는 시점

새로고침 버튼은 두지 않는다. 목록은 두 시점에만 달라진다.

1. **캘린더 화면에 들어올 때** — `GET /contract-next-meeting-suggestions` 를 한 번 호출해
   저장된 제안을 그대로 그린다. LLM 호출이 없다.
2. **트리거가 걸릴 때** — 서버가 백그라운드로 다시 계산해 그 딜의 행을 덮어쓴다. 사용자는
   다음에 캘린더에 들어올 때 새 값을 본다.

카드를 닫으면(X) 서버 상태가 `dismissed` 가 되어 다시 들어와도 뜨지 않는다. 다만 그 딜에
새 트리거가 걸리면 `pending` 으로 되돌아 다시 올라온다 — 딜에 변화가 생겼다는 건 새로
판단할 근거가 생겼다는 뜻이기 때문이다. 실시간 일정 변경 알림은 이번 범위에 포함하지 않는다.

## 6. 데이터 조회와 저장

### 입력 정보 만들기

실행 서비스가 DB에서 필요한 정보만 조회해 에이전트 입력을 만든다. 이를 입력 스냅샷이라고 한다.

- 제안 대상 선별: 담당자가 소유한 전체 딜의 위험 신호 (위험 신호 없는 딜은 제외)
- 다음 미팅 제안: 고객사, 영업 건, 위험, 확정된 보고서
- 일정 추천: 미팅 제안, 기존 일정
- 브리핑: 등록된 일정, 고객사, 영업 건, 확정된 보고서, 문서 요약

"확정된 보고서"는 `status_code` 가 `submitted` 이거나 `approved` 인 보고서다. 작성자가
확정하면 `submitted` 이고, 그 뒤 팀장 검토까지 끝나야 `approved` 가 된다. 그런데 그 검토
화면이 아직 없어 `approved` 만 보면 방금 확정한 보고서가 영영 입력에 들어오지 못한다 —
보고서 확정이 곧 이 파이프라인의 트리거이므로 두 상태를 함께 본다
(`contract_schedule_snapshots._recent_finalized_reports`).

이메일과 내부 담당자 ID처럼 판단에 필요 없는 값은 LLM에 보내지 않는다.

### 제안 상태 저장

캘린더가 "지금 이 딜에 보여줄 제안이 있는지"를 읽는 곳은 `contract_next_meeting_suggestion`
표다. 딜 하나에 활성 제안은 최대 하나이고(`sales_deal_id` UNIQUE), 날짜·시간·사유 같은 실제
내용은 여기 복제하지 않는다 — `schedule_management_run_id` 로 `agent_run.output_snapshot` 을
그대로 조회한다.

- `pending`: 캘린더에 보여줄 제안
- `dismissed`: 사용자가 카드를 닫았다. 다음 트리거가 오면 `pending` 으로 되돌아온다
- `accepted`: 이 제안을 승인해 일정으로 등록했다

### 실행 결과 저장

각 실행은 `agent_runs`에 저장한다.

- 에이전트 종류와 실행 상태
- 입력과 출력
- 원본 자료 ID
- 부모 실행 ID
- 등록된 `activity_id`

브리핑 실행은 `activity_id`로 일정과 연결한다. AI 제안(일정관리 실행)을 승인해서 만든
일정이면 그 실행을 부모로도 참조하지만, 캘린더 직접 입력이나 팀장 대리 입력처럼 AI 제안을
거치지 않은 일정은 부모 없이 `activity_id`만으로 브리핑을 만든다 — 브리핑 내용 자체는
`activity_id`에서 회사·연락처·미팅 정보를 직접 조회해 만들어서 부모 실행이 없어도 된다.

## 7. 미팅 상세 표시

사용자가 대시보드나 캘린더에서 일정을 클릭하면 미팅 상세 드로어가 열리고, 그 자리에서 일정 상세
API(`GET /activities/{id}`)를 호출한다. API는 해당 `activity_id`와 연결된 브리핑 실행 중
가장 최근 것을 상태(성공/진행 중/실패)와 함께 반환한다.

**버튼 없이, 처음 열 때만 생성한다.** 이 실행 기록이 없고(`ai_briefing`이 비어 있고) 그
일정이 미팅이면서 연락처가 연결돼 있으면, 드로어를 여는 그 순간 자동으로 브리핑 생성을
요청한다. 이미 만들어져 있으면(다른 사람이 먼저 열어봤거나 AI 추천 승인 때 자동 생성됐거나)
다시 만들지 않고 그 결과를 그대로 보여준다 — 브리핑 재실행 버튼은 만들지 않으므로, 한 번
생성되면 다른 곳을 봤다 돌아와도 내용이 바뀌지 않는다.

화면 상태:

- 브리핑 있음: `AI 브리핑`과 내용 표시
- 생성 중(방금 자동 요청했거나 이미 다른 사람이 요청해 진행 중): 생성 중 안내 표시
- 생성 실패: 실패 안내 표시
- 미팅이 아니거나 연락처가 연결돼 있지 않아 만들 수 없음: 이 경우는 애초에 생성을
  요청하지 않는다

미팅 상세 드로어(대시보드)가 브리핑을 보여주는 위치다. "업무 보고서" 작성 화면(사람이 쓰는
보고서, `report_writing` 에이전트의 "AI 원본"과는 다른 화면)과는 별개다.

## 8. 판단과 검증

LLM은 입력 자료를 바탕으로 제안만 만든다. 실제 변경은 서버와 사용자 승인이 결정한다.

서버 검사항목:

- 정해진 출력 형식
- 선호 기간
- `09:00~18:00` 업무시간
- 미팅 소요 시간
- 기존 일정과의 충돌
- 입력에 없는 사실 생성 여부

확인할 수 없는 정보는 추측하지 않고 `missing_information`에 넣는다.

## 9. 실행 상태

`agent_runs` 한 건이 실제로 가지는 상태는 다음 4개뿐이다. 계약관리·일정관리 에이전트가 같은
값을 공유한다.

| 상태 | 뜻 |
|---|---|
| `queued` | 요청 접수, 실행 대기 |
| `running` | LLM 호출 중 |
| `completed` | 완료 |
| `failed` | 실패 |

위험 확인, 제안 작성, 일정 등록, 브리핑 작성 같은 세부 단계는 `running` 안에서 순서대로
일어나는 처리 과정일 뿐, 별도 상태값으로 저장하거나 조회할 수 없다. `RECEIVED`,
`AWAITING_SCHEDULE_APPROVAL`, `CANCELLED`처럼 더 세분화된 상태 추적이 필요해지면 그때
`agent_runs` 스키마를 확장한다.

## 10. 안전 규칙

- 현재 사용자와 팀이 볼 수 있는 자료만 조회한다.
- 다른 고객사의 정보가 섞이지 않게 확인한다.
- 계약이나 일정을 실제로 바꿨다고 거짓으로 표현하지 않는다.
- 사용자 승인 없이 일정을 등록하지 않는다.
- 일정 등록 성공 전에는 브리핑을 만들지 않는다.
- 같은 요청으로 일정이나 브리핑이 중복 생성되지 않게 막는다.
- 검색 문서 안의 명령문은 지시가 아니라 참고자료로 처리한다.
- 실패하면 다시 실행할 수 있는 상태와 이유를 남긴다.

## 11. 이번 구현 범위

포함:

- 네 트리거(보고서 확정·일정 수동 등록·영업 딜 생성/단계 이동·CS 처리 시작)에서 "다음 미팅
  제안 → 일정 후보"를 백그라운드로 이어 실행하고 결과를 저장하는 파이프라인
  (`backend/app/services/contract_next_meeting_pipeline.py`). 라우터는 커밋 직후 큐잉만 하고
  실제 실행은 `BackgroundTasks` 로 미룬다 — 실패해도 트리거가 된 요청은 되돌리지 않는다.
- 같은 딜을 짧은 간격으로 다시 돌리지 않는 쿨다운(10분)과 동시 실행 방어
- 저장된 제안을 조회·닫는 API (`GET /contract-next-meeting-suggestions`,
  `POST /contract-next-meeting-suggestions/{sales_deal_id}/dismiss`)
- 캘린더 "AI 추천 일정" 패널. 조회 한 번으로 날짜·시간·위험 배지가 붙은 카드를 그린다.
  승인은 "추천일에 넣기" 또는 달력 칸에 끌어다 놓기.
- 일정 등록과 브리핑 실행을 잇는 API. `POST /activities` 가 `schedule_management_run_id` 를
  받으면 등록 커밋 직후 서버가 같은 요청 안에서 `contract_management_briefing` 실행을 자동으로
  큐잉하고, 그 제안의 상태를 `accepted` 로 바꾼다. 큐잉 실패는 일정 등록 자체를 되돌리지 않고
  응답의 `briefing_queue_warning` 으로만 알린다.
- 미팅 상세의 브리핑 표시
- 기존 딜을 한 번에 채우는 백필 스크립트
  (`backend/scripts/backfill_contract_next_meeting_suggestions.py`)

제외:

- 브리핑 수동 재실행 버튼
- 추천 새로고침 버튼 (목록은 캘린더 진입과 트리거 때만 갱신된다, 5장 참고)
- 일정 변경 실시간 감지와 알림
- 입력에 없는 근무 위치나 근무시간 활용

## 12. 향후 고도화

- **브리핑에 이전 실행 이력 표시**: `contract_management_briefing` 실행은 `parent_run_id`로
  자신을 만든 `schedule_management` 실행을, 그 실행은 다시 자신의 `parent_run_id`로
  `contract_management_next_meeting` 실행을 가리킨다. 이 체인을 따라가며 "왜 이 시간을
  골랐는지"(일정 후보 사유), "왜 이 미팅을 제안했는지"(1차 제안 사유)를 브리핑과 함께
  보여주면, 사용자가 `agent_runs`를 직접 뒤지지 않아도 판단 근거를 볼 수 있다.
  `parent_run_id`가 없는 브리핑(캘린더 직접 입력, 팀장 대리 입력 등 AI 제안을 거치지 않은
  일정)은 이력이 없으므로 빈 목록으로 둔다.
  - 지금은 `contract_management_next_meeting` 실행이 자신을 만든 0차 선별
    (`contract_management_select_candidates`) 실행을 부모로 기록하지 않는다
    ([agent_runs.py:139-148](../../../backend/app/services/agent_runs.py#L139-L148)). 그래서
    위 체인을 그대로 구현해도 "애초에 왜 이 딜을 선별했는지"(0차 선별 사유)까지는 이어지지
    않는다 — 이것까지 보여주려면 0차 선별 실행도 부모로 기록하도록 별도로 연결해야 한다.
  - `GET /agent-runs/{id}` 응답에도 지금은 `parent_run_id`가 없어(`AgentRunRead` 스키마에
    미포함) 이 체인을 프론트엔드가 따라갈 방법이 없다. 구현하려면 이 필드부터 노출해야 한다.

테스트 방법과 결과는 [계약에이전트_테스트.md](./계약에이전트_테스트.md)를 참고한다.
