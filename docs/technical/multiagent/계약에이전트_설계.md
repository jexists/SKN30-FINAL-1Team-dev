# 계약 에이전트 설계

## 목표(Goal)

회사별 영업·계약 및 C/S 활동의 히스토리를 일관되게 관리하고, 변경된 정보를 바탕으로 다음 행동을 지원한다.

- 신규 딜, 계약 단계 변경, 성사·갱신·만료 이력 관리
- C/S 요청, 처리 상태, 담당자 및 대응 이력 관리
- 완성된 미팅 보고서의 핵심 내용 반영
- 계약 만료, 납품, 장기 미접촉 등 위험 판정
- 계약 단계와 후속 조치에 적합한 다음 미팅 일정 제안
- 사용자가 승인한 다음 일정이 돌아오면 회사와 계약의 최신 상황을 요약한 브리핑 생성
- 예정된 미팅에 필요한 내부 자료를 RAG로 검색하여 참고자료 추천
- AI 결과를 초안으로 저장하고 사용자 승인 후에만 실제 데이터에 반영

에이전트는 두 시점에 나누어 실행된다.

1. **최초 실행**: 보고서·영업·C/S 변경을 분석해 위험을 판정하고 다음 미팅 일정을 제안한다. 이 시점에는 브리핑을 만들지 않는다.
2. **재진입 실행**: 일정관리 에이전트가 추천한 일정을 사용자가 승인해 돌아오면, 승인된 일정과 RAG로 조회한 자료를 근거로 브리핑을 생성한다. 이 시점에는 다음 미팅을 다시 제안하지 않는다.

## 모델(LLM)

계약·영업 정보를 구조화하고 여러 이력 사이의 관계를 파악할 수 있는 LLM을 사용한다.

- 비정형 보고서 및 활동 내용 구조화
- 기존 계약 히스토리와 신규 변경 내용 비교
- 계약 단계, 위험 요소, 미결 업무 및 후속 조치 추론
- 사용자에게 제공할 브리핑과 일정 제안 생성
- RAG 검색 결과 중 현재 미팅과 관련된 자료 선별

모델은 계약의 법적 효력을 판단하거나 사용자를 대신해 계약을 확정하지 않는다. 불확실한 내용은 사실로 단정하지 않고 `확인 필요` 항목으로 표시한다.

## 지침(Prompt/Policy)

- 현재 사용자가 접근할 수 있는 팀과 회사의 데이터만 조회한다.
- 회사, 계약, 고객, 보고서의 소속 관계를 항상 확인한다.
- 입력받은 변경 내용을 기존 히스토리와 비교하고 신규 사실, 수정 사항, 충돌 사항을 구분한다.
- 보고서에 없는 계약 조건이나 고객 의사를 추측해서 생성하지 않는다.
- 계약 금액, 기간, 단계, 담당자, 갱신일 등 중요한 정보는 근거를 함께 표시한다.
- 위험 판정은 정해진 위험 코드(계약 만료 임박, 견적 만료 임박, 납품 지연, 미해결 C/S, 후속 조치 지연, 계약 정보 누락 등)와 근거 데이터만으로 표시하고, 근거 없는 위험을 새로 만들지 않는다.
- 브리핑은 일정관리 에이전트가 추천한 일정을 사용자가 승인해 돌아온 재진입 실행에서만 생성한다. 최초 실행에서는 다음 미팅 일정만 제안하고 브리핑은 만들지 않는다.
- AI가 생성한 결과는 먼저 초안 상태로 저장한다.
- 계약 단계 변경, 성사·갱신·만료 처리 등 실제 변경은 사용자 승인 후에만 실행한다.
- AI가 변경안을 생성한 이후 원본 데이터가 변경된 경우, 기존 변경안을 실행하지 않고 최신 데이터를 기준으로 변경안을 다시 생성하여 사용자 승인을 요청한다.
- 일정은 확정하지 않고 후보로만 제시하며 일정관리 에이전트가 조율할 수 있도록 전달한다.
- 일정관리 에이전트와의 교류(duplex)는 일정 충돌 시 대체 후보를 요청받고 응답하는 범위로 한정한다. 확정된 일정을 이용해 접촉 이력을 갱신하는 기능은 이 설계에 포함하지 않는다.
- RAG 자료는 사용자 권한 범위 안에서 검색하고 출처를 표시한다.
- 개인정보와 민감한 계약 정보를 불필요하게 프롬프트나 로그에 남기지 않는다.

## 도구(Tools)

- 계약·딜 조회 및 변경 API
- 회사 및 고객 정보 조회 API
- 영업 활동 히스토리 조회·추가 도구
- C/S 요청 및 대응 이력 관리 도구
- 완성된 미팅 보고서 조회 도구
- 브리핑 초안 저장 도구
- 일정 후보 생성 및 일정관리 에이전트 호출 도구
- 문서 검색 및 벡터 검색 도구
- 팀·회사·사용자 접근 권한 확인 도구
- 승인 요청 및 승인 결과 조회 도구
- 데이터 버전 또는 수정 시각 확인 도구
- 장기 작업 생성 및 상태 조회 도구
- 멱등성 키 기반 중복 실행 방지 도구
- 감사 로그 기록 도구

조회 도구와 변경 도구는 분리한다. 변경 도구는 유효한 사용자 승인 정보와 최신 데이터 버전을 전달받은 경우에만 실행할 수 있어야 한다.

## 메모리(Memory)

계약 에이전트의 메모리는 회사와 계약 단위로 분리한다.

- 회사별 영업·계약 히스토리
- 계약 단계 변경 이력
- 미팅 및 보고서 요약 이력
- 주요 의사결정과 근거
- C/S 요청과 대응 이력
- 미결 업무 및 후속 조치
- 이전 브리핑과 일정 제안
- 사용자가 승인·거절·수정한 제안
- 반복적으로 확인된 사용자 선호

장기 메모리에는 검증된 사실만 저장한다. AI의 추론이나 제안은 사실과 구분하여 초안 또는 추론 상태로 보관한다.

## 지식(Knowledge/RAG)

다음 정보를 검색 대상으로 사용한다.

- 해당 회사의 계약 및 영업 히스토리
- 미팅 보고서와 미팅 요약
- 자료요약 에이전트가 처리한 PDF·PPTX·DOCX·HTML 문서
- 제품·서비스 설명 자료
- 제안서, 견적서, 계약 관련 내부 문서
- C/S 대응 자료와 FAQ
- 조직의 영업 프로세스 및 계약 단계 정의

검색 시 회사, 팀, 계약, 문서 보안등급, 작성일 등을 필터로 사용한다. 오래된 자료와 최신 자료가 충돌하면 최신성을 확인하고 충돌 사실을 사용자에게 알린다. 생성 결과에는 가능한 범위에서 문서명, 문서 ID, 관련 구간 등 출처를 연결한다.

## 계획·추론(Planning)

### 1차 실행 — 위험 판정과 다음 미팅 제안

1. 트리거 종류와 요청 ID를 확인한다.
2. 사용자 및 팀의 접근 권한을 검증한다.
3. 보고서, 영업 활동 또는 C/S 변경 내용을 읽는다.
4. 기존 계약 히스토리와 비교한다.
5. 신규 정보, 변경 정보, 충돌 정보, 누락 정보를 분류한다.
6. 계약 만료·납품·장기 미접촉 등 위험을 판정하고 근거를 남긴다.
7. 다음 미팅의 목적, 필요 시점, 예상 소요 시간과 일정 후보를 만든다.
8. 결과와 근거를 임시 저장한다.
9. 사용자에게 위험 판정과 다음 미팅 제안을 제시한다. 이 시점에는 브리핑을 만들지 않는다.
10. 승인 시 원본 데이터의 버전을 다시 확인한다.
11. 원본이 그대로라면 다음 미팅 제안을 일정관리 에이전트로 전달하고, 달라졌다면 재검토를 요청한다.
12. 실행 결과와 감사 로그를 저장한다.

### 재진입 실행 — 브리핑 생성

1. 일정관리 에이전트가 추천해 사용자가 승인한 일정을 입력으로 받는다.
2. 해당 고객사의 최신 딜·계약 상태와 승인된 보고서를 다시 조회한다.
3. 필요한 내부 자료를 RAG로 검색한다.
4. 승인된 일정, 계약 현황, RAG 자료를 근거로 회사별 브리핑을 생성한다. 근거가 없는 항목은 채우지 않고 부족하다고 표시한다.
5. 결과와 근거를 임시 저장하고 사용자에게 제시한다.
6. 실행 결과와 감사 로그를 저장한다.

## 상태(State)

| 상태 | 설명 |
|---|---|
| `RECEIVED` | 요청 접수 |
| `VALIDATING` | 입력과 권한 검증 |
| `ANALYZING` | 히스토리 및 보고서 분석, 위험 판정 |
| `DRAFTING` | 다음 미팅 제안 작성 (1차 실행) |
| `PENDING_APPROVAL` | 사용자 승인 대기 |
| `STALE` | 승인 대기 중 원본 데이터 변경 감지 |
| `APPROVED` | 사용자 승인 완료 |
| `EXECUTING` | 실제 계약·영업 데이터 변경 |
| `AWAITING_SCHEDULE` | 일정관리 에이전트의 일정 승인 대기 (재진입 전) |
| `RETRIEVING` | RAG 자료 검색 (재진입 실행) |
| `BRIEFING` | 브리핑 작성 (재진입 실행) |
| `COMPLETED` | 작업 완료 |
| `FAILED` | 처리 실패 |
| `CANCELLED` | 사용자 취소 |

상태에는 요청 ID, 멱등성 키, 입력 데이터 버전, 초안 버전, 승인자, 승인 시각, 실행 결과를 함께 기록한다. 1차 실행과 재진입 실행은 서로 다른 요청 ID를 가지며, 재진입 실행은 1차 실행의 요청 ID를 부모로 참조한다.

## 실행 루프(Agent Loop)

### 1차 실행 — 위험 판정과 다음 미팅 제안

1. 보고서 완성, 영업 활동 또는 C/S 활동 트리거를 수신한다.
2. 동일한 멱등성 키로 완료되거나 실행 중인 요청이 있는지 확인한다.
3. 입력값과 데이터 접근 권한을 검증한다.
4. 관련 회사·계약 히스토리와 필요한 문서를 조회한다.
5. 분석이 길어지면 비동기 작업으로 전환하고 작업 ID를 반환한다.
6. 클라이언트는 작업 ID로 진행 상태를 조회한다.
7. 위험 판정과 다음 미팅 제안을 초안으로 저장한다. 브리핑은 만들지 않는다.
8. 위험 판정, 변경 제안, 근거, 다음 미팅 제안을 사용자에게 제시한다.
9. 사용자 승인을 기다린다.
10. 승인 후 입력 데이터의 버전이나 수정 시각을 재확인한다.
11. 변경이 없다면 실제 작업을 한 번만 실행하고, 다음 미팅 제안을 일정관리 에이전트로 전달한다.
12. 변경이 있다면 `STALE` 상태로 전환하고 재분석·재승인을 요청한다.
13. 실행 결과와 감사 로그를 저장하고 `AWAITING_SCHEDULE` 상태로 대기한다.

### 재진입 실행 — 브리핑 생성

1. 일정관리 에이전트가 추천해 사용자가 승인한 일정을 입력으로 수신한다.
2. 동일한 멱등성 키로 완료되거나 실행 중인 요청이 있는지 확인한다.
3. 입력값과 데이터 접근 권한을 검증한다.
4. 해당 고객사의 최신 딜·계약 상태와 승인된 보고서를 조회한다.
5. 자료요약 에이전트를 RAG로 조회한다.
6. 승인된 일정이 없거나 조회할 자료가 없어도 브리핑은 생성하되, 없는 근거는 비어 있다고 표시한다.
7. 브리핑을 초안으로 저장한다.
8. 브리핑과 근거를 사용자에게 제시한다.
9. 실행 결과와 감사 로그를 저장한다.

## 평가·안전장치(Guardrails)

- 권한이 없는 팀·회사·계약 데이터 접근 차단
- 다른 회사의 히스토리가 섞이지 않도록 테넌트 경계 검증
- 계약 조건, 금액, 날짜, 단계의 근거 정확성 평가
- 브리핑에서 사실·추론·제안을 명확히 구분
- RAG 인용 자료의 관련성, 최신성, 접근 권한 검증
- 사용자 승인 없는 계약 상태 변경 차단
- 승인 대상과 실제 실행 내용의 동일성 검증
- 승인 이후 원본 데이터가 변경된 경우 실행 차단
- 멱등성 키를 이용한 중복 계약 변경 방지
- 도구 호출 횟수, 시간, 데이터 범위 제한
- 검색 문서의 프롬프트 인젝션을 지시가 아닌 참고자료로만 처리
- 실패 시 부분 변경을 방지하고 재시도 가능한 상태 유지
- 모든 조회·제안·승인·실행 이력에 대한 감사 로그 기록
