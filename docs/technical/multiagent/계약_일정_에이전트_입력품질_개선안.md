# 위험 신호의 입력 품질을 올리는 방안

| 항목 | 내용 |
|---|---|
| 대상 | 계약관리 에이전트의 위험 신호 입력 |
| 상태 | **검토안 (미구현)** |
| 작성 기준일 | 2026-08-31 |

계약관리의 위험 신호 여섯 중 넷은 사람이 딜에 입력한 날짜를 읽는다. 값이 비어 있으면
감지 자체가 안 된다(아키텍처 3.1 참고). 이 문서는 그 한계를 다루는 방안을 모은 것이다.

**아직 구현하지 않았다.** 아키텍처 문서는 "지금 이렇게 동작한다"를 담으므로 여기로 분리했다.

---

한계를 "담당자가 안 넣으면 방법이 없다"로 끝내지 않는다. **넣을 정보가 부족한 상황 자체를
다루는 방법**이 있다. 여덟 가지를 검토했고 아래 순서로 한다.

| 순서 | 방안 | 비용 | 효과 |
|---|---|---|---|
| 1 | ① 정밀도로 받기 | 컬럼 2개 + 계산 분기 | 커버리지가 즉시 오른다 |
| 2 | ② NULL을 세 갈래로 | 컬럼 1개 + 입력 UI | 결측 자체가 신호가 된다 |
| 3 | ⑥ 신호의 우아한 저하 | 계산 분기 | 빈 값에도 신호가 남는다 |
| 4 | ⑦ 신선도를 신호로 | 비교 한 줄 | 거의 공짜 |
| 5 | ③ 문서에서 역으로 채우기 | 추출 파이프라인 | 크지만 비싸다 |
| 6 | ④ 보고서 흐름에서 빈 슬롯만 질문 | 프롬프트 + 반영 UI | 입력 작업 자체를 없앤다 |
| — | ⑤ 규칙 파생값 · ⑧ 계획·실적 분리 | — | 뒤로 미룬다 |

**① "모른다"를 정밀도로 받는다**

사람이 모르는 것은 날짜가 아니라 **정확한 날짜**다. "9월 중순", "계약 후 6주"는 안다. 지금
스키마는 정확한 datetime 아니면 NULL 둘뿐이라, 대략 아는 정보가 통째로 버려진다.

```
expected_delivery_at         datetime   ← 기존
expected_delivery_precision  text       ← day | week | month | quarter
expected_delivery_source     text       ← entered | extracted | derived | unknown
```

신호 계산은 정밀도에 맞춰 **가장 이른 경계**를 쓴다(보수적). 화면에는 "9월 중순 (추정)"으로
쓴다. 입력 부담은 내려가고 커버리지는 올라간다.

**② NULL을 세 갈래로 쪼갠다**

지금은 NULL 하나에 세 가지가 섞여 있다.

| 지금 | 실제 의미 | 어떻게 다뤄야 하나 |
|---|---|---|
| NULL | 아직 안 넣음 | 입력을 유도한다 |
| NULL | 물어봤는데 고객도 모름 | 확인용 `Activity`를 자동 생성하고 D+3에 리마인드 |
| NULL | 이 딜엔 해당 없음 | 신호 계산에서 영구 제외 |

구분하면 "정보 부족"이 결함이 아니라 **그 자체로 읽히는 신호**가 된다. 계약 단계인데 예상
납품일이 비어 있는 딜은 지연 딜만큼 위험하다.

**⑥ 신호의 우아한 저하**

날짜가 없다고 신호를 침묵시키지 않고, 대체 신호로 강등한다.

| 신호 | 입력이 있을 때 | 없을 때 대체 |
|---|---|---|
| `delivery_delay_risk` | `expected_delivery_at` 지남 | `contract_signed_on` 경과일 + 단계 체류일 |
| `quote_expiring` | `quote_valid_until` 14일 이내 | `quote_issued_on` 이후 30일 무응답 |
| `contract_expiring` | `contract_ends_on` 30일 이내 | 대체 없음 — 결측을 ②의 신호로 올린다 |

카드에는 "추정 기반" 배지를 붙인다. 신뢰도를 숨기지 않는 것은 5.1과 같은 원칙이다.

**⑦ 신선도를 신호로 쓴다**

지금 임계값은 "날짜가 지났다"를 본다. 그런데 **"날짜가 지났는데 아무도 안 고쳤다"**가 훨씬
강한 신호다. `updated_at`과 대조하면 사람 입력의 신선도를 시스템이 관찰할 수 있다. 입력 품질
문제를 추가 입력 없이 감지하는 방법이고, 비교 한 줄이면 된다.

**③ 입력을 검토로 바꾼다 (문서 → 필드 제안)**

계약서·발주서는 이미 `Document`/`File`로 딜에 붙는다. 업로드 시 납품 기한·계약 만료일·견적
유효기간 후보를 뽑아 **초안으로 채워두고**, 담당자는 "맞음/고침"만 누른다. 근거(파일 + 해당
문장)는 `ai_evidence`에 남기고 원문으로 점프시킨다. 빈칸 채우기는 회피되지만 틀린 값 고치기는
잘 되는 것이 사람의 습성이다. 자료요약 에이전트(#80)와 재료가 겹친다.

**④ 보고서 작성 흐름에서 빈 슬롯만 묻는다**

`Report.transcript`가 이미 있다. 보고서를 쓸 때 **비어 있는 필드에 대해서만** 두세 개 묻는다
("이번 건 납품은 언제까지로 얘기됐나요?"). 자연어 답에서 날짜를 파싱해 딜 필드 반영을 제안한다.
보고서를 쓰는 김에 딜이 채워지므로 별도 입력 작업이 사라진다. 4.3 ①의 경계면을 넓히는 방향이다.

**⑤ 규칙 기반 파생값**

`contract_signed_on + 제품별 평균 리드타임`으로 채우고 `source = derived`로 표시한다. 리드타임은
완료된 딜에서 계산한다. 틀릴 수 있지만 **NULL보다 틀린 추정치가 낫다** — 담당자가 고치면 그
수정이 다시 리드타임 데이터가 된다.

**⑧ 계획과 실적을 분리한다**

`expected_delivery_at`은 계획값으로 두고, 실제 납품은 `PurchaseOrder`·출하 데이터에서 관찰한다.
둘의 차이가 진짜 신호이고, 이것은 입력 품질과 무관하다. 7.3 "위험 신호 자동화"의 최종형이다.
