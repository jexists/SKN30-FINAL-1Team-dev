# 일정관리 에이전트 설계

## 1. 목표

계약 에이전트가 제안한 선호 기간·소요 시간과 담당 영업사원의 기존 일정을 바탕으로, 겹치지 않는 일정 후보를 추천한다.

## 2. 입력과 출력

입력:

- 영업 건(`sales_deal`) ID
- 선호 시작·종료 시각
- 미팅 소요 시간(분)
- 미팅 이유 (선택)
- 담당 영업사원의 기존 일정 (선호 기간 앞뒤 7일 포함)

출력:

- 일정 후보 목록 (최대 10개)
- 충돌 정보 (겹치는 기존 일정의 ID와 사유)

후보 개수는 항상 10개가 아니다. 유효한 후보가 적으면 그보다 적게 반환할 수 있다.

## 3. 처리 흐름

1. 실행 서비스가 DB에서 선호 기간과 기존 일정을 조회해 입력 스냅샷을 만든다.
   - 계약관리 에이전트의 다음 미팅 제안 실행(`contract_management_next_meeting`)을 이어받으면(`parent_run_id`), 그 실행이 낸 선호 시간대·소요 시간·이유를 그대로 쓴다.
   - 이어받지 않으면 사용자가 직접 지정한 선호 시간대를 쓴다.
   - 선호 시간대가 없으면 오늘부터 7일을 기본 탐색 범위로 둔다.
2. LLM이 Asia/Seoul 09:00~18:00 업무시간 안에서, 기존 일정과 겹치지 않는 후보를 만든다.
3. 서버가 LLM 출력을 다시 검증한다.
   - 업무시간(09:00~18:00) 밖이거나 시작·종료가 같은 날짜가 아닌 후보는 버린다.
   - 기존 일정과 실제로 겹치는 후보는 목록에서 빼고 충돌 정보로 옮긴다.
4. 최종 `schedule_candidates`와 `conflicts`를 실행 결과로 저장한다.

계약 에이전트와 이 에이전트 사이에 대체 일정을 주고받는 왕복 호출은 없다. 한 번의 실행으로 끝난다.

## 4. 개인정보 보호

LLM에는 기존 일정의 시작·종료 시각과 종일 여부만 전달한다. 담당자(`owner_member_id`) 등은 LLM에 보내지 않고, 서버가 로컬에서 충돌을 다시 계산할 때만 사용한다.

## 5. 실행 상태

| 상태 | 뜻 |
|---|---|
| `queued` | 요청 접수, 실행 대기 |
| `running` | LLM 호출 중 |
| `completed` | 완료 |
| `failed` | 실패 |

계약관리 에이전트와 같은 `agent_runs` 테이블과 상태값을 공유한다. 캘린더 조회·충돌 검사·대체 요청 등을 구분하는 세분화된 중간 상태는 두지 않는다.

## 6. 이번 구현 범위

포함:

- 영업 건 하나에 대한 선호 기간·기존 일정 기반 후보 추천
- 09:00~18:00 업무시간 검증과 기존 일정 충돌 재검증(서버 측 재계산)
- 계약관리 에이전트의 다음 미팅 제안을 이어받아 실행(`parent_run_id`)
- 개인정보 최소화 (담당자 ID 등을 LLM에 보내지 않음)

제외 (7절 "향후 확장 계획" 참고):

- 여러 회사·여러 영업 건의 후보를 한 화면에서 통합 비교
- 충돌 시 계약 에이전트에 대체 후보를 재요청하는 양방향 협상
- 사용자별 선호를 학습하는 장기 메모리
- RAG·지식베이스 기반 정책 조회
- 캘린더 생성·수정·삭제, 이동 시간·준비 시간, 휴일·시간대 자동 계산
- 참석자 가용성 조회, 초대장 발송
- 세분화된 실행 상태(`FETCHING_CALENDAR`, `CHECKING_CONFLICTS` 등), 승인 대기 중 재검토(`STALE`), 캘린더 버전 확인
- 감사 로그, 캘린더 변경에 대한 멱등성 키 기반 잠금 (현재 `idempotency_key`는 같은 실행 요청의 중복 생성만 막는다)
- 후보 선택·승인을 위한 프론트엔드 화면 (현재는 백엔드 파이프라인 테스트로만 검증됨 — [멀티 에이전트 테스트 계획 및 결과 보고서.md](./멀티%20에이전트%20테스트%20계획%20및%20결과%20보고서.md) 참고)

## 7. 향후 확장 계획 (미구현)

아래는 최초 설계 단계에서 목표로 삼았던, 더 큰 범위의 일정관리 에이전트 구상이다. 현재는 구현되지 않았다. 실제로 만들 때 이 절의 내용을 구현 절(1~6절)로 옮기고 이 절은 갱신한다.

### 목표

- 여러 회사에서 제안된 미팅 후보 통합
- 사용자의 캘린더 일정 및 근무 가능 시간 확인
- 일정 중복, 이동 시간, 준비 시간, 우선순위 검토
- 충돌 시 계약 에이전트에 대체 일정 요청
- 사용자 승인 후에만 캘린더 일정 생성·수정·삭제
- 승인 대기 중 일정이 바뀌면 재검토

### LLM 역할 확장

- 회사별 미팅 목적과 긴급도 비교
- 대체 일정 요청 조건 생성
- 여러 후보 중 최적안 추천과 그 이유 설명

### 도구

- 사용자·팀 캘린더 조회 및 생성·수정·삭제 도구
- 가용 시간 검색, 일정 충돌 검사, 시간대·휴일 계산, 이동·준비 시간 계산 도구
- 계약 에이전트의 일정 후보 조회 도구, 계약 에이전트에 대체 일정 요청 도구
- 참석자 가용성 조회 도구
- 승인 요청 및 승인 결과 조회 도구, 캘린더 이벤트 버전 확인 도구
- 비동기 작업·상태 조회 도구, 감사 로그 기록 도구

조회 도구와 변경 도구는 분리하고, 캘린더 변경 도구는 유효한 사용자 승인과 최신 캘린더 버전이 확인된 경우에만 실행한다.

### 메모리

사용자별 일정 선호를 제한적으로 기억한다: 기본 근무시간·시간대, 선호 미팅 시간대, 회의별 기본 소요 시간, 일정 사이 여유 시간, 이동·준비 시간 규칙, 피해야 하는 시간대, 회사별 미팅 빈도, 사용자가 승인·거절·수정한 제안, 반복적으로 확인된 조정 기준. 캘린더 전체 내용은 복제하지 않는다.

### 지식(RAG)

회사별 미팅 목적과 일정 제안, 계약 단계별 권장 후속 미팅 시점, 근무시간·휴일·시간대 정책, 팀의 일정 운영 규칙, 미팅 종류별 권장 소요 시간, 이동·준비 시간 기준, 참석자·회의실 예약 규칙을 검색해 참고한다. 실제 가용 여부는 항상 캘린더 도구로 다시 검증한다.

### 상태(State)

`RECEIVED` → `VALIDATING` → `FETCHING_CALENDAR` → `CHECKING_CONFLICTS` → `REQUESTING_ALTERNATIVES` → `OPTIMIZING` → `DRAFTING` → `PENDING_APPROVAL` → (승인 대기 중 변경 시 `STALE`) → `APPROVED` → `EXECUTING` → `COMPLETED`/`FAILED`/`CANCELLED`

각 상태에는 작업 ID, 멱등성 키, 캘린더 스냅샷 버전, 후보 일정 버전, 승인 정보, 실행 결과를 기록한다.

### 평가·안전장치

- 사용자·팀 캘린더 접근 권한 검증, 다른 사용자의 비공개 일정 노출 방지
- 시간대·일광절약시간·휴일 변환 정확성 검증
- 고정 일정·보호된 시간대 임의 변경 금지
- 사용자 승인 없는 일정 생성·수정·삭제 차단, 초대장 발송 여부를 승인 화면에 명시
- 승인 후 캘린더 변경 시 기존 실행 차단, 멱등성 키와 이벤트 ID로 중복 생성 방지
- 계약 에이전트 간 대체 일정 요청의 최대 반복 횟수 설정
- 조율 불가 시 임의로 확정하지 않고 충돌 원인과 선택지 제시
- 도구 오류로 부분 생성된 이벤트 탐지·복구
- 조회·추천·승인·실행 과정에 대한 감사 로그 기록
