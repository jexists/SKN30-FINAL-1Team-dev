# 계약·일정 에이전트 트리거 정합 계획

## 0. 이 문서의 배경

계약관리·일정관리 에이전트의 호출 시점이 기대와 다르다는 문제 제기에서 출발해 현재 구현을
전수 확인했다. 확인 결과 **구현은 [계약_일정_에이전트_아키텍처.md](./계약_일정_에이전트_아키텍처.md)
2.2장의 트리거 4가지와 정확히 일치**했고, 어긋난 것은 **에이전트 흐름 다이어그램**이었다.

둘 중 무엇을 정본으로 볼지 확인한 결과 **다이어그램을 정본으로 삼기로 결정**했다. 따라서
기존 설계 문서와 구현이 다이어그램을 따라가야 하며, 이 문서는 그 차이와 맞춰야 할 범위를
정리한다.

**새 기능을 더하는 작업이 아니다.** 다이어그램이 정의한 플로우 가운데 아직 코드에 반영되지
않은 구간을 채워, 설계대로 돌아가게 만드는 것이다.

## 1. 판단 기준

- 다이어그램과 기존 문서·코드가 다르면 **다이어그램을 따른다.**
- 다이어그램에 없는 내용은 임의로 정하지 않고 **4장에 모아 확인을 받는다.**
- 기존 문서의 결정을 뒤집을 때는 그 근거가 무엇이었는지 3장에 남긴다.

## 2. 문제와 수정 방향

이미 다이어그램대로 동작하는 것은 여기서 다루지 않는다. **신규 영업 딜 등록**,
**보고서 완성 → 딜 귀속 확인분 전달**, **캘린더(트리거이자 조회 화면)** 세 가지가 그렇다.

아래는 아직 어긋난 아홉 가지다. 각각 무엇이 문제이고, 왜 그렇게 되어 있으며, 어떻게 맞출지를
차례로 적는다.

### 2.1 딜 정보를 고쳐도 다시 계산하지 않는다

**문제** — 다이어그램은 "영업 단계·정보 수정"을 한 항목으로 묶는데, 실제로는 단계를 옮길
때만 걸린다. 금액·일정·계약 정보를 고쳐도 추천은 옛 값 그대로다.

**구조** — 파이프라인 큐잉이 `move_sales_deal`
([sales_deals.py:1664](../../../backend/app/api/sales_deals.py#L1664))에만 있고
`update_sales_deal`(`PATCH /sales-deals/{id}`)에는 없다. 단계 이동만 "상황이 달라진 신호"로
본 설계다.

**수정** — `update_sales_deal` 에도 같은 큐잉을 넣는다. 다이어그램이 둘을 구분하지 않으므로
같은 신호로 취급한다.

### 2.2 계약 만료가 다가와도 아무도 알아채지 못한다

**문제** — "성사 계약 갱신·만료"를 감지하는 코드가 없다. 계약이 끝나가도 갱신 미팅 제안이
뜨지 않는다.

**구조** — 현재 트리거는 전부 **사용자가 API 를 호출할 때만** 작동한다. 만료는 아무도 누르지
않는데 시간이 지나 발생하므로, 이 방식으로는 잡히지 않는다.

다만 두 가지가 이미 갖춰져 있다.

| 필요한 것 | 상태 |
|---|---|
| 만료일 컬럼 | `sales_deal.contract_ends_on` 이 이미 있다 |
| 상시 실행 프로세스 | `python -m app.services.agent_worker` 가 별도 컨테이너로 떠 있다 ([runtime-environment-test.sh:176](../../../deploy/backend/tests/runtime-environment-test.sh#L176)) |

**수정** — 워커의 폴링 루프에 **하루 한 번 도는 검사**를 더한다. `contract_ends_on` 이
**D-30** 안에 든 딜을 찾아 파이프라인에 넣는다. 주기는 정확도가 아니라 부하 문제이며, 만료
알림이 몇 시간 늦어도 문제되지 않는다. 스케줄러를 새로 들일 필요는 없다.

계약 **갱신**은 따로 만들지 않는다. `contract_ends_on` 값이 바뀌는 것은 딜 정보 수정이라
2.1 의 트리거에 자연히 걸린다.

### 2.3 C/S 활동 대부분이 신호가 되지 못한다

**문제** — 다이어그램은 C/S 활동 세 가지를 모두 트리거로 둔다. 실제로는 상태가
`in_progress` 로 바뀔 때 하나만 걸린다. 요청을 등록하거나 답변을 달아도 아무 일도 없다.

**구조** — 큐잉이 `transition_support_request`
([support.py:381](../../../backend/app/api/support.py#L381)) 안에, 그것도 `in_progress`
조건 아래에만 있다. 위험 신호 스냅샷이 보는 조건(미해결 C/S)과 맞춘 설계다.

**수정** — 접점은 이미 다 있으므로 큐잉만 더한다.

| 다이어그램 | 접점 | 할 일 |
|---|---|---|
| 대응요청 등록 | `POST /support-requests` | 큐잉 추가 |
| 처리 상태 변경 | `POST /support-requests/{id}/transition` | 상태 한정을 풀어 **모든 전환**에서 걸리게 한다 |
| 담당자 변경 | 상태 전환과 같은 접점인지 확인 필요 | 확인 후 큐잉 추가 |
| 대응 이력·답변 등록 | `POST /support-requests/{id}/responses` | 큐잉 추가 |

답변 등록은 한 건에 여러 번 일어날 수 있으나, 시간 쿨다운은 걸지 않는다. 호출량을 보고
필요하면 호출 지점을 줄이는 쪽으로 다룬다(2.9).

### 2.4 일정을 고치거나 지워도 추천이 그대로 남는다

**문제** — 일정을 옮기거나 취소해도 재계산이 없다. 이미 지나간 상황을 근거로 만든 카드가
캘린더에 그대로 뜬다.

**구조** — [`update_activity`](../../../backend/app/api/activities.py#L771) 와
[`delete_activity`](../../../backend/app/api/activities.py#L830) 모두 큐잉하지 않는다.
등록 경로에만 트리거가 붙어 있다.

**수정** — 두 곳에 큐잉을 넣는다. 일정 변경은 곧 "그 시간대 사정이 달라졌다"는 신호이므로,
그 딜의 추천을 다시 계산한다.

### 2.5 일정관리를 직접 부를 수 없다

**문제** — 다이어그램은 일정 관련 활동에서 **일정관리로 직접** 화살표를 긋는다. 실제로는 그
경로가 없다. 일정관리는 언제나 계약관리 파이프라인의 2단계로만 실행된다.

**구조** — 백엔드는 이미 준비돼 있다. `POST /agent-runs`
([agent_runs.py:28](../../../backend/app/api/agent_runs.py#L28))로 `schedule_management` 를
직접 실행할 수 있고, 계약관리를 거치지 않을 때는 `preferred_starts_at`·`preferred_ends_at`·
`duration_minutes` 를 대신 받도록 검증까지 들어가 있다
([agent_runs.py:119](../../../backend/app/schemas/agent_runs.py#L119)). **프론트엔드에서
호출하지 않을 뿐이다.**

**수정** — 사용자가 "언제쯤, 몇 분짜리"를 입력하는 화면을 만들고 이 API 에 연결한다. 새 경로를
만들 필요는 없다.

### 2.6 딜 없는 일정은 아예 대상이 아니다

**문제** — 캘린더에서 딜 없이 일정을 잡으면 아무 추천도 만들어지지 않는다. 다이어그램은 일정
활동에 딜 조건을 달지 않는다.

**구조** — `POST /activities` 의 큐잉이 두 조건을 모두 만족할 때만 걸린다
([activities.py:676](../../../backend/app/api/activities.py#L676)).

1. AI 추천을 거치지 않은 등록이고 (`schedule_management_run_id` 가 없음)
2. 영업 딜이 연결돼 있다

더 깊은 곳에서도 딜이 축이다. 자리 선점(`_reserve`), 딜 조회(`_open_deal`), 입력 스냅샷,
제안 저장(`sales_deal_id` UNIQUE)이 모두 딜 ID 를 기준으로 돈다.

**수정** — 축을 **고객사**로 넓힌다. 계약관리 에이전트가 원래 요구하는 식별자는 딜이 아니라
고객사이고(`_REQUIRED_FIELDS["contract_management_next_meeting"] == {"customer_company_id"}`,
[agent_runs.py:60](../../../backend/app/schemas/agent_runs.py#L60)), 딜은 입력을 좁히는 용도로
쓰인다. 일정에는 고객사가 언제나 붙으므로 **딜이 없으면 고객사 기준으로 돌린다.**

그래서 바뀌는 것:

- 제안 저장 키를 딜 단위에서 **딜 또는 고객사** 로 바꾼다 (UNIQUE 제약 재설계)
- 잠금과 쿨다운의 단위도 같은 키를 따른다
- 딜이 없으면 위험 신호 대부분이 비므로, 그 상태로도 제안이 뜰지 프롬프트 수준에서 확인한다

**감수하는 것** — 딜이 없으면 영업 단계·금액·위험 신호가 모두 비어 판단 근거가 얇다. 근거
없는 제안이 늘어 중요한 추천이 묻힐 수 있다. 다이어그램을 정본으로 삼은 결정에 따른 것이므로,
실제 결과를 보고 재검토한다.

### 2.7 충돌이 나면 되묻지 않고 버린다

**문제** — 다이어그램의 점선 양방향 화살표(교류)가 없다. 일정관리가 충돌을 발견해도 계약관리
에게 되묻지 않고 그 후보를 버린다.

**구조** — [schedule_management.py](../../../backend/app/agents/schedule_management.py) 에는
`contract_management` 를 참조하는 코드가 아예 없다. 파이프라인도 일정관리 결과를 저장하고
끝난다. 되묻는 경로 자체가 만들어진 적이 없다.

**수정** — 일정관리 결과에 충돌만 남고 후보가 없으면 계약관리를 **한 번 더** 부른다.
되묻기는 **1회로 제한**한다. 상한이 없으면 두 에이전트가 무한히 주고받고 그때마다 LLM 비용이
붙는다.

### 2.8 후보가 0개면 화면에 아무 말도 없다

**문제** — 후보가 전부 버려지면 제안을 저장하지 않고 조용히 끝난다
([contract_next_meeting_pipeline.py:162](../../../backend/app/services/contract_next_meeting_pipeline.py#L162)).
사용자는 왜 카드가 안 뜨는지 알 수 없다. 아키텍처 7.3 에도 "조용한 실패" 로 적혀 있다.

**구조** — 제안 상태(`contract_next_meeting_suggestion.status_code`)가 DB CHECK 제약으로
`pending` / `dismissed` / `accepted` 세 값만 허용한다. "후보 없음" 을 담을 자리가 없다.

**수정** — 상태 값을 하나 더 받도록 **마이그레이션**하고, 그 상태의 카드를 화면에 표시한다.
이번 작업에서 스키마가 바뀌는 유일한 항목이다.

되묻기(2.7)를 넣어도 후보 0개는 남는다(3.1 의 측정). 그래서 알림을 되묻기보다 **먼저** 넣는다.

### 2.9 잦은 호출을 막는 방어가 화면 사정에 묶여 있다

**문제** — 같은 딜을 10분 안에 다시 돌리지 않는 쿨다운이 있다
([contract_next_meeting_pipeline.py:30](../../../backend/app/services/contract_next_meeting_pipeline.py#L30)).
영업현황 보드에서 단계를 연달아 옮기는 것을 막으려고 둔 값인데, 트리거가 늘면 다른 경로까지
같이 막는다.

**구조** — [`_ran_recently`](../../../backend/app/services/contract_next_meeting_pipeline.py#L198)
가 막는 것은 둘인데 성격이 다르다.

| 역할 | 처리 |
|---|---|
| 최근 10분 안에 실행됨 | **없앤다** |
| 이미 `queued`/`running` 인 실행이 있음 | **남긴다.** 동시 트리거가 같은 딜에 LLM 을 두 번 태우는 것을 막는다 |

연속 클릭은 첫 실행이 아직 `queued`/`running` 이라 두 번째 방어가 막는다. 시간 쿨다운이
실제로 덮는 것은 **첫 실행이 끝난 뒤 10분 안에 같은 딜을 다시 건드리는 구간**뿐이다.

**수정** — 시간 쿨다운을 **그 구간까지 포함해 완전히 없앤다.** 남는 방어는
`queued`/`running` 검사 하나다.

실행이 끝난 뒤 사용자가 같은 딜을 다시 건드렸다면 그것은 **새 정보다.** 시간으로 막으면
바뀐 상황이 반영되지 않은 낡은 추천이 그대로 남는다. 이 구조는 추천을 미리 계산해 두는
방식이라(아키텍처 2.1), 낡은 값이 남는 쪽이 호출이 한 번 더 나가는 것보다 나쁘다.

**잦은 호출은 시간이 아니라 호출 지점을 줄여 다룬다.** 영업현황 보드는 단계를 옮길 때마다가
아니라 **보드를 벗어날 때 한 번** 보낸다. 다만 화면 이탈 이벤트는 탭 닫기·새로고침·앱 강제
종료에서 잡히지 않으므로, 단계 이동 시점의 기존 트리거를 백업으로 남기고 중복만 거른다.
호출은 **보드에서 실제 변경이 있었을 때만** 보낸다.

C/S 답변 등록처럼 한 건에 여러 번 발생하는 트리거는 **일단 방어 없이 두고 실제 호출량을
본 뒤** 필요하면 같은 방식(호출 지점 줄이기)으로 다룬다. 시간 쿨다운은 다시 넣지 않는다.

## 3. 기존 문서에서 뒤집히는 결정

### 3.1 "왕복 협상은 없다" (아키텍처 3.2, 7.2)

아키텍처 문서는 왕복 협상을 **의도적으로 제외**했고 근거로 실측을 남겼다.

| 항목 | 결과 |
|---|---|
| 완료된 일정관리 실행 | 89건 |
| 충돌이 기록된 실행 | 42건 (47.2%) |
| 후보가 0개인 실행 | 2건 (2.2%) |

되물어야 할 상황이 2.2% 로 드물고, 그 2건의 원인도 "되묻지 않아서"가 아니라 계약관리가
선호 기간을 30분 한 칸으로 준 것이었다는 판단이다. 그래서 되묻는 대신 **호출 전에 선호
기간을 7일로 넓히는** 방식을 택했고 이는 구현돼 있다
([contract_schedule_snapshots.py:664](../../../backend/app/services/contract_schedule_snapshots.py#L664)).

다이어그램이 정본이므로 이 결정은 뒤집힌다(2.7). 다만 **근거가 된 측정은 여전히 유효하다.**
되묻기를 넣더라도 2.2% 를 위한 것이므로, 되묻기 1회 제한과 후보 0개 알림(2.8)을 함께 둔다.

### 3.2 낡은 기록 (아키텍처 7.3)

7.3장 "향후 확장" 에 `좁은 선호 기간 방어 — 좁게 오면 서버가 넓히는 규칙이 아직 없다` 로
적혀 있으나, 같은 문서 3.2장과 실제 코드는 모두 구현됐다고 말한다. **7.3의 이 줄은 낡았다.** 다이어그램
결정과 무관하게 정리한다.

## 4. 결정 사항

다이어그램에 없어 확인이 필요했던 것들이며, 아래 결정으로 모두 정해졌다.

| 항목 | 결정 | 근거 |
|---|---|---|
| 계약↔일정 교류(되묻기) | 넣는다. **1회 한정** | 2.7 |
| 후보 0개 처리 | **사용자에게 알린다** (마이그레이션 필요) | 2.8 |
| 갱신·만료 감지 | `contract_ends_on` 기준 **D-30**, 하루 1회 검사 | 2.2 |
| 쿨다운 10분 | **시간 쿨다운 완전 제거**, `queued`/`running` 방어만 유지 | 2.9 |
| 캘린더 | 트리거이자 조회 화면 — 이미 그렇게 동작한다 | — |
| 일정관리 직접 진입 | **만든다.** 기존 `POST /agent-runs` 를 프론트에 연결 | 2.5 |
| 딜 없는 일정 | **딜이 없어도 추천을 만든다** | 2.6 |

## 5. 작업 순서

한 번에 하지 않는다. **한 단계를 끝내면 화면에서 직접 확인하고, 결과를 본 뒤 다음 단계로
넘어간다.** [.agent-rules/branching.md](../../../.agent-rules/branching.md) 6장에 따라 단계마다
브랜치를 나누며, 각 브랜치는 시작 시점의 최신 `develop` 에서 만든다.

| 순서 | 브랜치 | 내용 | 화면 확인 |
|---|---|---|---|
| 1 | `docs-agent-trigger-alignment` | 이 문서. 아키텍처 문서 2.2·7.2·7.3 갱신 | 없음 (문서 리뷰) |
| 2 | `agent-cooldown-board-trigger` | 시간 쿨다운 제거, 보드 이탈 시 호출 (2.9) | 보드에서 단계를 연달아 옮기고 나갔을 때 실행이 1건만 생기는지 |
| 3 | `agent-trigger-cs-and-deal` | C/S 3종·담당자 변경, 딜 정보 수정 (2.1·2.3) | C/S 등록·답변·딜 수정 뒤 캘린더에 카드가 뜨는지 |
| 4 | `agent-trigger-activity-edit` | 일정 수정·취소 트리거 (2.4) | 일정을 옮기거나 지운 뒤 카드가 다시 계산되는지 |
| 5 | `agent-schedule-direct-run` | 일정관리 직접 진입 + 선호 기간 입력 UI (2.5) | 계약관리를 거치지 않고 시간 후보가 나오는지 |
| 6 | `agent-contract-expiry-scan` | `contract_ends_on` D-30 정기 검사 (2.2) | 만료 임박 딜을 만들어 두고 다음 검사에서 카드가 뜨는지 |
| 7 | `agent-empty-candidates-notice` | 후보 0개 알림 + 마이그레이션 (2.8) | 일정을 꽉 채운 뒤 "후보 없음" 이 화면에 보이는지 |
| 8 | `agent-schedule-negotiation` | 계약↔일정 되묻기 1회 (2.7) | 충돌 상황에서 되묻기가 한 번만 일어나는지 |
| 9 | `agent-pipeline-company-scope` | 딜 없는 일정까지 태우기 (2.6) | 딜 없이 잡은 일정에서도 카드가 뜨는지 |

**순서를 이렇게 둔 이유**

- **2번이 먼저다.** 쿨다운은 모든 트리거가 공유하는 방어라, 트리거를 늘리기 전에 정리해야
  뒤 단계에서 중복 실행과 비용을 판단할 수 있다.
- **7번이 8번보다 앞이다.** 되묻기를 넣어도 후보 0개는 남는다(3.1 의 측정). 알림이 먼저 있어야
  8번의 효과를 화면에서 구분할 수 있다.
- **9번이 마지막이다.** 제안 저장 키와 UNIQUE 제약이 바뀌어 앞 단계 전부에 영향을 준다.

각 단계는 **걸리는 지점이 늘어난 만큼 비용 영향을 함께 확인**한다(2.9).
