## 0. 이 문서의 범위

SalesLuv의 멀티 에이전트는 **다섯 개**다(`docs/project-overview.md` 7.1). 이 문서는 그중
**영업·계약관리·일정관리 두 에이전트**를 다룬다. 나머지 셋은 주고받는 데이터만 언급한다.

| 에이전트 | `agent_code` | 상태 | 이 문서에서 |
|---|---|---|---|
| 미팅 분석 | `meeting_analysis` | 구현됨 | 경계면만 |
| 보고서 작성 | `report_writing` | 구현됨 | 경계면만 |
| **영업·계약관리** | `contract_management_*` (3종) | 구현됨 | **전체** |
| **일정관리** | `schedule_management` | 구현됨 | **전체** |
| 자료요약 | `document_summary` | 구현됨 | 경계면만 |

자료요약은 계약관리 브리핑과 직접 맞물린다. 브리핑 입력의 `document_context`가 그
에이전트의 RAG 조회 결과다(4.3).

# 1부. 무엇을 만들었나

## 1.1 풀려는 문제

영업 담당자 한 명이 맡는 딜은 보통 20~30개다. 매일 **"오늘 누구를 챙겨야 하지?"**에
답하려면 딜마다 여섯 가지를 봐야 한다 — 계약 만료일, 견적 유효기간, 예상 납품일,
마지막 접촉일, 계약 체결일, 미해결 C/S(조건은 3.1).

**딜 30개 × 항목 6개.** 사람이 매일 훑기에는 많다. 그래서 시스템이 대신 훑고
**"이 고객을 이때쯤 만나세요"**를 카드로 띄운다.

## 1.2 두 에이전트로 나눈 이유

한 문장을 둘로 쪼갰다.

```
"○○병원을    다음 주 화요일 오전에    만나세요"
 └──────────┘  └──────────────────┘
  계약관리       일정관리
  (무엇을, 왜)    (언제)
```

**나눈 기준은 "컴퓨터가 답을 검산할 수 있는가"다.**

| | 계약관리의 답 | 일정관리의 답 |
|---|---|---|
| 예 | "지금 만나야 합니다" | "화요일 10시" |
| **검산 가능?** | ❌ 판단이라 정답이 없다 | ✅ 달력을 보면 안다 |
| 그래서 | 사람이 읽고 판단 | **서버가 전부 다시 검사** |

검산 가능한 답과 아닌 답을 한 에이전트가 같이 내면 **어디까지 믿어야 할지 흐려진다.**

# 2부. 어떻게 동작하나

## 2.1 가장 중요한 결정 — 미리 계산해 둔다

```
[전]  캘린더 진입 → AI 호출 → 대기 11.5초 → 카드
[후]  트리거 발생 → 뒤에서 AI 호출 → 저장
      캘린더 진입 → 저장된 것 조회 → 카드 (0.05초)
```

**계산 시점을 사용자가 보는 시점에서 떼어냈다.** 변경 전 7일간 98회 호출 중 1건은 60초를
넘겨 폴링 타임아웃으로 실패했는데, 그 경로 자체가 없어졌다.

| 얻음 | 잃음 → 대응 |
|---|---|
| 화면에서 AI 대기가 사라짐 (11.5초 → 0.05초) | 결과가 조금 오래됨 → **승인 시 충돌 재검사** |
| AI가 실패해도 화면은 멀쩡 (카드만 없음) | 계산 안 한 딜은 카드 없음 → **백필 스크립트** |
| 호출 횟수가 화면 진입 횟수와 무관해짐 | |

## 2.2 언제 계산하나 — 트리거 4가지

| 트리거 | 접점 | 왜 이때인가 |
|---|---|---|
| 보고서 확정 | `POST /reports/{id}/submit` | 새 근거가 생겼다 |
| 일정 수동 등록 | `POST /activities` (AI 미경유) | 이 딜이 한 번도 계산 안 됐을 수 있다 |
| 딜 생성·단계 이동 | `POST /sales-deals`, `.../move` | 상황이 달라졌다 |
| CS 처리 시작 | `POST /support-requests/{id}/transition` | 위험 신호와 같은 조건이다 |

**넷 다 영업 건 하나를 정확히 가리킨다.** 어느 딜을 계산할지가 이미 정해져 있어,
여러 딜 중 고르는 0차 선별이 캘린더 경로에서는 필요 없다(3.4).

## 2.3 전체 흐름

```text
트리거 발생 ─── 커밋 직후 큐잉만. 응답을 기다리지 않는다.
    ▼
[백그라운드]
 ① 자리 선점        잠금 + 쿨다운으로 중복 실행 차단
 ② 입력 준비        위험 신호를 규칙으로 계산 (트리거 딜만)
 ③ 계약관리         🤖 AI 1회 — 왜 만나야 하는지 + 언제쯤
 ④ 일정관리         🤖 AI 2회 — 구체적 날짜·시간 최대 10개
 ⑤ 서버 재검증 후 저장
    ⋮
    ⋮   여기서 끊긴다. 며칠 뒤에 봐도 된다.
    ⋮
[사용자가 캘린더를 열 때]
    저장된 카드 조회  ← 🤖 AI 호출 없음
    시간 후보 선택 → 승인
    ▼
 ⑥ 일정 등록 + 카드 선점 (한 트랜잭션)
 ⑦ 계약관리         🤖 AI 3회 — 미팅 전에 볼 브리핑
```

# 3부. 각 단계

## 3.1 계약관리 — 다음 미팅 제안

| | |
|---|---|
| `agent_code` | `contract_management_next_meeting` |
| 입력 | 고객사, 딜과 계약 단계, **위험 신호**, 최근 확정된 보고서 |
| 출력 | 위험 목록, 부족한 정보, 추천 행동, 미팅 이유·선호 기간·소요 시간 |

### 위험 신호는 AI가 만들지 않는다

```
[서버]  날짜를 계산     "계약 15일 남음, 견적 3일 남음"   ← 뺄셈. 틀릴 수 없다.
   ↓
[AI]    신호를 해석     "견적이 급하니 이번 주에 만나세요"  ← 판단. AI의 몫.
```

만료일 비교는 규칙으로 정확히 되는 일이고, **AI는 오늘이 며칠인지도 정확히 모른다.**
그래서 숫자는 서버가 만들고 AI는 해석만 한다.

| 신호 | 조건 | 심각도 | 값의 출처 |
|---|---|---|---|
| `contract_expiring` | 계약 만료 30일 이내 | 7일 이내 high | 사람 입력 |
| `quote_expiring` | 견적 유효기간 14일 이내 | 3일 이내 high | 사람 입력 |
| `delivery_delay_risk` | 예상 납품일 지남 | high | 사람 입력 |
| `contract_revisit_due` | 계약 체결 7일 경과 | 14일 경과 시 high | 사람 입력 |
| `follow_up_overdue` | 마지막 접촉 30일 경과 | — | **시스템 관찰** |
| `unresolved_support` | 미해결 C/S 있음 | 긴급이면 high | **시스템 관찰** |

### 이 신호들의 한계

**여섯 중 넷은 사람이 입력한 날짜**를 읽는다. 시스템이 스스로 아는 값이 아니다.

| 문제 | 예 |
|---|---|
| 비어 있으면 감지 못 함 | 예상 납품일을 안 넣으면 실제로 늦어져도 신호가 없다 |
| 끝난 일을 모름 | 납품을 마쳐도 날짜가 지났으면 신호가 남는다 (딜을 닫으면 빠짐) |
| 입력이 틀리면 신호도 틀림 | 잘못 넣은 날짜가 그대로 위험으로 잡힌다 |

**이 시스템의 추천 품질은 딜 입력 품질과 함께 간다.** 개선 방안은
[입력품질 개선안](./계약_일정_에이전트_입력품질_개선안.md)에 따로 정리했다.

### 신호가 없어도 실행한다

**트리거 경로에서는 위험 신호가 하나도 없어도 AI를 부른다.** 트리거 자체가 실행 이유이기
때문이다 — "이 딜에 무슨 일이 생겼다"가 이미 확인된 사실이라 다시 거를 이유가 없다.

반면 0차 선별(3.4)은 여러 딜 중 고르는 단계라, 근거 없는 딜을 후보에 올리지 않는다.
**같은 규칙인데 쓰임이 다르다.**

### 입력은 딜 하나로 좁힌다

한 고객사에 딜이 둘일 수 있다.

```
A병원 ├─ 딜 X  가격 협상 중        ← 트리거된 딜
      └─ 딜 Y  계약 임박, 위험 있음
```

회사 전체를 보내면 AI가 더 급해 보이는 **딜 Y를 답할 수 있다.** 그 답을 딜 X의 제안으로
저장하면 **이름은 X, 내용은 Y**가 된다. 예외도 로그도 안 남고 화면상 정상으로 보인다.

두 겹으로 막는다 — ① 트리거 딜만 보낸다 ② 답의 딜 번호가 다르면 버린다.

## 3.2 일정관리 — 시간 후보 추천

| | |
|---|---|
| `agent_code` | `schedule_management` |
| 입력 | 딜 ID, **선호 기간**, 소요 시간, 미팅 이유, **담당자의 기존 일정** |
| 출력 | 시간 후보 최대 10개, 충돌 정보 |

> **선호 기간**은 시간을 찾아볼 *범위*다. 미팅 길이가 아니다.
> "9월 1일 ~ 9월 10일 사이에서 60분짜리를 찾아라"에서 앞이 선호 기간, 뒤가 소요 시간이다.

### AI 답을 그대로 쓰지 않는다

AI는 `"9월 5일(토) 20:00"`처럼 답할 수 있다. 그럴듯하지만 토요일이고 업무시간도 아니다.

```
AI 후보 10개 → 서버 검사 ├─ 09:00~18:00(KST) 밖 → 버림
                        ├─ 시작·끝이 다른 날짜  → 버림
                        └─ 이미 일정 있음      → "충돌"로 이동
             → 살아남은 것만
```

**최대 10개지만 항상 10개는 아니다.** 개수가 아니라 유효성이 기준이다.

### 왕복 협상은 없다

충돌이 있어도 계약관리에게 되묻지 않고 한 번의 실행으로 끝낸다. 실 데이터로 확인한 근거는
이렇다.

**측정 (완료된 일정관리 실행 89건)**

| 항목 | 결과 |
|---|---|
| 충돌이 기록된 실행 | 42건 (47.2%) |
| **후보가 0개인 실행** | **2건 (2.2%)** |

충돌은 절반 가까이 나지만 **후보가 다 사라진 경우는 2.2%뿐**이다. 되물어야 할 상황 자체가
드물다. 그리고 그 2건은 원인이 같았다 — 계약관리가 선호 기간을 **30분짜리 한 칸**으로 줬다.

| 계약관리가 준 기간 | 실행 | 평균 후보 | 후보 0개 |
|---|---:|---:|---:|
| 1시간 이하 (칸 하나) | 34건 | **2.0개** | **2건** |
| 없음 → 기본 7일 | 55건 | **4.0개** | 0건 |

**문제는 "되묻지 않아서"가 아니라 "칸 하나를 줘서"다.** 되물어 봐야 또 칸 하나를 줄 수
있어 원인이 남는다. 대신 프롬프트에 "기간을 넓게 주라"는 기준을 넣었고(`v2`), 같은 입력
30건 A/B에서 선호 기간 폭이 **약 30분 → 평균 10일**로 바뀌었다.

**후보가 0개면 제안을 저장하지 않아 카드가 뜨지 않는다** — 조용한 실패다. 알리는 방법은
7.3의 과제다.

## 3.3 계약관리 — 미팅 브리핑

| | |
|---|---|
| `agent_code` | `contract_management_briefing` |
| 입력 | 등록된 미팅, 고객사·딜, 확정된 보고서, 문서 요약 |
| 출력 | 계약 요약, 위험, 부족한 정보, 추천 행동, 사용한 자료 ID |
| 시점 | 일정 등록이 **성공한 뒤** |

미팅 직전에 "이 고객 상황이 어땠더라"를 다시 뒤지지 않게 하는 요약이다. 등록이 커밋되기
전에는 만들지 않고, 반대로 브리핑이 실패해도 **등록은 되돌리지 않고** 경고만 띄운다.

## 3.4 계약관리 — 제안 대상 선별 (0차, 캘린더에서는 안 씀)

| | |
|---|---|
| `agent_code` | `contract_management_select_candidates` |
| 입력 | 담당자가 맡은 **모든 열린 딜**의 단계와 위험 신호 |
| 출력 | 지금 챙길 딜 최대 10개 + 우선순위 + 고른 이유 |
| 쓰는 곳 | 백필 스크립트, `POST /agent-runs` 수동 실행 |

AI에게 보내기 전에 규칙으로 두 번 거른다 — **이미 앞으로 잡힌 일정이 있는 딜**과
**위험 신호가 하나도 없는 딜**은 뺀다. 개발 DB에서 열린 딜 173개 → **81개**로 줄었다.

**트레이드오프가 있다.** 규칙이 AI보다 먼저 판단해 버린다는 뜻이라, "계약 단계가 오래 멈춰
있다" 같은 조건은 신호 목록에 없어 AI가 볼 기회 자체가 없다. 담당자당 20~30개를 다 보내면
프롬프트와 비용이 그만큼 늘어 지금은 이 선택을 유지하고, 필요한 조건이 생기면 **신호 규칙을
늘리는 쪽**으로 대응한다.

# 4부. 에이전트끼리 어떻게 이어지나

## 4.1 직접 부르지 않는다

에이전트끼리 함수를 호출하지 않고 **`agent_run` 테이블을 통해 이어진다.**

| 컬럼 | 담는 것 |
|---|---|
| `agent_code` | 어떤 에이전트의 어떤 역할인가 |
| **`parent_run_id`** | **어느 실행을 이어받았나** ← 연결 고리 |
| `input_snapshot` / `output_snapshot` | AI에 보낸 입력과 받은 출력 그대로 |
| `source_refs` | 무엇이 이 실행을 촉발했나 |
| `status_code` | `queued` / `running` / `completed` / `failed` |

**왜 이렇게 하나** — ① 하나가 죽어도 다른 게 안 멈춘다 ② 입출력이 남아 "왜 이런 답이
나왔나"를 추적할 수 있다 ③ 지금 계산하고 사흘 뒤에 이어받아도 된다.

`parent_run_id`가 만드는 사슬(다음 미팅 제안 ← 시간 후보 ← 브리핑)을 거꾸로 따라가면
판단 근거를 알 수 있다. 다만 API가 이 필드를 안 내려줘 화면에서는 못 따라간다(7.3).

## 4.2 상태는 네 개뿐이다

```
queued → running → completed
                └→ failed
```

"위험 확인 중" 같은 세부 단계는 만들지 않았다. **선계산 구조에서는 사용자가 기다리지 않아
중간 상태를 볼 일이 없다.** 상태를 늘리면 저장·조회·표시 코드가 다 늘어난다.

## 4.3 다른 에이전트와의 경계

**① 보고서 작성 → 계약관리 (연결됨)**

사람이 "확정"을 누르면(`draft` → `submitted`) 그 **상태 변화가 트리거**가 된다. 직접 부르는
게 아니라 DB 상태로 이어진다. `draft` 보고서는 근거로 쓰지 않는다.

**② 자료요약 → 계약관리 브리핑 (연결됨)**

브리핑 스냅샷을 만들 때 `sales_context.retrieve_briefing_context()`로 자료실을 검색해
`document_context`를 채운다. 검색어는 고객사명·미팅 제목·딜 제목으로 결정적으로 조립하고,
범위는 **이 딜 또는 이 고객사**(OR)다 — 자료는 딜에만 붙기도 하고 고객사에만 붙기도 한다.

문서 본문은 LLM 입력 JSON에 싣지 않는다. 자료실 파일은 외부에서 받은 문서라 안의 문장이
지시문으로 읽히면 안 되므로, `to_briefing_prompt_block()`이 만드는 `<document_context>`
경계 블록으로 감싸 이어 붙인다(5부). 브리핑이 낸 출처 중 실제로 조회되지 않은 문서는
서버가 버린다.

> 검색이 실패하거나 관련 자료가 없어도 브리핑은 그대로 만든다 — 문서 근거가 필요한
> 항목만 "부족한 정보"로 남는다. "앞 단계 데이터가 없어도 최소 동작해야 한다"는 원칙이다.

**③ 미팅 분석** — 같은 보고서를 보고 각자 실행될 뿐 데이터를 주고받지 않는다.

## 4.4 카드 상태는 따로 저장한다

`agent_run`은 "무슨 일이 있었나"의 기록이고, "지금 캘린더에 뭘 보여줄까"는 다른 질문이라
얇은 표를 따로 뒀다.

```sql
contract_next_meeting_suggestion
  sales_deal_id               UNIQUE   -- 딜 하나에 활성 카드 하나
  schedule_management_run_id           -- 내용은 여기로 찾아간다
  status_code   pending | dismissed | accepted
```

**날짜·시간·사유는 복사하지 않는다.** 같은 사실을 두 곳에 두면 언젠가 어긋난다.

# 5부. 안전장치

AI를 쓰는 시스템에서 실제로 터지는 문제들이다. 각각 **어디서 막는지** 정리한다.

## 5.1 없는 걸 지어내는 문제 (환각)

| 상황 | 막는 방법 | 어디서 |
|---|---|---|
| 근거 없는 날짜를 만듦 | 만들지 말고 **비워두게** 지시 | 프롬프트 |
| 확인 안 되는 정보 | "부족한 정보"에 넣게 지시 | 프롬프트 + 출력 형식 |
| 엉뚱한 딜을 답함 | 딜 번호가 다르면 **버림** | 서버 |
| 주말·업무시간 밖 | **버림** | 서버 |
| 이미 찬 시간 | 후보에서 빼고 "충돌"로 | 서버 |

**실측** — 실제 데이터로 만든 시간 후보 **266개를 전수 검사**했다. 과거 0개, 주말 0개.

## 5.2 시간 처리

AI는 오늘이 며칠인지 정확히 모른다. **현재 날짜를 함께 주고, 답을 다시 검증한다.**

| 검사 | 조치 |
|---|---|
| 끝나는 시각이 이미 지남 | 기본 범위(오늘부터 7일)로 |
| 시작이 이미 지남 | 현재 시각으로 당김 |
| 시작이 끝보다 늦음 | 기본 범위로 |
| 시간대가 안 붙은 문자열 | **UTC로 못 박고 그 값을 이후 단계에 넘김** |

**마지막이 특히 중요하다.** 원본 문자열을 그대로 흘리면 이쪽은 UTC로, `contract_management`는
Asia/Seoul로 읽어 **같은 글자가 9시간 다르게 해석된다.**

## 5.3 중복 실행과 비용

트리거 한 번이 **AI 호출 두 번**이다. 칸반에서 딜을 연달아 옮기면 트리거가 몰린다.

| 겹 | 방법 | 막는 시점 |
|---|---|---|
| 1 | 같은 딜은 10분 안에 다시 안 돌림 | AI 부르기 전 |
| 2 | **DB 잠금** — 동시에 둘이 와도 하나만 통과 | AI 부르기 전 |
| 3 | 저장할 때 `sales_deal_id` UNIQUE | AI 부른 뒤 |

**2겹이 왜 필요한가** — 1겹만 있으면 두 작업이 모두 "최근 실행 없음"으로 판단해 각자
AI를 태운다. 중복은 3겹이 걸러 내지만 **그때는 이미 비용이 나간 뒤다.**

## 5.4 승인 경합

승인 버튼을 연달아 누르거나 두 탭에서 함께 누르면 요청이 겹친다. **순서를 바꿔서 막는다.**

```
[전]  일정 저장 → "이 추천 썼음" 표시     두 요청이 모두 통과 → 일정 두 개
[후]  "내가 쓸게" 잠그기 → 일정 저장      두 번째는 여기서 막힘 → 409
```

> 🎫 표를 뽑고 나서 좌석을 예약 표시하면 두 명이 같은 자리에 앉는다. **먼저 잠그고** 뽑아야
> 한다.

**잠금만으로는 부족하다.** 잠금은 순서만 세우고 권한은 보지 않아, 조회 조건에 팀과 담당자
범위를 함께 건다. 안 그러면 실행 번호를 아는 사람이 남의 팀 카드를 내려버릴 수 있다.

| 방어 | 방법 |
|---|---|
| 중복 등록 | 등록 **앞에서** 행 잠금, 두 번째는 `409` |
| 권한 | 조회 조건에 팀 + (일반 담당자면) 딜 소유자 |
| 뒤늦은 충돌 | 승인 시점에 겹침 재검사 → 경고 (등록은 막지 않음) |
| 브리핑 중복 | 같은 일정에 같은 키가 나오게 해 중복 생성 차단 |

## 5.5 개인정보

**AI에게 보낼 것을 허용 목록으로 정한다.** 목록에 없으면 안 나간다.

| 보내지 않는 것 | 대신 |
|---|---|
| 이메일 | — |
| 내부 담당자 ID | 서버가 로컬에서 충돌 계산할 때만 사용 |
| 기존 일정의 제목·참석자 | **시작·종료 시각과 종일 여부만** |

## 5.6 실패 격리

**AI 실패가 사용자의 원래 작업을 되돌리지 않는다.**

```
보고서 확정 → 커밋 → 파이프라인   실패해도 보고서는 확정된 채로
일정 등록  → 커밋 → 브리핑 큐잉   실패해도 일정은 등록된 채로
```

실패는 `agent_run.status_code = failed`와 `error_message`로 남는다.

# 6부. 관통하는 원칙

지금까지의 모든 결정이 한 문장에서 나온다.

> ## **AI는 판단만 하고, 확인할 수 있는 것은 기계가 확인한다.**

```
DB → 규칙으로 입력 준비 → 🤖 AI 판단 → 규칙으로 검증 → DB
     └─── 기계 ───┘      └ 사람 몫 ┘   └─── 기계 ───┘
```

에이전트를 둘로 나눈 것(1.2), 위험 신호를 규칙으로 계산한 것(3.1), AI 답을 재검증하는
것(3.2), 허용 목록으로 입력을 통제하는 것(5.5)이 전부 이 원칙의 적용이다.

# 7부. 범위와 향후

## 7.1 이번에 만든 것

- 네 트리거에서 "미팅 제안 → 시간 후보"를 뒤에서 이어 실행하고 저장하는 파이프라인
- 중복 실행 3중 방어 (쿨다운 · DB 잠금 · UNIQUE)
- 저장된 카드 조회·닫기 API, 캘린더 AI 추천 패널 (시간 후보 선택, 승인, 충돌 경고)
- 일정 등록 → 브리핑 자동 실행, 카드 상태 전이, 미팅 상세의 브리핑 표시
- 자료요약 RAG 연결: 브리핑 근거 조회, 경계 블록 주입, 출처 검증과 화면의 `📎 근거 자료`
- 기존 딜 일괄 계산 백필 스크립트

## 7.2 만들지 않은 것

| 제외 | 왜 |
|---|---|
| 계약↔일정 왕복 협상 | 원인이 다른 데 있다(3.2) |
| 사용자 선호 학습 | 데이터가 아직 없다 |
| 세분화된 실행 상태 | 사용자가 기다리지 않아 볼 일이 없다 |
| 참석자 가용성·초대장 | 외부 캘린더 연동이 선행 |
| 브리핑 재실행 버튼 | 같은 입력이면 같은 결과다 |

## 7.3 향후 확장

| 항목 | 내용 | 근거 |
|---|---|---|
| **좁은 선호 기간 방어** | 프롬프트로 넓게 주게 했으나(`v2`), 좁게 오면 서버가 넓히는 규칙이 아직 없다 | 3.2 측정 |
| **후보 0개를 알리기** | 지금은 카드가 안 뜨고 끝난다 — 조용한 실패다 | 3.2 측정 |
| **위험 신호 자동화** | 여섯 중 넷이 사람 입력에 기댄다 | [입력품질 개선안](./계약_일정_에이전트_입력품질_개선안.md) |
| 판단 근거 역추적 | `parent_run_id` 사슬을 화면에 노출. API가 이 필드를 내려주는 것이 선행 | — |
| 0차 선별 연결 | "왜 이 딜을 골랐는지"까지는 사슬이 안 이어진다 | — |
| 장기 메모리 · RAG | 선호 시간대, 계약 단계별 권장 후속 시점 | — |
