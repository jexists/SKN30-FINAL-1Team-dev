# AI 브리핑·관련자료 개선 구현 계획

작성일: 2026-09-13
대상: [이슈 #171](https://github.com/jexists/SKN30-FINAL-1Team-dev/issues/171) 중 [박지유] 일정 상세
상태: 구현 전 계획.

## 0. 이 문서의 위치

[자동 갱신 구현 계획](./브리핑_자동갱신_구현계획_refresh.md)은 **"언제 다시 만드나"**를 다룬다.
이 문서는 이슈 #171이 물은 **"무엇을 어떻게 보여주나"**를 다룬다. 아래에서 그 문서를
**자동 갱신 계획**이라고 부른다.

겹치는 지점이 하나 있다. **관련자료 미노출 버그의 원인 중 하나를 자동 갱신 계획이 고친다**
(1장 원인 ③). 그래서 이 문서의 C단계는 그 결과에 의존한다.

## 1. 먼저 버그 원인 — 코드로 확인한 것

이슈의 테스트 시나리오 두 개를 develop 코드로 추적했다.

| 시나리오 | 추적 결과 |
| --- | --- |
| 일정 생성 → 영업현황 등록 → 자료실에 **상품** 연결 → 일정 클릭 | **안 나온다.** 재현되는 버그 |
| 일정 생성 → 영업현황 등록 → 자료실에 **딜** 연결 → 일정 클릭 | **나와야 정상.** 코드에 조건이 이미 있다 |

원인은 셋으로 갈린다. 성격이 달라서 고치는 방법도 다르다.

| 원인 | 무엇이 문제인가 | 해결 방향 | 단계 |
| --- | --- | --- | --- |
| ① 상품 범위 공백 | 미팅에 딜이 없으면 딜 상품 자료를 못 찾는다 | **버그가 아니라 명세로 확정.** 화면에 안내를 넣는다 | A |
| ② 처리 중 표시 없음 | 자료는 정상인데 아직 처리 중이라 안 보인다 | 목록에 처리 중 상태를 드러낸다 | A |
| ③ 스냅샷에 갇힘 | 아직 일어나지 않았다. 방향을 잘못 잡으면 생긴다 | 자동 갱신이 들어간 뒤에 옮긴다 | C |

①·② 는 지금 고칠 것이고, ③ 은 **만들지 않도록 순서를 지키는 것**이다. ① 과 ② 는 확정된
결과로 **둘 다 백엔드 조회 범위를 바꾸지 않고 화면만 고친다.**

### 원인 ① 미팅에 딜이 안 걸려 있으면 딜 상품 자료를 못 찾는다 — 명세로 확정

`activity_documents._product_ids`는 `activity.sales_deal_id`가 없으면 **딜 대표 상품과 견적
품목을 아예 보지 않고 돌아간다.** 미팅 자신의 `product_id`만 남는다.

일정을 먼저 만들고 영업 건을 나중에 만드는 순서에서는 미팅에 딜이 안 걸려 있다. 그래서
딜에 상품이 있어도, 자료가 그 상품에 연결돼 있어도 범위가 빈 집합이 된다. 미팅에 상품을
직접 골라 두지 않았다면 상품 자료가 영구히 안 보인다.

**해결 방향 — 이 동작을 명세로 확정하고, 화면이 그렇게 안내한다(확정).**

고객사를 거쳐 상품 범위를 넓히는 안도 검토했으나 채택하지 않았다. 범위가 넓어지면 이 미팅과
무관한 딜의 상품 자료까지 딸려오고, "왜 이 자료가 여기 있나"를 설명할 수 없다. 대신 **범위를
좁게 두고 사용자가 직접 연결하게** 한다.

- `_product_ids` 는 **고치지 않는다.** 딜이 없으면 미팅 자신의 `product_id` 만 본다.
- 미팅에 딜도 상품도 없으면 화면에 **"영업 건을 연결하면 관련 상품 자료가 함께 표시됩니다"**
  를 안내하고, 연결로 바로 갈 수 있게 한다.
- 빈 목록을 그냥 두지 않는다. **"자료가 없다"와 "연결이 안 돼 못 찾는다"는 다른 상태**이고,
  지금은 둘 다 똑같이 비어 보인다.

미팅에 상품만 직접 골라 둔 경우는 지금처럼 그 상품의 자료가 나온다(2장에서 "포함"으로 확정).

### 원인 ② 딜 연결 자료는 나와야 한다 — 안 나왔다면 파일 처리 중이었을 가능성

`document_scopes`에 **고객사 경유 조건**이 이미 있다. 자료가 딜 D 에만 걸려 있어도, 미팅의
고객사가 D 의 고객사라면 `Document.sales_deal_id IN (그 고객사의 딜들)` 로 잡힌다.

그런데 목록은 `processing_status == 'completed'` 인 파일만 본다. 자료실 업로드는 백그라운드
OCR·요약이라 **등록 직후 일정을 클릭하면 아직 완료가 아니어서 안 보인다.**

이건 버그가 아니라 **표시 부재**다. 화면이 "처리 중"을 알려주지 않아 사라진 것처럼 보인다.

> 재현할 때 파일의 처리 상태를 먼저 확인해야 한다. 시나리오 2 가 실제로 안 나왔다면 이쪽이
> 유력하다.

**해결 방향 — 없는 것과 아직 안 된 것을 구분해 보여준다.** 지금은 완료된 파일만 목록에
넣으므로 둘 다 똑같이 빈 목록이다. 처리 중인 파일이 있으면 목록에 상태를 함께 내보내
`처리 중` 으로 표시하고, 처리에 실패한 파일도 조용히 사라지지 않게 한다.

**조회 범위 자체는 바꾸지 않는다.** 완료되지 않은 파일은 본문이 없어 브리핑 근거로 쓸 수
없다. 표시만 더하는 것이라 위험이 작고 ① 과 같은 A 단계에 넣는다.

### 원인 ③ 관련자료를 브리핑 근거로 옮기면 스냅샷에 갇힌다

관련자료를 브리핑 실행 결과에서 가져오게 바꾸면, 미팅 등록 때 한 번 만든 스냅샷에 고정된다.
그 뒤에 올린 자료는 브리핑을 다시 만들기 전까지 나오지 않는다.

**해결 방향 — 순서를 지킨다.** 이 원인은 아직 일어나지 않았다. 관련자료를 브리핑 근거로
옮기는 변경을 자동 갱신보다 먼저 넣으면 그때 생긴다.

- **자동 갱신 전까지** 관련자료는 지금처럼 실시간 조회로 둔다(`GET /activities/{id}/documents`).
  느리지도 않고, 오히려 항상 최신이다.
- **자동 갱신이 들어간 뒤** 브리핑 근거로 옮긴다. 자료를 올리면 지문이 바뀌어 브리핑이 다시
  만들어지므로 스냅샷이 굳지 않는다.

그래서 이 문서의 C 단계는 자동 갱신 계획에 의존한다(7장). 두 변경을 한 PR 에 섞지 않는다.

### 화면 선행 조건 — 자동 갱신 완료를 드로어가 따라가야 한다

2026-09-13 로컬 화면 테스트에서 자동 갱신 API 응답과 화면 상태 전환이 어긋난 것을 확인했다.
서버는 이전 성공 브리핑을 게시하면서 최신 실행이 돌고 있으면 다음처럼 응답한다.

```json
{
  "status": "completed",
  "content": { "contract_summary": "이전 성공 브리핑" },
  "refreshing": true,
  "refresh_error": null
}
```

`status` 는 **화면에 게시할 성공본의 상태**이고, `refreshing` 은 **그 뒤 최신 실행의 상태**다.
따라서 화면이 `status == queued/running` 만 보고 재조회하면 위 응답에서는 폴링을 시작하지 않는다.
결과적으로 새 브리핑이 완성돼도 드로어를 닫았다 다시 열기 전까지 이전 본문과 `최신 자료 반영 중`
표시가 남는다. 관련자료를 브리핑 스냅샷으로 옮기는 C 단계까지 진행하면 새 자료가 처리돼도 같은
화면에 반영되지 않아 원인 ③을 다시 만들게 된다.

**해결 방법 — `useAiBriefing` 을 게시 상태와 갱신 상태가 분리된 조회 전용 훅으로 바꾼다.**

- 상세 진입 시 `GET /activities/{id}` 를 한 번 호출하고, 브리핑이 없어도
  `POST /agent-runs` 를 보내지 않는다. 생성 책임은 서버 트리거와 worker 에만 둔다.
- 최초 응답의 `ai_briefing.refreshing === true` 일 때만 5초 간격으로 같은 GET을 반복한다.
  `status` 는 폴링 조건으로 쓰지 않는다.
- 폴링 중에는 `loading` 으로 되돌리지 않고 마지막 성공 `content` 를 계속 표시한다.
- 재조회 결과 `refreshing !== true` 가 되면 마지막 응답으로 교체하고 폴링을 끝낸다. 성공이면
  새 본문이 보이고, 실패이면 이전 본문과 `refresh_error` 안내가 함께 보인다.
- 드로어를 닫거나 다른 일정으로 이동하면 타이머와 늦게 도착한 응답을 취소한다.
- 최초 GET 실패만 기존 오류 영역에 표시한다. 갱신 중 일시적인 조회 실패가 이미 보이던 본문을
  가리지 않도록 마지막 성공 상태를 보존하고, 드로어가 열려 있으면 5초 뒤 GET을 다시 시도한다.
  구현은 `AbortController`와 취소 가능한 타이머를 함께 써서 닫힌 뒤 요청이나 타이머가 남지 않게
  한다.

따라서 **C 단계의 선행 조건은 백엔드 자동 예약만이 아니라 위 화면 전환까지 포함한 자동 갱신
완료**다. 이 조건을 만족하기 전에는 관련자료 조회를 브리핑 스냅샷으로 옮기지 않는다.

## 2. 관련자료 정의

이슈가 "정의 필요"라고 남긴 부분이다. 아래를 결정안으로 제시한다.

| 대상 | 포함 | 근거 |
| --- | --- | --- |
| 이 미팅의 딜에 연결된 자료 | **포함** | 가장 직접적인 근거다 |
| 이 미팅 고객사의 **진행 중** 딜에 연결된 자료 | **포함** | 자료실 업로드 화면이 고객사 칸을 주지 않아, 딜 경유가 실질적으로 유일한 고객사 판정 경로다 |
| 딜 대표 상품·견적 품목에 연결된 자료 | **포함하되 "제품 자료"로 분리 표시** | 카탈로그·스펙처럼 고객사와 무관한 공용 자료다. 섞으면 어느 쪽이 이 고객사 것인지 알 수 없다 |
| 미팅에만 지정된 상품의 자료 | **포함 (확정)** | 인사차 방문·신규 탐색 미팅에도 상품 자료가 필요하다. 지금 코드가 이미 그렇게 동작하고, 제품 자료로 분리 표시하므로 섞이지 않는다 |
| 같은 팀의 연결 없는 자료 | 제외 | 범위가 무한해진다 |

이슈 상단 공통 항목인 **"회사에 매핑된 관련 딜 가져오는 기준"**도 정해졌다. **진행 중 딜만
본다** — 지금 `_open_deals` 의 `phase_code != 'closed'` 를 그대로 둔다. 종료·실패 딜의 자료는
근거로 쓰지 않는다. 그 대가는 8장에 적었다.

**원인 ① 의 처리 방향은 확정됐다.** 미팅에 딜이 없을 때 고객사를 거쳐 범위를 넓히지 않고,
"영업 건을 연결해야 딜 상품 자료가 나온다" 를 명시된 동작으로 둔다. 화면이 그 사실을
안내한다(1장 원인 ①).

## 3. RAG를 어떻게 쓰는지

- **관련 자료**는 키워드 점수와 pgvector 코사인 검색을 합쳐 **상위 5개 청크**를 고른다.
  임베딩을 쓸 수 없으면 키워드만 쓴다.
- **검색어**는 `고객사명 + 미팅 제목 + 이 미팅 딜의 제목 + 미팅 메모`이고, 상품이 있으면 상품명을
  덧붙인다. 별도 LLM 이 검색어를 만들지 않는다.
- **제품 자료는 RAG 가 아니다.** 연결 관계로 바로 조회하고 개수 제한도 없다.

추가로 할 일은 **화면에 그 구분이 보이게 하는 것**이다. 관련 자료에는 `RAG 검색` 표시와
페이지·발췌를 붙이고, 제품 자료에는 붙이지 않는다.

## 4. 브리핑 형식

브리핑은 지금도 다섯 가지를 내놓는다. **그런데 화면이 그중 절반만 쓴다.**

| 필드 | 내용 | 화면에 |
| --- | --- | --- |
| `contract_summary` | 본문 문단 | 나온다 |
| `risks` | 주의사항. 코드·심각도·**설명 문장**·근거 | **라벨만 나온다** |
| `recommended_actions` | 해야 할 일 목록 | 나온다 |
| `missing_information` | 확인되지 않은 값 | **안 나온다** |
| `source_refs` | 본문이 인용한 자료 | **안 나온다** |

이슈가 원한 형식과 대조하면 이렇다. **셋은 화면만 고치면 되고, 하나만 브리핑 생성을 바꿔야
한다.**

| 이슈가 원한 항목 | 지금 | 할 일 | 어디를 고치나 |
| --- | --- | --- | --- |
| 미팅에서 달성해야 하는 것 | **없다** | 출력 필드를 새로 만든다 | **프롬프트 + 스키마** |
| 미팅시 주의사항 | `risks[].message` 로 **이미 받고 있는데** 화면이 라벨만 보여준다 | 받은 문장을 그대로 보여준다 | 화면 |
| 추가로 해야 하는 액션 | `recommended_actions` | 그대로 쓴다 | — |
| 근거를 관련자료로 표시 | `source_refs` 는 있는데 자료 줄과 연결이 없다 | 인용 표시를 자료 줄에 건다 | 화면 |

### 왜 첫 줄만 뒤로 미루나

"달성해야 하는 것"을 새로 받으려면 **브리핑을 만드는 지시문(프롬프트)과 받아쓰는 틀(스키마)을
같이 바꿔야 한다.** 그건 브리핑을 *언제* 만드느냐가 아니라 *무엇을* 만드느냐를 바꾸는 일이다.

자동 갱신 계획은 **"브리핑 생성 자체는 손대지 않는다"**를 전제로 서 있다. 언제 만드는지만
바꾸니까, 브리핑이 이상해지면 원인을 예약·실행 쪽으로 좁힐 수 있다. 여기서 프롬프트까지 같이
바꾸면 **갱신이 잘못 돈 건지 프롬프트를 바꾼 탓인지 가릴 수 없다.**

프롬프트를 바꾸면 버전도 올려야 하고, 그러면 **예전 형식으로 만든 브리핑과 새 형식이 한동안
섞인다.** 자동 갱신이 돌면서 하나씩 새 형식으로 바뀌는 셈이라, 갱신이 안정된 뒤에 하는 편이
뒤탈이 적다.

**나머지 셋은 기다릴 필요가 없다.** 백엔드가 이미 보내는 값을 화면이 안 쓰고 있을 뿐이라,
자동 갱신과 무관하게 먼저 할 수 있다.

화면 쪽 — 이슈의 "딱 봤을 때 눈에 띄는 디자인"은 이렇게 잡는다.

- 주의사항을 본문 위에 배치하고, 없으면 영역 자체를 숨긴다.
- 본문은 문단 텍스트 그대로 두되 확인이 필요한 값은 지금처럼 강조 표시를 유지한다.
- 달성 목표와 액션은 체크 가능한 목록 모양으로 구분한다.

## 5. 관련 자료가 많을 때

- **문서 단위로 묶는다.** 같은 문서에서 여러 청크가 걸리면 한 줄로 모으고 발췌는 기본 하나만
  펼친다.
- **상위 몇 개만 펼치고 나머지는 접는다.** 지금도 상위 5개 청크라 문서 수는 그보다 적지만,
  제품 자료는 개수 제한이 없어 길어질 수 있다.
- **정렬 기준을 정한다.** 검색 점수 순인지 최근 등록 순인지. 관련 자료는 점수, 제품 자료는
  등록 순이 자연스럽다.

## 6. 적합성 판단 기준과 결과 평가

평가표 골격은 이미 [detail.md](../../ppt/contract_schedule/detail.md) 9장에 있다. 이 작업은
그 표를 **채우는 것**이다.

- 합성 딜과 정답 근거를 만들어 대조한다. 없는 계약 조건 생성, 다른 딜 정보 혼입, 근거와 다른
  출처를 중대 오류로 분류한다.
- 4장의 형식 변경이 끝난 뒤에 측정해야 의미가 있다. 항목이 달라지면 기준도 달라진다.
- 실제 고객 데이터로 평가하지 않는다.

## 7. 단계 구분

| 단계 | 내용 | 선행 조건 |
| --- | --- | --- |
| **A** | 원인 ①·② 처리 — 딜 미연결 안내, 처리 중 상태 표시. **둘 다 화면 작업이고 조회 범위를 바꾸지 않는다** | 없음 |
| **B** | 관련자료 정의를 코드 범위에 반영 | 없음. 2장이 확정됐다 |
| **C** | 원인 ③ 해소 | 자동 예약 + `refreshing` 기준 화면 재조회까지 완료된 자동 갱신 |
| **D** | 관련 자료 다수 UX (5장) | B |
| **E1** | 화면이 이미 받은 값을 쓴다 — 주의사항 문장, 확인되지 않은 값, 근거 연결 (4장) | 없음. 백엔드를 건드리지 않는다 |
| **E2** | "달성해야 하는 것" 출력 필드 추가 (4장) | C. 프롬프트 버전을 올린다 |
| **F** | 평가 기준 채우기 (6장) | E2 |

A·B 를 먼저 하는 이유는 **정의와 버그가 사용자가 지금 겪는 문제**이고, 형식 변경보다 위험이
작기 때문이다. **확인받을 것이 모두 정해져(8장) A·B 는 바로 시작할 수 있다.**

E1 은 백엔드를 건드리지 않아 언제든 넣을 수 있고, E2 는 프롬프트를 바꾸므로 자동 갱신이
안정된 뒤에 한다.

## 8. 확정된 결정

**막혀 있는 것은 없다. 네 항목 모두 정했다.**

| 항목 | 결정 | 근거 |
| --- | --- | --- |
| 미팅에만 지정된 상품의 자료 (2장) | **포함한다** | 인사차 방문·신규 탐색 미팅에도 상품 자료가 필요하다. 지금 코드가 이미 그렇게 동작하고, 제품 자료로 분리 표시하므로 섞이지 않는다 |
| 원인 ① 처리 방향 (1장) | **명시된 동작으로 둔다** | 범위를 넓히지 않는다. 화면이 "영업 건을 연결하면 관련 상품 자료가 함께 표시됩니다" 를 안내한다 |
| 종료된 딜의 자료 (2장) | **쓰지 않는다. 진행 중 딜만 본다** | 지금 `_open_deals` 동작을 유지한다. 종료 딜까지 열면 오래된 딜이 쌓일수록 자료가 늘고, "몇 년 치까지" 를 다시 정해야 한다 |
| 형식 변경 시점 (4장) | **자동 갱신 뒤에 한다** | 프롬프트 버전을 올리면 옛 형식과 새 형식이 섞인다. 자동 갱신이 먼저 돌고 있어야 미팅 하나씩 새 형식으로 교체된다. 문제가 생겨도 원인을 가릴 수 있다 |

세 번째 결정에는 **아는 대가가 있다.**

> **재계약·갱신 미팅에서 직전 계약 자료가 근거로 나오지 않는다.** 그 딜은 이미 `closed` 라
> 범위 밖이기 때문이다. 이번에는 범위를 좁게 두고, 실제로 불편이 드러나면 "최근 N 년 종료 딜"
> 같은 조건으로 따로 검토한다. 지금 열어 두면 기준 없이 범위만 넓어진다.

네 번째 결정의 실행 조건은 하나다. **형식 변경과 자동 갱신을 같은 배포에 넣지 않는다.**
자동 갱신을 먼저 내보내 안정된 것을 확인한 뒤 형식을 바꾼다.
