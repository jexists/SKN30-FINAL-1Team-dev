# 미팅분석 → 보고서작성 → 계약관리 → 일정관리 Agent 흐름

> 원본 다이어그램은 [SalesLuv_멀티에이전트_운영_플로우.html](SalesLuv_멀티에이전트_운영_플로우.html)이다. 이 문서는 그 다이어그램 중 미팅분석·보고서작성·계약관리·일정관리 4개 Agent가 이어지는 부분을, 개발자와 Agent(코딩 에이전트)가 순서대로 따라가며 읽을 수 있도록 글로 풀어 쓴 것이다. 자료요약 Agent는 계약관리 Agent가 브리핑을 만들 때 RAG로 조회하는 접점만 5단계에서 다루고, 자료실 문서를 요약하는 자체 흐름은 다루지 않는다.
>
> 정확한 Input/Output/Model 정의가 이 문서와 다이어그램이 어긋나면 다이어그램을 기준으로 삼는다. 계약관리 Agent의 실제 구현 결정과 근거는 [계약관리_Agent_MVP_ADR.md](계약관리_Agent_MVP_ADR.md)를 본다.

## 단계별 설명

### 1. 미팅분석 Agent — 미팅 원문을 구조화한다

- **Input**: 녹음 파일(STT), 미팅 내용 메모, 직접 입력 중 하나
- **Output**:
  - C/S 사항 — 보고서 Agent와 C/S 관리 페이지가 공통으로 쓴다
  - 딜 특성 구조화 — 승인권자·예산·경쟁사·니즈 4가지
  - 계약가능성 분류(M) — ML 모델이 위 딜 특성을 입력받아 `계약가능성 높음` / `계약가능성 주의` 두 가지로 판정하는 참고 지표(`Won` 예측 확률 0.5 기준). 승인 절차 없이 화면에 표시만 된다([딜_승산_점수_데이터_전처리_및_AI_학습_모델.md](딜_승산_점수_데이터_전처리_및_AI_학습_모델.md) 참고)
- 이 Agent의 분석 결과는 보고서작성 Agent로 넘어간다. 미팅 원문 자체도 "원문 참조"로 보고서작성 Agent에 함께 전달된다(점선 — 분석 결과와 달리 필수 입력은 아니고 참고용).

### 2. 보고서작성 Agent — 초안을 만들고, 사람이 승인해야 완성된다

- **Input**: 미팅분석 Agent의 분석 결과(필수) + 미팅 원문(참조)
- **처리**: C/S 사항을 포함한 보고서 초안을 생성한다.
- **사람 확인 지점**: 사용자가 초안을 수정하고 승인해야 "보고서 완성" 상태가 된다. **승인 전 초안은 계약관리 Agent로 넘어가지 않는다** — 승인이라는 게이트를 반드시 통과해야 다음 단계 입력이 된다.
- **Output**: 보고서 완성 → 계약관리 Agent의 입력(`I`)이 된다.

### 3. 계약관리 Agent — 승인된 보고서 + 계약 활동을 결합해 다음 미팅을 제안한다

- **Input**:
  - 보고서작성 Agent가 완성한 보고서 (승인된 것만)
  - 계약 관련 활동 — 신규 계약 등록, 기존 계약 수정, 계약 만료·삭제
  - C/S 관련 활동 — C/S 대응요청 등록, 처리 상태·담당자 변경, 대응 이력·답변 등록
- **처리**: 위 입력을 결합해 계약 현황을 요약하고, 위험(만료·납품·장기 미접촉)을 판정하고, 다음 미팅이 필요한지 판단한다.
- **데이터가 부족할 때**: 보고서가 아직 승인 전이거나 필요한 항목(니즈·구매장벽·접촉신호·다음미팅안건)이 비어 있으면, 브리핑에 "무엇이 부족한지"를 그대로 보여준다 — 억지로 채우거나 추측하지 않는다. 계약관리 Agent MVP는 이 부분을 실제로 구현해뒀다: 보고서 쪽 출력을 `ApprovedMeetingInsight`(전부 optional 필드)로 받고, 값이 없으면 브리핑에 "승인된 미팅 분석 결과 연동 대기 중입니다"라고 표시한다(`backend/app/schemas/contract_briefing.py`, `backend/app/services/contract_briefing_llm.py`).
- **Output**: 다음 미팅 일정 제시 → 일정관리 Agent의 입력(`I`)이 된다.
- **브리핑은 이 시점에 만들지 않는다**: 일정관리 Agent가 추천한 다음 일정을 사용자가 승인해 계약관리 Agent로 다시 들어온 뒤에 생성한다(5단계).

### 4. 일정관리 Agent — 다음 일정을 추천하고, 계약관리 Agent와 계속 교류한다

- **Input**:
  - 계약관리 Agent의 "다음 미팅 일정 제시"
  - 일정 관련 활동 — 일정 등록·수정·취소, 캘린더
- **처리**: 위 정보를 바탕으로 다음 일정을 추천한다.
- **Output**: 다음 일정 추천 제시(화면 표시) → 사용자가 수정·승인하면 계약관리 Agent의 입력(`I`)이 된다(5단계).
- **교류(duplex)**: 계약관리 Agent와 일정관리 Agent는 한 방향 입출력 외에 별도로 양방향 교류를 한다. 예를 들어 사용자가 계약관리 Agent의 제안을 받아 일정관리 Agent에서 실제 미팅을 확정하면, 그 확정된 일정이 다시 계약관리 Agent로 돌아가 "최근 접촉 시각"에 반영돼야 다음 위험 판정(장기 미접촉)과 다음 미팅 제안이 최신 상태를 기준으로 계산된다. 이 교류의 정확한 전달 방식(API 호출 vs 공유 테이블 조회)은 아직 두 담당자 간 확정되지 않았다.

### 5. 계약관리 Agent 재진입 — 승인된 일정과 자료요약을 묶어 브리핑을 만든다

- **Input**:
  - 사용자가 승인한 다음 일정(일정관리 Agent 출력)
  - 이미 관리 중인 딜·계약 상태와 승인된 보고서
- **처리**: 브리핑을 만들 때 자료요약 Agent를 **RAG로 조회**해 자료실 문서의 요약을 근거로 함께 사용한다. 계약관리 Agent가 필요한 시점에 호출하고 자료요약 Agent가 응답하는 양방향 교류이며, 보고서작성 Agent가 미팅 원문을 읽는 "원문 참조"(단방향 참고 전달)와는 다르다.
- **Output**: 브리핑 생성
- 일정이 승인되지 않았거나 조회할 자료가 없어도 브리핑 자체는 만들어야 하며, 없는 근거는 채우지 않고 비어 있다고 표시한다.

## 설계 원칙: 이전 단계 데이터가 없어도 동작해야 한다

4개 Agent는 서로 다른 담당자가 서로 다른 속도로 개발한다. 그래서 각 Agent는 **앞 단계의 출력이 아직 없어도 최소한으로는 동작**해야 한다.

- 보고서작성 Agent 입력이 없으면 → 계약관리 Agent는 계약 활동만으로 위험 판정과 브리핑을 만들고, 고객 인사이트 섹션은 "연동 대기"로 비워 둔다.
- 계약관리 Agent 출력이 없으면 → 일정관리 Agent는 일정 관련 활동만으로 동작해야 한다.

계약관리 Agent MVP는 이 원칙을 지키려고 승인된 보고서 인풋(`ApprovedMeetingInsight`)과 일정관리로 보내는 아웃풋(`NextMeetingSuggestion`)을 둘 다 optional 스키마로 만들고, 값이 없을 때의 동작을 테스트로 확인해뒀다. 다른 Agent를 만들 때도 같은 패턴(입력 optional화 + 없을 때 사용자에게 상태 표시)을 권장한다.

## 사람 확인이 필요한 지점 (Human-in-the-loop)

| Agent | 지점 | 확인 전에는 |
|---|---|---|
| 보고서작성 | 초안 → 수정·승인 | 계약관리 Agent로 넘어가지 않음 |
| 계약관리 | 브리핑·다음 미팅 제안 | 계약·일정을 자동으로 바꾸지 않음(제안만) |
| 일정관리 | 다음 일정 추천 → 수정·승인 | 캘린더에 자동 등록하지 않음(추천만). 승인 전에는 계약관리 Agent의 브리핑 생성으로 넘어가지 않음 |

## 현재 구현 상태

- 미팅분석·보고서작성·일정관리 Agent: 실제 백엔드 구현 없음(설계 단계)
- 계약관리 Agent: 위험 판정, 브리핑 합성 인터페이스(목업), 일정관리로 보낼 다음 미팅 제안까지 구현됨. 실 API 엔드포인트와 실 LLM 연동은 진행 중 — [계약관리_Agent_MVP_ADR.md](계약관리_Agent_MVP_ADR.md)의 "이어서 진행할 작업" 참고
- Agent 간 실제 연결(보고서 완성 → 계약관리, 계약관리 ↔ 일정관리 교류, 승인된 일정 → 계약관리 재진입, 계약관리 ↔ 자료요약 RAG 조회)은 아직 아무것도 연결되지 않았고, 각 담당자 간 형식 합의가 먼저 필요하다
