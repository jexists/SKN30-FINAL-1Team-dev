# 딜 승산 모델의 입력 계약과 학습 흐름

> 기준일: 2026-08-31. 이 문서는 현재 입력과 실행 경로를 안내한다. 실험 수치와 선정 근거는 [머신러닝·딥러닝 학습결과서](머신러닝_딥러닝_학습결과서.md), 저장 파일과 검증 범위는 [학습한 ML/DL 모델 산출물](학습한_ML_DL_모델_산출물.md)을 기준으로 확인한다.

## 1. 현재 입력 계약

ML 모델은 미팅 원문을 직접 읽지 않는다. 미팅 분석 Agent가 원문에서 구조화한 다음 13개 범주형 값을 받는다.

| 컬럼 | 의미 |
|---|---|
| `Authority` | 고객 측 의사결정 권한 |
| `Competitors` | 경쟁사 존재·검토 여부 |
| `Purch_dept` | 구매부서 참여 여부 |
| `Budgt_alloc` | 예산 확보·배정 여부 |
| `Forml_tend` | 공식 입찰 여부 |
| `RFP` | 제안요청서 여부 |
| `Posit_statm` | 긍정적인 구매 표현 |
| `Source` | 영업기회 유입 경로 |
| `Client` | 고객과의 기존 거래 관계 |
| `Scope` | 계약·수행 범위의 명확성 |
| `Cross_sale` | 교차판매 여부 |
| `Deal_type` | 거래 유형 |
| `Needs_def` | 요구사항 정의 수준 |

허용 범주는 전처리 노트북의 `CATEGORY_VALUES`와 산출물 보고서에 정리한다. `Product`·`Seller`·`Att_t_client` 등 제외한 9개 컬럼은 현재 입력에 넣지 않는다. 22개 전체 컬럼으로 확장한다는 이전 계획은 현재 기준이 아니다.

확인되지 않은 값은 `Unknown`으로 유지한다. `No`는 사실이 없다고 확인한 값이므로 둘을 섞지 않는다. 실제 서비스 입력에는 임의 마스킹을 적용하지 않으며, 계약에 없는 범주를 조용히 무시하지 않는다.

## 2. 전처리와 학습 흐름

[Salvirt B2B Sales Dataset](https://www.salvirt.com/research/b2bdataset/)의 원본 448건을 유지한다. 완전 중복은 조사하되 삭제하지 않고, 같은 13개 입력 조합을 한 그룹으로 묶어 학습·평가 사이의 중복 노출을 막는다.

실제 미팅에서 값 일부를 확인하지 못하는 상황을 시험하기 위해, 원래 있던 `Unknown`을 보존하면서 행마다 총 4개 컬럼이 `Unknown`인 마스킹 10세트를 만든다. 같은 원본 행에서는 마스킹 조합이 겹치지 않으며 정답은 마스킹 위치를 정하는 데 사용하지 않는다. 이 변형들은 새 거래 10건을 의미하지 않는다.

현재 실행 순서는 다음과 같다. 상세 실행 방법은 [노트북 안내](../../backend/notebooks/README.md)에 있다.

1. [공통 전처리](../../backend/notebooks/deal_data_preprocessing.ipynb): 13개 범주·정답 `Lost=0/Won=1`·그룹·마스킹 세트를 만든다.
2. [RF 베이스라인](../../backend/notebooks/deal_model_paper_rf_baseline.ipynb): 논문의 RF와 30회 반복 분할 방식을 참고하되, 우리 데이터 조건에서 그룹 기준 8:2 분할로 평가한다.
3. [RF 튜닝](../../backend/notebooks/deal_model_paper_rf_tuning.ipynb): 각 외부 Train 내부의 5-Fold 그룹 CV에서 Brier 기준으로 파라미터를 선택한다.
4. [분류 앙상블](../../backend/notebooks/deal_model_paper_rf_ensemble.ipynb): RF·LR·ExtraTrees·CatBoost 단일 모델과 Soft Voting·Stacking을 비교하고 후보를 저장한다.

RF·LR·ExtraTrees는 모델 파이프라인 안에서 13개 범주를 원핫 인코딩한다. CatBoost는 같은 13개 범주형 컬럼을 직접 받는다. 분류 임계값은 `0.5`이며 정확도·AUC·Precision·Recall·F1·FP·FN도 함께 확인한다.

전처리 노트북에 남아 있는 Train 313건/Test 135건의 7:3 분할은 이전 실험 호환용이다. 최신 RF 흐름은 전체 마스킹 데이터와 그룹 ID를 가져와 별도로 30회 분리한다. 논문의 정확한 파라미터가 확인되지 않았고 입력·마스킹·그룹 분리도 다르므로 완전한 논문 재현이라고 부르지 않는다.

## 3. 새 배포용 연결과 이전 모델 기록

| 구분 | 새 배포용 연결 | 이전 모델 기록 |
|---|---|---|
| 식별자 | `deal-paper-rf-ensemble-v1` | `deal-stacking-lr-v1` |
| 기본 모델 | RF·LR·ExtraTrees·CatBoost | LR·MultinomialNB·ExtraTrees·CatBoost·TabICL |
| 결합 모델 | LogisticRegression Stacking | LogisticRegression Stacking |
| 저장 상태 | 첫 분할 원본 357건 × 마스킹 10세트의 선정 모델 유지 | 기존 모델 파일과 실험 기록 보존 |
| 연동 상태 | 로컬 로더·의존성·배포 스크립트 연결 완료, AWS 배포 전 | 기존 버전 디렉터리는 롤백용으로 보존 |

두 구성은 모두 `Stacking_LR`라는 이름을 쓰지만 서로 다른 모델이다. 최신 평가 평균과 저장 파일 한 개의 평가도 구분해야 한다. 새 `.joblib`을 기존 파일 이름으로 바꾸지 않고, 코드와 배포 파일을 같은 버전으로 맞춘다.

이번 작업은 기존 선정 모델의 가중치·임계값을 유지하고 로컬 백엔드를 연결한 것이다. 전체 데이터 재학습이나 AWS 업로드·배포는 하지 않았다. 두 ML 보고서와 제출용 DOCX·PDF는 연결 전 학습 결과 기록으로 보존한다. 현재 파일·해시·권한·배포 검사 기준은 [배포 인계](../../deploy/backend/README.md)에 정리한다. 이전 실험 노트북과 모델 저장 기록도 삭제하지 않는다.

## 4. 서비스 사용과 후속 검증

서비스에서는 구조화된 입력으로 `high_probability`를 계산하고, `계약가능성 높음(high)` 또는 `계약가능성 주의(watch)`를 참고 정보로 표시한다. 분류 결과로 거래 단계·실제 계약을 자동 변경하거나 담당자를 평가하지 않는다.

FP는 실제 Lost 거래를 Won으로 표시한 경우다. 주의가 필요한 거래를 놓칠 수 있으므로 확인해야 하지만, FP만 줄이다가 실제 Won 거래를 지나치게 놓치지 않도록 다른 지표도 함께 본다. Brier를 튜닝 기준으로 선택한 이유와 이 오류 비용의 해석은 학습결과서에 정리한다.

후속 작업은 `develop` 병합·모델 업로드 후 AWS의 새 후보 컨테이너에서 로딩·추론을 확인하고 실제 운영 데이터를 검증하는 것이다. 합성 입력의 추론 검사는 새 성능 평가가 아니며, 공개 데이터의 반복 평가 결과도 SalesLuv의 실제 한국어 미팅 성능을 보장하지 않는다. 이후 재학습 데이터는 예측 시점의 입력과 확정된 승패를 연결하며, 결과가 난 뒤의 정보가 입력에 섞이지 않도록 한다.

원본 CSV와 모델 파일은 Git에 추가하지 않는다. 데이터 출처를 표시하고, 상업적 사용이나 원본 재배포 전에는 제공자의 사용 조건을 확인한다.
