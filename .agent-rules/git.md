# Git 마무리

커밋·푸시·PR 생성 또는 수정을 요청받은 경우 해당 동작 직전에 읽습니다. 요청받은 단계까지만 수행하며, 커밋 요청을 푸시 권한으로, 푸시 요청을 PR 생성 권한으로, PR 요청을 병합 권한으로 확대하지 않습니다.

브랜치의 작업 범위·이름·대상은 [`branching.md`](branching.md)를 기준으로 합니다.

## 1. 실행 전 확인

- `git status --short --branch`로 현재 브랜치와 staged·unstaged·untracked 변경을 모두 확인합니다.
- `git diff --name-status`, `git diff --stat`, `git diff`로 추적 중인 변경과 삭제·이름 변경을 확인합니다.
- `git ls-files --others --exclude-standard`로 diff에 표시되지 않는 untracked 파일도 확인합니다.
- staged 변경이 있으면 `git diff --cached`로 현재 요청에 속하는지 확인합니다.
- detached HEAD이거나 `main`, `develop`에서 일반 작업을 커밋·푸시하려는 상태면 중단하고 알립니다.
- 푸시나 PR 전에는 원격 상태를 확인합니다. `git pull`, merge, rebase는 자동으로 실행하지 않습니다.
- 변경 범위에 맞는 테스트·lint·빌드·문서 검사를 실행하고 `git diff --check`도 확인합니다.
- 실행하지 못한 검사와 실패한 검사는 숨기지 않고 사유와 함께 알립니다.
- 비밀값, 실제 개인정보·의료 데이터, 원본 수집 자료, 위치 메타데이터, 허가되지 않은 외부 자료가 포함되지 않았는지 확인합니다.

## 2. 변경 분리와 staging

- 현재 요청과 직접 관련된 파일 또는 hunk만 staging합니다.
- 기본적으로 `git add -- <명시적 경로>`를 사용합니다.
- 사용자나 다른 작업의 변경이 있는 작업트리에서는 `git add .`, `git add -A`처럼 범위가 넓은 staging을 사용하지 않습니다.
- 삭제 파일과 새 파일은 파일명만 보고 포함하지 않고 실제 내용과 의도를 확인합니다.
- 관련 없는 변경은 staging하지 않으며 작업트리를 정리하려고 삭제·복원·stash하지 않습니다.
- 한 hunk에 서로 다른 작업이 섞여 안전하게 분리할 수 없으면 중단하고 사용자에게 확인합니다.
- staging 후 `git diff --cached --name-status`, `git diff --cached --stat`, `git diff --cached --check`, `git diff --cached`로 커밋될 내용을 다시 확인합니다.
- staged 변경이 없으면 빈 커밋을 만들지 않습니다.

## 3. 커밋

- 하나의 커밋에는 독립적으로 설명·검토·되돌릴 수 있는 하나의 작업 의도만 담습니다.
- 커밋 메시지는 Conventional Commits 형식을 사용합니다.

  ```text
  <type>[(scope)][!]: <요약>
  ```

- `type`은 변경 성격에 맞게 선택합니다.
  - `feat`: 기능 추가
  - `fix`: 버그 수정
  - `docs`: 문서만 변경
  - `refactor`: 기능 변화 없는 구조 개선
  - `test`: 테스트 추가·수정
  - `perf`: 성능 개선
  - `build`: 빌드·의존성 변경
  - `ci`: CI 설정 변경
  - `chore`: 그 밖의 유지보수
- `scope`는 의미가 분명할 때만 사용하고, 요약은 실제 변경 결과를 간결하게 표현합니다.
- 예: `docs: AI 브랜치 및 Git 작업 규칙을 구체화`
- 호환성을 깨는 변경은 `!`와 `BREAKING CHANGE:` footer로 명시합니다.
- 커밋 후 `git show --stat --oneline HEAD`와 `git status --short --branch`로 실제 커밋과 남은 변경을 확인합니다.
- hook이 실패하거나 파일이 추가로 수정되면 상태를 다시 확인하며 자동으로 `--amend`하지 않습니다.

## 4. 푸시

- 푸시는 명시적으로 요청받았을 때만 수행합니다.
- `main`, `develop`에는 직접 푸시하지 않습니다.
- upstream이 없으면 동일 이름의 원격 브랜치가 이미 존재하는지 확인한 뒤 현재 브랜치를 push합니다.
- upstream이 있으면 로컬과 원격의 ahead·behind 상태를 확인한 뒤 일반 push를 사용합니다.
- non-fast-forward 거절이 발생하면 중단하고 원격 변경을 알립니다. 자동으로 pull, merge, rebase 또는 force push하지 않습니다.
- 푸시 후 로컬 `HEAD`와 upstream 커밋이 일치하는지 확인합니다.

## 5. PR

- 같은 head 브랜치의 열린 PR이 있는지 확인해 중복 PR을 만들지 않습니다.
- 작업 브랜치는 `develop`을 대상으로, `develop`은 `main`을 대상으로 PR을 생성합니다.
- 생성 전 head·base, 커밋 목록, 전체 diff가 현재 작업 범위와 일치하는지 확인합니다.
- PR 제목과 본문은 기본적으로 한국어로 작성합니다.
- 제목은 변경 결과를 한 문장으로 요약하고, 본문에는 다음 내용을 포함합니다.

  ```md
  ## 변경 요약

  - 변경 사항과 목적

  ## 검증

  - 실행한 검사와 결과
  - 미실행 검사가 있다면 사유

  ## 영향 및 주의 사항

  - 영향 범위, 수동 적용 작업, 후속 작업 또는 없음

  ## 관련 이슈

  - 관련 이슈가 있을 때만 기재
  ```

- 실행하지 않은 검사를 통과했다고 쓰지 않고, 진행 중인 CI를 완료로 표현하지 않습니다.
- PR 생성 후 URL, 상태, head·base, 제목·본문, CI 상태를 확인합니다.
- PR 생성 요청은 리뷰어·라벨 지정, 승인, 병합 권한을 포함하지 않습니다.

## 6. 이력과 변경 보호

- 관련 없는 변경을 없애기 위해 `restore`, `checkout`, `reset`, `clean`, `stash`하지 않습니다.
- `commit --amend`, rebase, squash 등 공개된 커밋 이력을 자동으로 다시 쓰지 않습니다.
- force push, 브랜치·태그·원격 ref 삭제, 원격 주소·Git 전역 설정 변경은 별도 명시적 요청과 영향 확인 없이는 수행하지 않습니다.
- PR을 닫거나 병합하거나 기존 리뷰 상태를 변경하지 않습니다.
- 관련 없는 변경이 남아 있어도 현재 작업을 안전하게 분리할 수 있으면 그대로 두고 완료 보고에 알립니다.

## 7. 완료 보고

- 생성한 커밋 해시와 메시지
- 푸시한 원격 브랜치
- 생성하거나 갱신한 PR URL과 base·head
- 실행한 검사와 결과, 실행하지 못한 검사와 사유
- 커밋에 포함하지 않고 작업트리에 남겨 둔 관련 없는 변경
