# 브랜치 전략

이 문서는 새 독립 작업 단위를 시작할 때 현재 브랜치를 계속 사용할지, 새 브랜치로 분리할지를 정합니다. 파일을 수정할 때마다 새 브랜치를 만들지 않습니다.

## 1. 시작 전 확인

- 먼저 `git status --short --branch`로 현재 브랜치와 staged·unstaged·untracked 변경을 확인합니다.
- 읽기·조사·설명만 하는 작업에는 브랜치를 만들거나 전환하지 않습니다.
- 변경량이나 파일 수가 아니라 작업 목적과 PR·롤백 경계로 판단합니다.
- 같은 워크트리를 여러 에이전트가 공유하면 주 작업 에이전트만 브랜치를 생성·전환합니다.

## 2. 현재 브랜치를 계속 사용하는 경우

다음 조건을 모두 만족하면 현재 브랜치를 이어서 사용합니다.

- 현재 변경과 새 요청이 같은 사용자 목표 또는 같은 이슈·PR에 속합니다.
- 변경을 하나의 PR에서 함께 검토·병합·롤백하는 것이 자연스럽습니다.
- 현재 브랜치가 `main` 또는 `develop`이 아닙니다.

같은 기능의 보완, 버그 수정, 테스트·문서 추가, 리뷰 반영은 보통 기존 브랜치에서 계속합니다. 후속 요청이 들어왔다는 이유만으로 새 브랜치를 만들지 않습니다.

## 3. 새 브랜치로 분리하는 경우

다음 중 하나면 별도 브랜치로 분리합니다.

- 기존 작업과 목적이 다른 기능·버그·리팩터링·문서 작업입니다.
- 별도 PR로 검토하거나 독립적으로 병합·롤백해야 합니다.
- 기존 작업 브랜치가 이미 병합되었거나 종료되었습니다.
- 수정 작업을 시작하는데 현재 브랜치가 `main` 또는 `develop`입니다.

파일이 겹친다는 이유만으로 같은 작업으로 보지 않고, 수정량이 작다는 이유만으로 기존 브랜치에 섞지 않습니다. 다른 브랜치의 미병합 변경이 필요하면 임의로 복사하지 말고 선행 병합이나 stacked PR 필요 여부를 확인합니다.

## 4. 기존 변경 보호

- 기존 변경이 현재 작업에 속하면 해당 브랜치에서 계속합니다.
- 다른 작업이거나 소유·의도가 불분명한 변경은 임의로 stash, commit, reset, restore, checkout하지 않습니다.
- 별도 작업을 병행해야 하면 기존 변경을 건드리지 않는 별도 worktree를 사용합니다. 기준 브랜치나 경로가 불분명하면 먼저 확인합니다.
- 같은 파일이나 hunk에 서로 다른 작업이 섞여 안전하게 분리할 수 없으면 중단하고 범위를 확인합니다.

## 5. 기준 브랜치와 이름

- 새 작업 브랜치는 확인 가능한 최신 `develop`을 기준으로 만듭니다.
- 가능하면 먼저 원격 `develop` 상태를 확인합니다. 확인하지 못했다면 로컬 브랜치가 최신이라고 가정하지 않고 기준 커밋과 제약을 알립니다.
- 브랜치 이름은 `<GitHub 사용자명>/<짧은 작업명>` 형식을 사용합니다.
- 작업명은 영문 소문자·숫자의 kebab-case로 작성합니다. 예: `jexists/docs-agent-rules`.
- GitHub 사용자명은 인증된 계정의 login을 사용합니다. 저장소 소유자, OS 사용자명, `git config user.name`으로 추측하지 않으며 확인할 수 없으면 사용자에게 묻습니다.
- 진행 중이거나 공유된 기존 브랜치는 이름 규칙만 맞추기 위해 자동으로 변경하지 않습니다.

## 6. 병합 흐름과 롤백 경계

- 작업 브랜치는 `develop`으로, `develop`은 릴리스 시 `main`으로 PR을 통해 병합합니다.
- `main`과 `develop`에서 일반 작업을 직접 커밋하거나 푸시하지 않습니다.
- 한 브랜치에는 독립적으로 설명·검토·롤백할 수 있는 한 가지 작업 목적만 둡니다.
- 해당 기능에 필요한 테스트·문서·마이그레이션은 같은 브랜치에 포함할 수 있습니다. 무관한 포맷 정리·리팩터링·의존성 갱신은 분리합니다.
- 병합된 브랜치를 새 작업에 재사용하지 않고 최신 `develop`에서 새 브랜치를 만듭니다.
- Git 롤백은 저장소 변경만 되돌립니다. 이미 적용된 DB·배포·외부 시스템 변경에는 별도의 복구 절차와 명시적 승인이 필요합니다.
